通过结构化追问帮助用户将模糊的"怎么测"转化为精确的、可执行的测试用例规格。

## 核心理念

测试用例的价值不在数量，而在**能否证伪**——好的测试用例能在修复前 100% 重现问题、修复后 100% 通过。如果一个测试用例修复前也能通过，它就是无效的。

> "如果你的测试在 bug 存在时也是绿的，那它根本不是在测试任何东西。"

## 适用场景

- Bug 修复后需要验证修复有效
- 新功能需要设计验收测试
- 需要设计对照组实验（修复前 vs 修复后）
- 性能/并发/超时等非功能性场景的测试设计

## 追问方法论

### 第 0 轮：理解测试目标（What to Prove）

先搞清楚用户想通过测试证明什么。

操作：
- 从用户描述中提取：1）要验证的功能/修复 2）问题的重现条件 3）期望的正确行为
- 复述："你想验证的是——在 XX 条件下，系统应该 YY 而不是 ZZ，对吗？"
- 标记不确定的部分

### 第 1 轮：现状调研（Context Research）

**了解被测代码的结构、现有测试、测试基础设施。**

操作：
- 使用 `Task`（Explore）或 `Grep`/`Read` 调研：
  - 被测代码的核心逻辑和关键路径
  - 已有的测试文件和测试模式（单元测试/集成测试/E2E）
  - 测试基础设施（mock 方式、fixture、helper）
  - 可控的输入变量和可观测的输出
- 识别：哪些行为可以在单元测试中验证、哪些必须用集成/E2E 测试

### 第 2 轮：场景分解（Scenarios）

**将模糊的"测一下"拆分为具体的、可枚举的测试场景。**

追问方向：
- **正向场景**：正常路径应该产生什么结果？
- **故障注入场景**：模拟什么故障来验证容错能力？（超时、网络断开、API 报错、并发竞态）
- **边界场景**：极端输入（0 个、1 个、最大数量）的预期行为？
- **对照场景**：修复前 vs 修复后，同一输入应该产生不同的结果——具体是什么不同？
- **回归场景**：修复是否可能破坏已有功能？需要回归验证什么？

技巧：
- 用 `AskUserQuestion` 给出场景选项让用户勾选，附带"你还想覆盖哪些场景？"的开放选项
- 结合代码调研，主动提出用户可能遗漏的场景
- 每个场景要能独立运行、独立判断 pass/fail

### 第 3 轮：Mock 与控制（How to Simulate）

**确认如何制造测试条件。** 尤其是故障场景——不能等真实故障发生。

追问方向：
- **依赖 Mock**：外部 API、数据库、AI 模型调用怎么 mock？用什么 mock 库/方式？
- **时间控制**：超时场景怎么模拟？用真实等待还是 fake timer？
- **并发控制**：并发竞态怎么稳定重现？用 delay 注入还是同步屏障？
- **数据准备**：测试数据怎么准备？用 fixture、seed、还是 factory？
- **环境隔离**：测试之间互相影响吗？需要清理/重置什么？

技巧：
- 结合项目已有的测试基础设施给建议
- 区分"单元测试可 mock"和"必须真实运行"的部分
- 对照组实验需要保证**唯一变量**——除了修复代码，其他条件完全一致

### 第 4 轮：断言与判定（How to Judge）

**确认每个场景的 pass/fail 判定标准。**

追问方向：
- **结果断言**：检查什么值/状态？精确匹配还是模式匹配？
- **时序断言**：操作应该在多少时间内完成？超时阈值是多少？
- **副作用断言**：数据库状态、日志输出、API 调用次数等副作用怎么验证？
- **否定断言**：什么情况不应该发生？（不应该卡住、不应该报错、不应该泄漏资源）
- **容忍度**：允许多少误差？（如"90% 的 case 应该在 60s 内完成"vs"每个 case 必须在 60s 内完成"）

技巧：
- 每个场景至少一个 assert，最好是一个主断言 + 辅助断言
- 避免"不报错就算通过"——要有明确的成功条件
- 对照组的判定特别注意：修复前应该 fail、修复后应该 pass

### 第 5 轮：测试层级（Where to Test）

**确认在哪一层写测试最合适。**

追问方向：
- **单元测试**：能否隔离核心逻辑、mock 依赖后验证？优先考虑
- **集成测试**：需要真实数据库/API 交互吗？
- **E2E 测试**：需要从前端 UI 走完整流程吗？
- **手动验证**：有些场景只能手动验证吗？如何标准化手动验证步骤？

技巧：
- 测试金字塔：单元测试 > 集成测试 > E2E 测试（数量递减）
- 对照组实验通常在集成/E2E 层面最有说服力
- 结合项目的测试栈（Vitest + Testing Library + Playwright）给建议

## 执行规则

1. **善用 `AskUserQuestion` 给选项**：测试场景天然适合 checklist 式追问
2. **每轮 2-3 个问题**：不要一次列出所有可能的测试场景
3. **先调研再追问**：了解被测代码和现有测试后，追问才有针对性
4. **跳过已明确的**：用户已经描述清楚的场景直接确认
5. **收敛到可执行**：输出的测试用例规格必须能直接用来写代码
6. **对照组思维**：修复类测试必须同时描述"修复前应 fail"和"修复后应 pass"

## 输出格式

当测试方案足够清晰后，输出结构化测试用例规格：

```markdown
## 测试规格：{被测功能/修复}

### 测试目标
{一句话描述要验证什么}

### 测试层级
{单元测试 / 集成测试 / E2E / 混合}

### 测试场景

#### 场景 1：{场景名}
- **前置条件**：{数据准备、mock 配置}
- **操作步骤**：{触发什么操作}
- **预期结果**：{pass 条件}
- **对照**：{修复前的表现 vs 修复后的表现，如适用}

#### 场景 2：{场景名}
- ...

### Mock 策略
- {外部依赖 A}：{mock 方式}
- {外部依赖 B}：{mock 方式}

### 数据准备
- {fixture / seed / factory 策略}

### 回归检查
- [ ] {已有功能不被破坏的验证点}
```

## 与其他技能的协作

- **clarify 之后**：需求澄清确定"做什么"后，调用本技能设计验收测试
- **worktree 配合**：为工作区（修复分支 / 对照分支）分别生成测试用例
- **独立使用**：任何需要设计测试方案的场景都可调用

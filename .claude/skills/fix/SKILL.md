读取缺陷报告 → 修复代码 → 自测验证 → 生成修复报告。

## 核心理念

缺陷报告传递的是**观察**（我看到了什么），修复报告传递的是**决策**（我做了什么以及为什么）。

diff 能看到改动本身，但不会告诉你**为什么这样改**，也不会告诉你**考虑过但没采用的方案**。修复报告的价值在于记录决策，保护未来维护者。

### 与缺陷报告的镜像关系

```
缺陷报告                      修复报告
────────                      ────────
Delta (现象)     ──回答──→    Root Cause (成因)
  "什么坏了"                    "为什么坏了"

Location (位置)  ──回应──→    Change (变更)
  "在哪里"                      "改了哪里"

Path (路径)      ──镜像──→    Verification (验证)
  "怎么触发"                    "怎么确认修好"

Impact (影响)    ──反转──→    Blast Radius (波及)
  "坏了多少"                    "修复波及多少"

    ∅            ──新增──→    Rationale (决策)
                                "为什么这样修"
```

## Phase 0: 读取缺陷报告

### 操作

1. 读取 `.task/DEFECT.md`，提取四要素：
   - **Delta**：期望行为、实际行为、偏差描述
   - **Path**：复现步骤、环境、数据依赖
   - **Location**：功能模块、代码定位、根因分析
   - **Impact**：严重度、影响范围

2. 如果 `DEFECT.md` 不存在，用 `AskUserQuestion` 提示用户先运行 `/diagnose`

3. 向用户简要复述缺陷要点，确认理解正确后进入修复

## Phase 1: 修复实施

### 目标
基于缺陷报告的 Location + 根因分析，实施最小化修复。

### 操作

1. **读取相关代码**
   - 按 DEFECT.md 中的"代码定位"逐个 `Read` 涉及文件
   - 理解上下文、调用关系

2. **设计修复方案**
   - 构思 2-3 个可能的方案
   - 选择最小化、最安全的方案
   - 记录被排除的方案及原因（Phase 3 写入 Rationale）

3. **实施修改**
   - 用 `Edit` 修改代码，遵循项目约定（CLAUDE.md）
   - 每个修改点记录：文件路径、修改前后对比、修改原因
   - **只改问题本身，不顺手重构**

4. **静态检查**
   ```bash
   make typecheck
   make test
   ```
   - 如果失败，修复引入的问题后重新检查
   - 如果现有测试因行为变更而失败，评估是否需要同步更新测试

## Phase 2: 自测验证

### 目标
用 Playwright 走一遍缺陷报告中的复现路径，确认缺陷已消除；再检查影响范围。

### 操作

#### 2.1 检查环境
检查 dev 服务器是否在运行：
```bash
curl -s -o /dev/null -w "%{http_code}" http://localhost:{端口号} 2>/dev/null
```
如果存在 `.worktree/meta.json`，从中读取端口号；否则使用默认 3000。

如果未运行：`make up`（`run_in_background=true`），轮询等待就绪，**最多 15s**。超时则 `make down` + `make up` 重启，仍失败则报错给用户。

#### 2.2 正向验证（复现路径不再触发缺陷）
1. 按 DEFECT.md 的复现步骤逐步操作
2. 在原来出现缺陷的步骤截图
3. 确认期望行为已恢复

#### 2.3 回归验证（影响范围无回归）
1. 根据修改涉及的模块，检查相关功能
2. 如果修改影响了布局/样式：不同视口尺寸下截图检查
3. 如果修改影响了数据流：验证上下游数据一致性

#### 2.4 截图命名
- `.task/FIX_REPORT.assets/fix-{简述}-verify.png` — 正向验证截图
- `.task/FIX_REPORT.assets/fix-{简述}-regression-{N}.png` — 回归验证截图

## Phase 3: 生成修复报告

### 五个不可约元素

从验证者的认知需求反推，缺少任何一个都无法完成验收：

```
            修复报告
               │
      ┌────────┼────────┐
      │        │        │
 Root Cause  Change  Rationale
 (为什么坏)  (改了啥) (为什么这样改)
      │        │        │
      └────────┼────────┘
               │
      ┌────────┴────────┐
      │                 │
 Blast Radius      Verification
 (还动了什么)      (怎么证明好了)
```

1. **Root Cause（根因）**——"为什么坏了"：缺陷的真正成因，不是症状。Delta 是果，Root Cause 是因
2. **Change（变更）**——"具体改了什么"：把散落的 diff 组织成可理解的叙事，而非全量 diff
3. **Rationale（决策依据）**——"为什么这样改"：选择此方案的理由 + 被排除的替代方案 + 已知局限。**这是修复报告独有的元素**——缺陷报告是观察不做决策，修复报告是行动必须解释决策
4. **Blast Radius（影响范围）**——"还影响了什么"：修复的扩散面。明确标注直接影响、间接影响、不影响的部分
5. **Verification（验证方式）**——"怎么证明修好了"：正向验证（原路径不再触发）+ 回归验证（影响区域无回归）

### 资源管理

所有修复产物统一放在 `.task/` 下：
```
.task/
├── DEFECT.md                         # 缺陷报告（输入）
├── DEFECT.assets/                    # 缺陷截图
├── FIX_REPORT.md                     # 修复报告（输出）
└── FIX_REPORT.assets/                # 修复截图
    ├── fix-{简述}-verify.png
    └── fix-{简述}-regression-{N}.png
```

### 报告模板

```markdown
# 修复报告：{一句话标题}

> 修复时间：{YYYY-MM-DD HH:mm}
> 关联缺陷：[DEFECT.md](DEFECT.md)
> 分支：`{branch}`

## 1. Root Cause（根因）

### 为什么坏了
{缺陷的真正成因——机理层面的解释，不是症状复述}

### 因果链
{从触发条件到最终表现的完整因果链}
1. {起因}
2. → {传导}
3. → {最终表现}

## 2. Change（变更）

### 修改摘要
{用 1-3 句话概括逻辑上做了什么，把散落的 diff 组织成叙事}

### 修改明细
| 文件 | 改动 | 说明 |
|------|------|------|
| `path/to/file.ts:行号` | {修改前 → 修改后} | {为什么改这里} |
| ... | ... | ... |

## 3. Rationale（决策依据）

### 为什么选择此方案
{选择理由}

### 考虑过的替代方案
| 方案 | 未采用原因 |
|------|-----------|
| {方案 A} | {原因} |
| {方案 B} | {原因} |

### 已知局限
{此方案的局限或后续需要跟进的事项。无则写"无"}

## 4. Blast Radius（影响范围）

### 直接影响
- {修改的代码被哪些功能调用}

### 间接影响
- {行为变化是否引发上下游连锁。无则写"无"}

### 不影响
- {明确声明不受影响的部分，减少验证者焦虑}

## 5. Verification（验证方式）

### 静态检查
- `make typecheck`：{通过/失败}
- `make test`：{通过/失败}

### 正向验证
按缺陷报告复现路径操作，缺陷不再出现：
1. {步骤}
2. ...
3. → 预期行为已恢复

| 验证项 | 截图 |
|--------|------|
| 修复后 | ![verify](FIX_REPORT.assets/fix-{简述}-verify.png) |

### 回归验证
Blast Radius 标记的影响区域走一遍，行为正常：
- {验证项 1}：正常
- {验证项 2}：正常

## 过程备注

{执行过程中捕获的学习信号。无则留空}
```

### 报告自检清单

- [ ] **Root Cause**：解释了机理而非复述症状？因果链完整？
- [ ] **Change**：修改叙事清晰？非维护者能理解？
- [ ] **Rationale**：有替代方案对比？未来维护者知道"别删这段代码"？
- [ ] **Blast Radius**：直接/间接/不影响都标了？验证者知道该额外检查什么？
- [ ] **Verification**：正向 + 回归都验了？截图附了？

### 流程

1. 生成报告内容，展示给用户
2. 用 `AskUserQuestion` 确认报告是否准确
3. 确认后写入 `.task/FIX_REPORT.md`
4. 告知用户后续操作（如 `/verify` 验证、`/test-guard` 守护等）

## 执行规则

1. **先读缺陷报告**：不要凭空修复，必须基于 DEFECT.md 的定位和分析
2. **最小化修改**：只改问题本身，不顺手重构、不加无关优化
3. **记录决策**：修复过程中考虑过的方案都要记下，写入 Rationale
4. **必须自测**：用 Playwright 走完复现路径，不能只靠 typecheck/test
5. **静态检查不跳过**：`make typecheck` + `make test` 必须通过
6. **截图取证**：修复后的正向验证必须截图
7. **环境启动不卡死**：15s 超时就 `make down` + `make up` 重启，仍失败报错
8. **过程备注**：执行过程中遇到重试、惊讶、绕路、确认、环境等偏差信号时，记录到报告的「过程备注」节。格式：`[重试/惊讶/绕路/确认/环境] 简述`

## 与其他技能的协作

- **典型流程**：`/diagnose` → 缺陷报告 → `/fix` → 修复报告 → `/pr-wt` 或 `/pr` 提交
- **在工作区内使用**：先 `/create-wt` 创建工作区 → `/fix` 修复 → `/pr-wt` 合并
- **独立使用**：如果缺陷简单明确，也可以手动创建 DEFECT.md 后直接 `/fix`

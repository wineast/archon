需求与问题记录技能——通过更新 `web/guide/` 使用文档来记录需求和问题，基于 git diff 驱动工作区创建。

## 核心理念

**`web/guide/` 使用文档是唯一的 source of truth。** 不创建 backlog 文件，不维护功能树索引。

- 新功能/改进 → 创建或更新 `web/guide/` 文档
- Bug/清理 → 在对应 `web/guide/` 文档中标注已知问题
- `git diff web/guide/` = 待办清单

## 触发条件

当用户提到以下任意表述时，应调用此技能：
- "开启记录模式"、"记录模式"
- "记录一下"、"记个需求"
- "这是个 bug"、"发现个问题"
- "我想要..."、"需要一个..."
- "创建工作区"、"基于这些创建工作区"

## 核心工作流

```
用户："开启记录模式"
  ↓
记录模式（只更新文档，不实现）
  用户报告问题/描述需求 → 更新 web/guide/ 文档 → 简短确认 → 等待下一个
  ...
  ↓
用户："创建工作区"
  ↓
git diff web/guide/ → 分析变更 → 分组 → 提交文档变更 → 调用 /worktree 创建工作区
```

### 1. 记录模式

用户说"开启记录模式"后进入此模式：

- **只更新文档，不实现**：不修改任何业务代码，不进入规划模式
- **快速响应**：每次用户报告时，快速分析 + 更新文档 + 简短确认
- **允许简要分析**：可以用 `Grep`/`Read` 快速查看相关代码以准确更新文档，但不做任何业务代码修改
- **采访式需求澄清**：描述模糊时通过 `AskUserQuestion` 追问。**在离用户最近的时刻澄清**，而不是留到创建工作区时。

  **应该问的**（用户意图、需求、偏好）：
  - 期望的最终效果是怎样的？
  - 有没有偏好的方案方向？
  - 有什么约束或注意事项？

  **不该问的**（代码实现细节，Claude 自己读代码就知道）：
  - 当前代码怎么实现的？用了什么组件？
  - 数据库表结构是怎样的？

  如果描述和方向已经足够清晰，跳过采访直接记录。

#### 文档结构要求

每个 guide 文档开头必须有一段简短的**用户需求说明**——这个功能解决什么问题、为什么需要它。让读者一眼就明白动机，而不只是看到操作步骤。

格式：文档标题下方、正文之前，用一段话说明背景和需求。例如：

```markdown
# 嵌入式 Widget

企业客户需要把 Agent 聊天嵌入自己的网站，而不是让用户跳转到 Archon 平台。Widget 通过一行 script 标签完成集成，零前端开发成本。

## 快速开始
...
```

#### 文档更新规则

| 类型 | 操作 |
|------|------|
| 新功能 | 在 `web/guide/` 下创建新文档（或更新现有文档的新章节），描述功能的使用方式和行为 |
| 改进 | 更新对应 `web/guide/` 文档，修改或扩展相关描述 |
| Bug | 在对应 `web/guide/` 文档末尾的 `## 已知问题` 章节添加条目 |
| 清理 | 在对应 `web/guide/` 文档末尾的 `## 已知问题` 章节添加条目（标注为技术债） |

创建新文档或更新现有文档时，如果文档开头缺少用户需求说明，一并补上。

**Bug/清理标注格式**：

在对应文档末尾维护一个 `## 已知问题` 章节：

```markdown
## 已知问题

- 某个按钮点了没反应，原因是...
- （技术债）某处代码需要重构为...
```

如果文档中已有此章节，追加条目。如果没有，在文档末尾新增。

**guide/README.md 同步**：如果创建了新文档，在 `web/guide/README.md` 的目录中添加对应条目。

**确认格式**：`已记录 — {简短标题}（web/guide/{file}.md）`

### 2. 创建工作区

用户说"创建工作区"时：

1. 查看 `web/guide/` 目录的 git diff：
   ```bash
   git diff web/guide/
   git diff --name-only web/guide/
   git status web/guide/
   ```
2. 分析变更内容——每个文件的新增/修改/已知问题就是要实现的任务
3. 按**可并行原则**分组：无依赖的变更分到不同工作区，有强关联的合入同一工作区
4. **直接执行，不要反复确认分组方案**
5. 提交 `web/guide/` 变更到当前分支（让工作区分支能包含文档变更）：
   ```bash
   git add web/guide/
   git commit -m "docs: update guide for upcoming changes"
   ```
6. 调用 `/worktree` 技能为每组创建工作区，传入对应的 web/guide/ 文件变更列表（即 `guideDocs` 数组，如 `["web/guide/schemas.md"]`）。worktree 技能会将此列表写入 `meta.json`，用于合并时回溯更新文档。

## 注意事项

- 记录模式下严禁修改业务代码
- `web/guide/` 文档是面向使用者的说明，用清晰的用户视角编写
- Bug 修复后，实现时应移除对应的「已知问题」条目
- 如果某个问题找不到对应的 web/guide/ 文档（比如纯内部实现问题），在最相关的文档中标注，或创建一个新的 guide/ 文档

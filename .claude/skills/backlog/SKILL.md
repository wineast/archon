Backlog 管理技能——在 `backlog/` 目录下统一记录 issue 和需求，积累后批量创建工作区解决。

## 触发条件

当用户提到以下任意表述时，应调用此技能：
- "开启记录模式"、"记录模式"
- "记录一下"、"记个 backlog"、"记个 issue"、"记个需求"
- "这是个 bug"、"发现个问题"
- "我想要..."、"需要一个..."、"新功能"
- "查看 backlog"、"有哪些 issue"、"有哪些需求"
- "关闭"、"这个修了"、"这个做完了"

## 条目类型

每条记录有一个 `type` 字段，决定其行为差异：

| 类型 | 含义 | 功能树同步 | 模板最后一节 |
|------|------|-----------|-------------|
| `bug` | 缺陷、错误 | 可选（影响功能时才同步） | `## 修复方向` |
| `cleanup` | 代码清理、技术债 | 可选 | `## 修复方向` |
| `feature` | 新功能 | **必须** | `## 验收标准` |
| `improvement` | 增强、优化 | **必须** | `## 验收标准` |

## 目录结构（文件夹即状态）

```
backlog/
  open/           ← 新记录、待处理
  in-progress/    ← 已分配工作区，开发中
  archived/       ← 已完成
```

- 文件通过所在文件夹表示状态，**文件内不写状态字段**
- 状态变更 = 移动文件到对应文件夹

## 核心工作流

```
用户："开启记录模式"
  ↓
记录模式（只记录，不实现）
  用户报告问题/描述需求 → 创建文件到 backlog/open/ → 简短确认 → 等待下一个
  ...
  ↓
用户："基于这些 backlog 创建工作区"
  ↓
读取 backlog/open/ 下所有条目 → 分组 → 调用 /worktree 创建工作区 → 移动到 backlog/in-progress/
```

### 1. 记录模式

用户说"开启记录模式"后进入此模式：

- **只记录，不实现**：不要去修改任何业务代码，不要进入规划模式
- **快速响应**：每次用户报告问题/描述需求时，快速分析 + 创建文件 + 简短确认
- **允许简要分析**：可以用 `Grep`/`Read` 快速查看相关代码以写出准确的分析，但不做任何修改
- **自动判断类型**：根据用户描述自动判断 type（bug/cleanup/feature/improvement）
- **功能树同步**：
  - `feature` / `improvement`：必须同步 `features/README.md`
  - `bug` / `cleanup`：仅当会导致功能变更时同步（纯修复不影响功能的跳过）
- **确认格式**：
  - 无功能树关联：`已记录 — {标题}`
  - 有功能树关联：`已记录 — {标题}（已同步功能树）`

### 2. 创建工作区

用户说"基于这些 backlog 创建工作区"时：

1. 读取 `backlog/open/` 下所有条目
2. 分析条目间的关联和依赖，合理分组
3. 向用户展示分组方案（哪些条目放在一个工作区）
4. **采访式需求澄清**：分组确认后，针对每个工作区通过 `AskUserQuestion` 向用户提问，挖掘真实意图和偏好。

   **应该问的**（用户意图、需求、偏好）：
   - 期望的最终效果是怎样的？
   - 有没有偏好的方案方向？
   - 有什么约束或注意事项？

   **不该问的**（代码实现细节，Claude 自己读代码就知道）：
   - 当前代码怎么实现的？用了什么组件？
   - 数据库表结构是怎样的？

   采访通常 1-2 轮即可，如果描述和方向已经足够清晰，可以跳过采访。

5. 调用 `/worktree` 技能为每组创建工作区（将采访结果作为上下文传入）
6. 将对应文件移动到 `backlog/in-progress/`，并在文件中添加 `- **工作区**: {name}` 字段

## 文件规范

- 新建条目放入 `backlog/open/`
- 文件名格式：`{简短描述}.md`（例：`build-assistant-no-default-model.md`），用英文短横线连接
- 创建前用 `Glob` 检查 `backlog/` 下所有子目录是否已有同名文件，避免重复

### 模板

```markdown
# {标题}

- **类型**: bug | cleanup | feature | improvement
- **优先级**: low | medium | high | critical
- **发现日期**: YYYY-MM-DD
- **功能树**: {功能树中对应条目的名称，feature/improvement 必填，bug/cleanup 可选}
- **工作区**: {worktree 名称，创建工作区时填入，新建时不写此行}

## 描述

{详细描述}

## 分析

{技术分析、涉及的文件和代码位置}

## 修复方向 / 验收标准

{bug/cleanup 用"修复方向"，feature/improvement 用"验收标准"}
```

字段说明：
- 类型：根据用户描述自动判断
- 截图：如果用户提供了截图，在描述中注明"见对话中截图"
- 分析：引用具体文件路径和行号，尽量具体
- 功能树：feature/improvement 必填；bug/cleanup 仅当影响功能时填写
- 工作区：新建时不写此字段；分配工作区时添加

## 其他操作

### 查看 backlog

列出 `backlog/` 下各子目录的条目，按状态分组展示。可选按类型筛选。

### 关闭条目

将文件从当前位置移动到 `backlog/archived/`：
```bash
mv backlog/in-progress/{name}.md backlog/archived/
```

## 功能树同步

### feature / improvement（必须同步）

1. 读取 `features/README.md`
2. 判断需求属于哪个模块分类
3. 在对应分类下追加条目：
   ```markdown
   - [ ] **功能名称** — 功能描述
     - 来源：[file.md](../backlog/open/file.md)
   ```
4. 用 `Edit` 工具定位插入，不要覆盖整个文件

### bug / cleanup（可选同步）

仅当 bug/cleanup 会导致功能变更（新增/删除/修改功能）时同步：
- **删除功能**：将对应条目标记为删除或移除
- **修改功能**：更新条目描述
- 功能树条目的 `来源` 字段链接到 backlog 文件

## 注意事项

- 记录模式下严禁修改业务代码
- 文件名不带编号，用简短英文描述命名
- 状态完全由文件夹决定，文件内无需状态字段
- feature/improvement 必须关联功能树，不允许"孤立需求"

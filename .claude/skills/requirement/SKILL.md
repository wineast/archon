通过采访式追问 → 代码调研 → 方案收敛，生成结构化需求报告。

## 核心理念

需求报告是**委托书**——指着一片空白说"这里要造一个东西"。与缺陷报告（起诉书）的根本区别：

- 缺陷报告描述**已存在的偏差**，需求报告描述**尚不存在的能力**
- 缺陷报告的难点是**精确描述**，需求报告的难点是**认知对齐**
- 缺陷报告有隐式锚点（修复前的正确行为），需求报告没有锚点——"做到了"的定义必须显式声明

用户说出来的往往是**解决方案**而非**问题本身**。采访的目标是穿透表面诉求，从 Why 出发重建完整的需求画面。

## 链路定位

```
需求报告 ──→ 实现报告 ──→ 验收报告
 委托书       施工方案       竣工验收

 Who    ──→  User Flow   ──→  场景走查
 Why    ──→  Design Why  ──→  动机满足度
 What   ──→  Change Set  ──→  能力核对
 Accept ──→  Test Cover  ──→  清单逐项 ✓/✗
 Constr ──→  Compliance  ──→  约束逐项 ✓/✗
```

## Phase 0: 采访——挖掘真实需求

### 目标
把用户零散的描述转化为结构化的需求初判。穿透"我要一个XX按钮"的表面，找到"谁因为什么痛点需要什么能力"。

### 操作

1. **通读用户输入**，识别：
   - 表面诉求（用户直接说要做什么）
   - 隐含动机（为什么要做）
   - 用户的方案设想（如果有）
   - 约束线索（时间、兼容性、不可改变的部分）

2. **复述确认**：输出"我理解你的需求是……"

3. **用 `AskUserQuestion` 追问**（每轮 2-3 个问题，不轰炸），沿五元素逐层挖掘：

   **Who（谁在什么处境下）**：
   - 这个功能的主要使用者是谁？（FDE / 最终用户 / 开发者 / 管理员）
   - 使用场景是什么？（日常高频 / 偶尔配置 / 一次性设置）
   - 用户当前怎么解决这个问题的？（手动操作 / 绕行方案 / 完全没法做）

   **Why（为什么需要）**：
   - 什么触发了这个需求？具体场景是什么？
   - 不做会怎样？是能忍受的不便还是阻断性问题？
   - 做了之后最大的价值是什么？

   **What（要什么能力）**：
   - 做完后用户应该能做到什么之前做不到的事？
   - 这次做哪些？哪些明确不做？
   - 粒度校准：太抽象→追问细化，太具体（锁定实现）→拉回到能力层

4. 追问直到 Who + Why + What 三元素明确后进入下一 Phase。

### 技巧
- 优先给选项点选，减少打字负担
- 能通过读代码推断的就不问用户（先调研再追问）
- Who 决定 What 的形态——同一句话不同角色含义完全不同
- Why 是根节点——丢失 What 可以从 Why 重新推导，丢失 Why 则整条链路失去北极星

## Phase 1: 代码调研

### 目标
理解项目现状，为定义 What、Acceptance、Constraint 提供基础。

### 操作

1. **调研现有实现**
   - 使用 `Task`（subagent_type=Explore）或 `Grep`/`Read` 调研相关功能区域
   - 了解：现有数据模型、相似功能的交互模式、当前 UX/DX
   - 识别：可复用的模式、潜在冲突、会受影响的现有行为

2. **关注维度**
   - **UX 现状**：当前用户操作路径、界面布局
   - **DX 现状**：对外接口、组件 API、配置项
   - **数据模型**：相关的 DB schema、数据流
   - **影响面**：如果改了这块，哪些地方会受影响？

3. **输出调研发现**
   - 向用户说明现状："当前是这样的：……"
   - 基于调研提出候选方案或补充追问

## Phase 2: 方案收敛与验收定义

### 目标
确定 What 的精确边界，定义 Acceptance 清单和 Constraint 红线。

### 操作

1. **收敛 What**
   - 基于调研提出 2-3 个候选方案（如有多种可行路径）
   - 用 `AskUserQuestion` 让用户选择或修正
   - 粒度把控：能力声明层（"用户能批量删除过期记录，操作前需确认"），不锁定 UI 细节

2. **定义 Acceptance（验收标准）**
   - 从 What 推导可判定的命题集
   - 展示给用户确认："我认为做到以下几点就算完成，你看对吗？"
   - 每条 Acceptance 必须是 ✓/✗ 可判定的——不用"应该好用"这种模糊描述

3. **明确 Constraint（约束）**
   - **业务约束**：向用户追问——"有什么是绝对不能碰的？"
   - **技术约束**：从代码调研中提取——"我发现 XX 有 N 处调用，如果改接口都要跟着改"
   - **兼容约束**：现有行为哪些必须保持不变？

4. **预期变更预览**
   - UX：before → after
   - DX：接口/API 变化（如有）
   - Database：schema 变更（如有）
   - Breaking Changes：不兼容变更穷举

## Phase 3: 输出需求报告

### 输出位置

**固定写入 `.worktree/REQ.md`**（`.worktree/` 目录始终存在于项目根目录）。

### 五不可约元素

报告围绕五个不可约元素组织——从链路终点（验收报告的 Verdict）倒推，缺少任何一个都无法闭合链路：

```
           需求报告
              │
      ┌───────┼───────┐
      │       │       │
    Who     Why     What
   (谁)    (为何)   (做什么)
      │       │       │
      └───────┼───────┘
              │
      ┌───────┴───────┐
      │               │
 Acceptance       Constraint
 (怎么算成)       (什么不行)
```

1. **Who（主体 + 场景）**——"谁在什么处境下"
   - 不确定 Who，What 是不确定的——不同角色同一句话含义完全不同
   - 传递给实现报告：据此设计用户流程
   - 传递给验收报告：用 Who 的视角走验收路径

2. **Why（动机）**——"为什么需要这个能力"
   - 五个元素中唯一不可从其他元素推导的信息——根节点
   - 丢失 What 可从 Why 重新推导；丢失 Why 则遇到边界 case 就瞎了
   - 传递给实现报告：Design Decision 锚定 Why
   - 传递给验收报告：Verdict 回答"Why 被满足了吗"

3. **What（能力声明）**——"系统要获得什么新能力"
   - 能力边界层，不锁定实现方案
   - 需求报告与实现报告之间的契约接口
   - 传递给实现报告：Change Set 必须覆盖 What 声明的每一项能力

4. **Acceptance（验收标准）**——"怎么判定做到了"
   - 可判定的命题集（只有 true/false），不是散文
   - 整条链路的终止条件——没有它，永远可以说"还不够好"
   - 传递给验收报告：逐项核对

5. **Constraint（约束）**——"什么边界不可越过"
   - 事前声明的红线，不是事后描述的影响
   - 业务约束必须由需求方显式声明（实现者无法推导）
   - 传递给实现报告：Design Decision 中说明如何满足
   - 传递给验收报告：逐项确认未被违反

### 报告模板

```markdown
# 需求报告：{一句话标题}

> 创建时间：{YYYY-MM-DD HH:mm}
> 分支：`{branch}`

## 1. Who（主体 + 场景）

### 使用者
{谁会用这个功能——角色/身份}

### 使用场景
{什么处境下需要——频率、触发时机、当前解法}

## 2. Why（动机）

### 痛点
{当前遇到什么问题 / 缺失什么能力}

### 做了的价值
{解决什么问题、带来什么好处}

### 不做的代价
{维持现状会怎样——能忍受的不便 / 持续恶化的问题 / 阻断性影响}

## 3. What（能力声明）

### 核心能力
{系统要获得什么新能力——能力边界层描述，不锁定 UI/实现细节}

- {能力 1}
- {能力 2}
- ...

### 不做（Out of Scope）
- {明确排除的内容}

## 4. Acceptance（验收标准）

{可判定的命题清单——每条只有 ✓/✗，无模糊地带}

- [ ] {Given 前置条件, When 操作, Then 预期结果}
- [ ] ...

## 5. Constraint（约束）

### 业务约束
- {不可违反的业务规则——来自需求方}

### 技术约束
- {架构限制、性能预算、兼容性要求——来自代码调研}

### 不可打破的现有行为
- {必须保持不变的现有功能/接口}

## 预期变更

### UX
#### 现状
{当前用户操作路径 / 界面}
#### 目标
{期望的用户操作路径 / 界面}

### DX
<条件——涉及接口/API 变更时展示>
#### 现状
{当前接口/调用方式}
#### 目标
{期望的接口/调用方式}

### Database
<条件——涉及 schema 变更时展示>
{新增/修改的表和列}

### Breaking Changes
{不兼容变更穷举。无则写"无"}

## 参考
- {相关代码路径、可复用模块、规范文档——从代码调研中提取}

## 过程备注

{执行过程中捕获的学习信号。无则留空}
```

### 报告自检清单

生成报告后，对照五元素逐项检查：

- [ ] **Who**：使用者和场景都明确了吗？不同角色看到这份报告会理解为同一件事吗？
- [ ] **Why**：痛点清晰吗？"做了/不做"的价值和代价都写了吗？
- [ ] **What**：能力声明在正确的粒度吗？（不是模糊轮廓，也不是锁定实现）
- [ ] **Acceptance**：每条验收标准都是 ✓/✗ 可判定的吗？覆盖了 What 声明的每项能力吗？
- [ ] **Constraint**：业务约束有向用户确认过吗？技术约束有从代码调研中提取吗？

### 流程

1. 生成报告内容，展示给用户
2. 用 `AskUserQuestion` 确认报告是否准确、是否需要补充
3. 确认后用 `Write` 写入 `.worktree/REQ.md`
4. 启动/更新报告查看器：
   ```bash
   node .claude/skills/shared/serve-req-chain.mjs
   # 用 Bash(run_in_background=true) 执行
   # 幂等：已有 viewer 进程运行时自动跳过，文件变化通过 SSE 自动刷新
   ```
5. 告知用户报告位置，并提示后续操作

## 执行规则

1. **采访优先**：先问清楚再调研代码，不要上来就读代码猜需求
2. **Why 是北极星**：所有追问最终要收敛到 Why——它决定了其他四个元素的形态
3. **善用 `AskUserQuestion` 给选项**：追问时优先提供 2-4 个选项点选，减少打字负担
4. **渐进式追问**：每轮 2-3 个问题，不轰炸
5. **先复述后追问**：追问前先确认理解正确
6. **代码先行补充**：能通过读代码推断的就不问用户
7. **收敛而非发散**：每一轮都在缩小范围
8. **尊重用户判断**：用户说"不需要考虑"就不追问
9. **粒度校准**：What 太抽象就追问细化，太具体（锁定实现）就拉回到能力层
10. **Acceptance 必须可判定**：模糊的验收标准等于没有标准
11. **过程备注**：执行过程中遇到重试、惊讶、绕路、确认、环境等偏差信号时，记录到报告的「过程备注」节。格式：`[重试/惊讶/绕路/确认/环境] 简述`

## 与其他技能的协作

- **需求链路**：`/requirement` 生成需求报告 → 实现 → 验收
- **缺陷链路**：`/diagnose` 生成缺陷报告 → `/fix` 修复 → `/verify` 验证
- **典型流程**：`/create-wt` 创建工作区 → `/requirement` 定义需求 → 实现 → `/pr-wt` 提交（自动关联需求文档）
- **PR 报告集成**：`/pr-wt` 生成报告时，如果 `.worktree/REQ.md` 存在，验收评估者会对照五元素逐项核对

通过采访式追问 → 环境准备 → Playwright 主动复现 → 代码调研，生成结构化缺陷报告。

## 核心理念

用户报 bug 时说的往往是**表面症状**而非**根本原因**。诊断的目标是：

1. **采访**：通过结构化追问明晰问题的边界和触发条件
2. **复现**：主动启动环境、准备数据、用 Playwright 复现并截图取证
3. **定位**：从症状追溯到根因，找到具体代码位置
4. **报告**：输出标准化缺陷报告，含复现证据和修复方向

与 `requirement` 的区别：`requirement` 是需求链路的委托书（"要造什么"），`diagnose` 是缺陷链路的起诉书（"哪里坏了"）。

## Phase 0: 采访——明晰问题

### 目标
把用户零散的描述转化为结构化的缺陷初判。

### 操作

1. **通读用户输入**，识别：
   - 表面症状（用户能观察到什么）
   - 用户的猜测/归因
   - 已尝试的排查

2. **复述确认**：输出"我理解的问题是……"

3. **用 `AskUserQuestion` 追问**（每轮 2-3 个问题，不轰炸）：
   - **复现路径**：从哪个页面/入口开始？具体操作步骤？
   - **触发条件**：每次都出现还是偶发？特定数据/配置才触发？
   - **环境**：dev 还是 prod？哪个浏览器？
   - **期望 vs 实际**：正确行为是什么？实际看到什么？
   - **数据依赖**：复现需要特定的数据吗？（如特定的 Agent、特定配置项）

4. 追问直到以下信息明确后进入下一 Phase：
   - 一条可执行的复现路径（步骤 1→2→3→...）
   - 预期结果
   - 实际结果
   - 复现所需的数据/前置条件

### 技巧
- 优先给选项点选，减少打字负担
- 能通过读代码推断的就不问用户
- 如果用户提供了截图，直接用 `Read` 查看

## Phase 1: 环境准备

### 目标
确保本地开发环境可用，为 Playwright 复现做准备。

### 操作

#### 1.1 检查并启动环境

**确定端口号**：如果存在 `.worktree/meta.json`，从中读取实际端口号；否则使用默认端口 3000。

**检查 Docker**：
```bash
docker info > /dev/null 2>&1
```
- 如果 Docker 未启动：`open -a Docker`，轮询 `docker info` 等待就绪（最多 60s）
- **不要问用户，自动处理**

**检查 dev 服务器是否已运行**：
```bash
curl -s -o /dev/null -w "%{http_code}" http://localhost:{端口号} 2>/dev/null || echo "not running"
```

如果 Docker 或 dev 服务未运行：
```bash
make up  # 用 run_in_background=true 后台启动，一条命令启动全部服务（DB + dev + storybook + inngest）
```
轮询 `curl localhost:{端口号}` 等待就绪，**最多 15s**。如果超时：
1. `make down` 先停掉
2. 再 `make up` 重启
3. 再等 15s
4. 仍然失败则报错给用户，**不要反复轮询卡死**

#### 1.2 准备测试数据
根据 Phase 0 采访得到的数据依赖：
- 检查数据库中是否有复现所需的数据
- 如果缺少数据，通过 API / Playwright UI 操作创建（如创建 Agent、添加配置项等）
- 记录数据准备步骤，后续写入报告

#### 1.3 安装 Playwright（如需要）
首次使用 Playwright MCP 时如果浏览器未安装，调用：
```
mcp__playwright__browser_install
```

## Phase 2: Playwright 主动复现

### 目标
按复现路径操作，截图取证，确认 bug 存在。

### 操作

1. **导航到起始页面**
   ```
   mcp__playwright__browser_navigate → 目标 URL
   ```

2. **按复现步骤逐步操作**
   - 每一步先 `browser_snapshot` 获取页面结构
   - 用 `browser_click` / `browser_type` / `browser_fill_form` 执行操作
   - 关键步骤前后用 `browser_take_screenshot` 截图（存到 `screenshots/` 目录）
   - 等待页面响应：`browser_wait_for`

3. **Bug 触发后取证**
   - 截图记录 bug 现象：`browser_take_screenshot`
   - 如果是布局问题：额外截全页面（`fullPage: true`）
   - 如果是控制台报错：`browser_console_messages`
   - 如果是网络请求问题：`browser_network_requests`
   - 如果需要检查元素状态：`browser_evaluate` 执行 JS 检查 DOM

4. **输出复现结果**
   - 确认 bug 已复现 → 继续 Phase 3
   - 未复现 → 回到 Phase 0 追问用户，确认触发条件

### 资源管理
所有诊断产物统一放在 `.worktree/` 下，截图等附件放在 `DEFECT.assets/` 子目录：
```
.worktree/
├── DEFECT.md                                    # 缺陷报告
└── DEFECT.assets/                               # 附件资源
    ├── diagnose-{简述}-step{N}.png              # 各步骤截图
    └── diagnose-{简述}-bug.png                  # Bug 现象截图
```
报告中用相对路径引用：`![desc](DEFECT.assets/xxx.png)`

## Phase 3: 代码调研与根因定位

### 目标
从复现路径追溯到具体代码位置，找到根因。

### 操作

1. **沿 UI 追踪代码路径**
   - 从页面组件开始，沿调用链追踪
   - 使用 `Task`（subagent_type=Explore）或 `Grep`/`Read`

2. **关注维度**
   - **布局问题**：flex/grid 容器、overflow、min-h-0、高度约束
   - **数据流**：数据从哪来、经过哪些变换、到哪去
   - **状态管理**：涉及哪些状态？转换是否有遗漏？
   - **边界条件**：空值、并发、竞态、类型不匹配
   - **近期改动**：`git log --oneline -20 -- <相关文件>`

3. **收敛根因**
   - 列出 2-3 个最可能的根因假设
   - 结合复现证据验证假设
   - 确定根因后定位到具体文件:行号

## Phase 4: 输出缺陷报告

### 输出位置

**固定写入 `.worktree/DEFECT.md`**（`.worktree/` 目录始终存在于项目根目录）。如果目录不存在则先创建。

### 四不可约元素

报告围绕四个不可约元素组织——从修复者的认知需求反推，缺少任何一个都无法完成修复：

```
           缺陷报告
              │
    ┌─────────┼─────────┐
    │         │         │
  Delta    Path     Location
  (what)   (how)    (where)
    │         │         │
    └─────────┼─────────┘
              │
           Impact
           (so what)
```

1. **Delta（偏差）**——"错在哪"：期望行为 + 实际行为 + 二者之差。只有实际没有期望，修复者不知道什么是"对的"；只有期望没有实际，修复者不知道什么"坏了"
2. **Path（复现路径）**——"怎么触发"：环境/上下文 + 操作步骤 + 输入数据。不可复现的缺陷在认识论上等价于不存在
3. **Location（定位）**——"在哪里"：模块/功能/页面 + 版本/分支 + 具体代码坐标。路径是用户视角的操作序列，定位是系统视角的代码空间坐标
4. **Impact（影响）**——"多严重"：严重度（功能不可用 vs 体验瑕疵）+ 影响范围。影响决定修复策略——阻断级需要 hotfix，低影响可以排期

```markdown

## 1. Delta（偏差）

## 2. Reproduction Path（复现路径）

{具体到代码逻辑的根因——为什么这段代码产生了偏差}

```{lang}

```

## 4. Impact（影响）

### 影响范围

- **验收标准**：Given {前置条件}, When {操作}, Then {预期结果}

```

### 报告自检清单

生成报告后，对照四元素逐项检查：

- [ ] **Delta**：期望和实际都写了吗？偏差描述清晰吗？
- [ ] **Path**：任何人按步骤都能复现吗？截图附了吗？
- [ ] **Location**：定位到具体文件:行号了吗？根因分析了吗？
- [ ] **Impact**：严重度和影响范围都评估了吗？

### 流程

1. 生成报告内容，展示给用户
2. 用 `AskUserQuestion` 确认报告是否准确、是否需要补充
3. 确认后用 `Write` 写入文件
4. 告知用户报告位置，并提示后续操作（如 `/create-wt` 创建工作区修复、直接修复等）

## 执行规则

1. **采访优先**：先问清楚再动手，不要上来就读代码
2. **主动复现**：必须用 Playwright 实际复现，不能只靠代码推理
3. **截图取证**：关键步骤和 bug 现象必须截图
4. **善用 `AskUserQuestion` 给选项**：减少用户打字负担
5. **渐进式追问**：每轮 2-3 个问题，不轰炸
6. **代码先行**：能通过读代码确认的就不问用户
7. **收敛而非发散**：每一轮都在缩小范围
8. **尊重用户判断**：用户说"不是这个方向"就换方向
9. **环境检查不遗漏**：Docker、服务、数据三件套确认后再复现
10. **过程备注**：执行过程中遇到重试、惊讶、绕路、确认、环境等偏差信号时，记录到报告的「过程备注」节。格式：`[重试/惊讶/绕路/确认/环境] 简述`

## 与其他技能的协作

- **典型流程**：发现 bug → `/diagnose` 生成缺陷报告 → `/create-wt` 创建工作区 → 修复 → `/pr-wt` 提交
- **与 issue 的关系**：`/issue` 轻量记录问题，`/diagnose` 深度诊断。可以先 `/issue` 记录，后续 `/diagnose` 排查
- **独立使用**：也可以单独调用来排查任何问题

通过结构化追问 + 主动代码调研，帮助用户定位 bug 根因并生成可执行的修复脚本。

## 核心理念

用户报 bug 时说的往往是**表面症状**而非**根本原因**。诊断的目标是：

1. **复现**：确认问题确实存在，明确触发条件
2. **定位**：从症状追溯到根因，找到具体代码位置
3. **方案**：给出最小化修复方案，避免引入新问题

与 `clarify-req` 的区别：`clarify-req` 问"要做什么"，`diagnose` 问"哪里坏了、为什么坏、怎么修"。

## 追问方法论

### 第 0 轮：整理症状

用户描述 bug 往往零散、混合了观察和猜测。先整理成结构化描述。

操作：
- 通读用户输入，识别：1）表面症状 2）用户的猜测/归因 3）已尝试的排查
- 输出"我理解的问题是……"的复述
- 分离事实（可观察的行为）和推测（用户的猜测），标记待验证项

**这一步只整理，不下结论。**

### 第 1 轮：复现确认

**在深入调研之前，先确认问题可复现、触发条件明确。**

追问方向：
- **复现路径**：具体操作步骤是什么？从哪个页面/入口开始？
- **触发条件**：每次都出现还是偶发？特定数据/配置才触发？
- **环境**：dev 还是 prod？哪个浏览器？有无相关配置？
- **期望 vs 实际**：正确行为应该是什么？实际看到/得到的是什么？

技巧：
- 用 `AskUserQuestion` 提供常见场景选项，减少描述成本
- 如果用户能给截图/报错信息，优先让用户提供
- 如果有错误日志，用 `Read` 查看 `.logs/dev.log`

### 第 2 轮：代码调研

**基于复现路径，主动调研相关代码区域。**

目标：理解出问题的代码逻辑，找到可疑位置。

操作：
- 使用 `Task`（subagent_type=Explore）或 `Grep`/`Read` 追踪代码路径
- 从用户操作的入口（页面组件/API 路由）开始，沿调用链追踪
- 关注：数据流、状态变更、边界条件、近期改动

调研时特别关注：
- **数据流**：数据从哪来、经过哪些变换、到哪去？哪一步出了问题？
- **状态管理**：涉及哪些状态？状态转换是否有遗漏？
- **边界条件**：空值、并发、竞态、类型不匹配？
- **近期改动**：`git log --oneline -20 -- <相关文件>` 看最近有没有相关变更

### 第 3 轮：根因定位

目标：从多个可疑点收敛到具体根因。

操作：
- 基于调研结果，列出 2-3 个最可能的根因假设
- 用 `AskUserQuestion` 让用户确认/排除（结合用户能观察到的现象）
- 如果需要进一步验证，补充代码调研

追问方向：
- **假设验证**："根据代码，我怀疑是 X 导致的。你观察到 Y 现象吗？"
- **排除法**："如果是 A 的问题，应该同时出现 B。你有看到 B 吗？"
- **范围确认**：确认问题是单点的还是系统性的

### 第 4 轮：修复方案

目标：确定最小化、安全的修复方案。

操作：
- 基于根因提出修复方案（可能多个）
- 用 `AskUserQuestion` 让用户选择方案
- 明确修复的影响范围和风险

方案评估维度：
- **最小化**：改动范围尽可能小，只修问题本身
- **安全性**：不引入新问题，不破坏现有功能
- **可验证**：修复后怎么确认问题已解决

## 执行规则

1. **善用 `AskUserQuestion` 给选项**：追问时优先提供 2-4 个选项点选，减少打字负担
2. **渐进式追问**：每轮 2-3 个问题，不轰炸
3. **先复述后追问**：追问前先确认理解正确
4. **代码先行**：能通过读代码确认的就不问用户，减少用户负担
5. **适时调研代码**：需要了解实现时，随时用 `Task`（Explore）或 `Grep`/`Read`
6. **收敛而非发散**：每一轮都在缩小范围，快速逼近根因
7. **尊重用户判断**：用户说"不是这个方向"就换方向

## 输出：生成 fix.sh

诊断完成后生成 `fix.sh` 修复脚本。

### prompt 格式

```markdown
# 修复：{一句话描述问题}

## 问题描述
{问题的表面症状——用户能观察到什么}

## 复现路径
1. {具体操作步骤}
2. ...
期望结果：{应该发生什么}
实际结果：{实际发生了什么}

## 根因分析
{根本原因是什么，具体到代码位置}

### 涉及文件
- `path/to/file.ts:行号` — {说明}

## 修复方案
{具体修复思路——改什么、怎么改、为什么这样改}

## 验收标准
- Given {前置条件}, When {操作}, Then {预期结果}
- ...

## 风险评估
- 影响范围：{这次修改会影响哪些功能}
- Breaking Changes：{有无不兼容变更。无则写"无"}

## 参考
- {相关代码路径、文档——从调研中提取}
```

### prompt 生成原则

- **症状要具体**：写清楚用户看到了什么，不要笼统
- **根因要精确**：定位到具体文件和代码逻辑，不能模糊
- **方案要最小化**：只修问题本身，不顺手重构
- **验收要可操作**：修完后按什么路径验证
- **风险要诚实**：影响范围如实列出
- **信任执行 Agent**：它有完整的代码访问权限和 CLAUDE.md 上下文，能自行调研和实现

### 流程

1. 展示生成的 prompt 内容，用 `AskUserQuestion` 让用户确认或修改
2. 确认后在当前目录创建 `fix.sh`（`<<'PROMPT'` 单引号定界符禁止 shell 展开）+ `chmod +x`
3. 提示用户：运行 `./fix.sh` 启动自主修复

```bash
#!/usr/bin/env bash
# Auto-generated by diagnose skill
claude --dangerously-skip-permissions "$(cat <<'PROMPT'
<prompt 内容>
PROMPT
)"
```

## 与其他技能的协作

- **典型流程**：发现 bug → `/diagnose` 诊断定位 → 生成 `fix.sh` → 运行 `./fix.sh` 自主修复
- **与 issue 的关系**：`/issue` 记录问题，`/diagnose` 深入诊断。可以先 `/issue` 记录，后续 `/diagnose` 排查
- **与 create-wt 的配合**：复杂 bug 可先 `/create-wt` 创建工作区 → 进入工作区 → `/diagnose` 诊断 → `./fix.sh` 修复
- **独立使用**：也可以单独调用来排查任何问题

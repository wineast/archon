通过结构化追问帮助用户将模糊想法转化为清晰、可执行的需求文档。

## 核心理念

用户说出来的往往是**解决方案**而非**问题本身**。需求澄清的目标是穿透表面诉求，找到背后的真实问题和验收标准。

> "用户不是需要一个 1/4 英寸的钻头，而是需要一个 1/4 英寸的孔。"

## 追问方法论

### 第 0 轮：整理用户输入（Organize First）

**用户的输入可能是杂乱无序的**——口语化表达、思路跳跃、细节和目标混在一起。在做任何事之前，先把用户的原始输入整理成结构化的理解。

目标：从用户的混乱表达中提取**核心诉求**和**关键细节**，让后续调研和追问有明确方向。

操作：
- 通读用户的完整输入，识别出：1）用户想解决什么问题 2）用户设想的方案 3）提到的具体细节和约束
- 用简洁的语言重新组织，输出"我理解你的意思是……"的复述
- 标记不确定或模糊的部分，作为后续追问的方向

**注意：这一步只整理，不评判、不追问。** 确保自己真正听懂了用户在说什么再往下走。

### 第 1 轮：现状调研（Context Research）

**在向用户追问之前，先主动调研相关代码的现状**。用户提出需求时给的上下文往往很少，必须主动补全项目现状才能问出精准问题。盲目追问只能得到通用答案，基于现状的追问才能挖出真正有价值的信息。

目标：理解与需求相关的**项目现状**——现有功能做到了什么程度、数据模型长什么样、有没有类似的模式可以复用、有没有潜在冲突。

操作：
- 使用 `Task`（subagent_type=Explore）或 `Grep`/`Read` 快速调研用户提到的相关功能区域
- 了解：现有数据模型、已有的相似功能、当前的交互模式、技术栈约定
- 识别：用户可能没意识到的约束、可以复用的现有模式、潜在的冲突点

**注意：调研的目的是理解现状，不是规划实现方案。** 理解现状是为了在后续追问中给出有意义的选项。例如：
- 发现已有类似功能 → "现有的 XX 功能已经做了类似的事，你想在此基础上扩展，还是做一个独立的？"
- 发现数据模型限制 → "当前 XX 表没有 YY 字段，你是需要新增字段还是用另一种方式？"
- 发现现有约定 → "项目里 XX 类型的功能统一用了 AA 模式，这次要沿用还是有不同需求？"
- 发现潜在冲突 → "你要做的 XX 和现有的 YY 会冲突，你倾向于替换 YY 还是共存？"

### 第 2 轮：理解问题域（Why & Who）

目标：弄清楚用户在解决什么问题、为谁解决。

追问方向：
- **动机**：为什么要做这个？是什么触发了这个需求？
- **现状**：目前是怎么处理的？有什么痛点？
- **用户**：谁会使用这个功能？他们的典型场景是什么？
- **价值**：做完之后，用户的体验会有什么变化？

技巧：
- 如果用户直接给了解决方案（"加个按钮"），追问"这个按钮是为了解决什么问题？"
- 连续追问"为什么"（5 Whys），直到触及核心痛点
- 注意区分"nice to have"和"must have"
- 结合代码调研结果，给出选项而非开放提问（"你是想要 A 还是 B？"比"你想怎么做？"更高效）

### 第 3 轮：明确边界（What & What Not）

目标：界定这次要做什么、不做什么。

追问方向：
- **范围**：这次只做哪些场景？哪些明确不做？
- **输入输出**：功能接收什么、产出什么？
- **边界条件**：极端情况怎么处理？（空数据、超长文本、并发操作等）
- **交互**：用户怎么触发？成功/失败时看到什么？

技巧：
- 用"假设……会怎样？"探索边界
- 用"如果我们不做 X，影响大吗？"收窄范围
- 对每个功能点确认：是 P0（必须有）还是 P1（最好有）
- 结合代码调研主动提示："当前 XX 已经支持了 AA，这次需要兼容吗？"

### 第 4 轮：验收标准（How to Verify）

目标：定义怎么算"做完了"。

追问方向：
- **完成标志**：用户做完操作后应该看到什么结果？
- **质量要求**：性能、兼容性、可访问性有要求吗？
- **测试场景**：给我一个具体的端到端场景，我来验证？

技巧：
- 用 Given-When-Then 格式描述验收标准
- 每个验收标准都应该是可演示的
- 基于代码调研，主动补充用户可能遗漏的验收点

### 第 5 轮：约束（Constraints）

目标：识别必须遵守的技术和业务约束。

追问方向：
- **技术约束**：必须用什么技术栈/API？有什么现有约定要遵守？
- **兼容性**：需要和哪些现有功能/数据兼容？
- **时间约束**：有 deadline 或优先级排序吗？

技巧：
- 从代码调研中提取已有约束（如项目用了 react-hook-form、shadcn 等），主动向用户确认是否沿用
- 不要问已经在 CLAUDE.md 中有明确规定的约束，直接作为已知条件纳入

## 执行规则

1. **善用 `AskUserQuestion` 给选项**：追问时优先用 `AskUserQuestion` 提供 2-4 个选项让用户点选，减少用户打字负担。只有在确实无法预设选项的开放性问题时才用纯文本追问。结合代码调研结果来构造有意义的选项（如"沿用现有的 XX 模式"vs"新做一套"）
2. **渐进式追问**：每轮问 2-3 个问题，不要一次抛出所有问题轰炸用户
3. **先倾听后追问**：在追问之前先复述用户的意思确认理解正确
4. **跳过已明确的**：如果用户的描述已经足够清晰，直接跳过对应轮次
5. **适时调研代码**：当需要了解现有实现来提出更精准的问题时，使用 `Task`（Explore）或 `Grep`/`Read` 调研代码
6. **收敛而非发散**：追问的目的是收窄范围让需求可执行，不是扩大范围
7. **尊重用户判断**：用户说"不需要考虑"就不追问，不要强行追加复杂度

## 输出格式

当需求足够清晰后，输出结构化需求文档：

```markdown
## 需求：{一句话标题}

### 背景
{为什么要做、解决什么问题}

### 目标用户 & 场景
{谁在什么场景下使用}

### 功能描述
{要做什么，用户视角的行为描述}

### 验收标准
- [ ] {Given-When-Then 格式的验收条件}
- [ ] ...

### 约束
- {技术约束、业务约束}

### 不做（Out of Scope）
- {明确排除的内容}
```

## 生成启动脚本（req.sh）

需求澄清完成后，自动生成 `req.sh` 启动脚本，让用户可以启动一个新的 Claude Code 实例自主执行实现。

### 触发条件

输出需求文档后，询问用户是否生成 `req.sh`。

### 生成 prompt 的原则

基于澄清结果生成 prompt，必须是**需求导向**的：
- **写需求，不写实现**：描述期望的用户体验和行为，不要写具体的代码方案、文件路径、函数名
- **写验收标准**：明确完成后应该能看到什么效果、通过什么检验
- **写约束，不写步骤**：如果有技术约束（如"必须用 react-hook-form"），可以列出，但不要写实现步骤
- **信任执行 Agent**：它有完整的代码访问权限和 CLAUDE.md 上下文，能自行调研和规划实现方案

### 流程

1. 向用户展示生成的 prompt，让用户选择：使用此 prompt / 自定义修改
2. 在当前目录创建 `req.sh`，用 heredoc 传递 prompt（`<<'PROMPT'` 单引号定界符禁止 shell 展开，避免 `*#$[]` 等字符被截断/转义）：
   ```bash
   #!/usr/bin/env bash
   # Auto-generated by clarify skill
   claude --dangerously-skip-permissions "$(cat <<'PROMPT'
   <用户确认的 prompt>
   PROMPT
   )"
   ```
3. `chmod +x req.sh` 使其可执行
4. 提示用户：运行 `./req.sh` 启动自主执行

## 与其他技能的协作

- **典型流程**：`/create-wt` 创建工作区 → 用户进入工作区启动 Claude Code → `/clarify-req` 澄清需求 → 生成 `req.sh` → 用户运行 `./req.sh` 启动自主实现
- **独立使用**：也可以单独调用来梳理任何需求，不一定要生成启动脚本

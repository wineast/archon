通过结构化追问帮助用户将模糊想法转化为清晰、可执行的需求文档。

## 核心理念

用户说出来的往往是**解决方案**而非**问题本身**。需求澄清的目标是穿透表面诉求，找到背后的真实问题，然后从三个维度确定实现方向：

- **UX**：最终用户的体验如何变化？
- **DX**：开发者的使用方式如何变化？
- **Breaking Changes**：现有行为哪些会被打破，影响范围多大？

## 追问方法论

### 第 0 轮：整理用户输入

用户的输入往往杂乱无序。在做任何事之前，先整理成结构化理解。

操作：
- 通读完整输入，识别：1）用户想解决什么问题 2）设想的方案 3）具体细节和约束
- 输出"我理解你的意思是……"的复述
- 标记模糊部分，作为后续追问方向

**这一步只整理，不评判、不追问。**

### 第 1 轮：现状调研

**在追问之前，先主动调研代码现状。** 盲目追问只能得到通用答案，基于现状的追问才能挖出有价值的信息。

目标：理解项目现状——现有功能程度、数据模型、交互模式，以及**当前的 UX 和 DX 是什么样的**。

操作：
- 使用 `Task`（subagent_type=Explore）或 `Grep`/`Read` 调研相关功能区域
- 了解：现有数据模型、相似功能、当前交互模式、对外 API/接口
- 识别：可复用的模式、潜在冲突、**会受影响的现有行为和接口**

调研时特别关注：
- **UX 现状**：当前用户操作路径是什么？界面长什么样？
- **DX 现状**：有哪些对外接口、组件 API、配置项？其他模块怎么调用的？
- **Breaking 表面积**：如果改了这块，哪些地方会受影响？有多少调用方？

### 第 2 轮：目标与范围

目标：弄清要解决什么问题、做到什么程度。

追问方向：
- **动机**：为什么要做？什么触发了这个需求？
- **目标状态**：做完后，用户/开发者应该能做到什么之前做不到的事？
- **范围**：这次做哪些？哪些明确不做？
- **优先级**：哪些是 P0（必须有），哪些是 P1（最好有）？

技巧：
- 结合代码调研给选项而非开放提问
- 用"如果不做 X，影响大吗？"收窄范围

### 第 3 轮：UX 设计

目标：明确最终用户体验的变化——**从用户视角看，前后有什么不同**。

追问方向：
- **交互变化**：用户操作路径怎么变？新增/移除/修改了哪些界面元素？
- **信息架构**：信息的组织方式变了吗？导航结构变了吗？
- **状态与反馈**：加载、成功、失败、空状态分别展示什么？
- **边界情况**：极端输入（空数据、超长文本、大量数据）时用户看到什么？

技巧：
- 基于调研描述"现在用户是这样操作的：……"，让用户在此基础上说明期望变化
- 用 `AskUserQuestion` 的 `markdown` 预览展示 UI 布局选项（ASCII mockup）
- 如果功能无 UI 变化（纯后端），跳过此轮

### 第 4 轮：DX 设计

目标：明确开发者体验的变化——**对外接口、组件 API、配置方式怎么变**。

追问方向：
- **接口变化**：API 参数、返回值、组件 props 怎么变？
- **使用方式**：调用方的代码需要怎么改？
- **配置变化**：配置项、环境变量、schema 有变化吗？
- **心智模型**：开发者需要理解哪些新概念？

技巧：
- 基于调研列出现有接口："当前 XX 组件接受这些 props……"，让用户说明期望变化
- 如果功能无 DX 变化（纯 UI 调整），跳过此轮

### 第 5 轮：Breaking Changes

目标：**显式枚举**所有不兼容变更，确定影响范围和应对策略。

这一轮基于前面的 UX/DX 讨论结果，结合代码调研中发现的调用方，逐一确认：

追问方向：
- **变更清单**：哪些现有行为会改变？列出每一项
- **影响范围**：每个变更影响多少调用方/页面/用户？是局部还是全局？
- **兼容策略**：每个变更是直接破坏（hard break）还是渐进迁移（deprecate → migrate → remove）？
- **数据兼容**：现有数据需要迁移吗？旧数据还能正常工作吗？

技巧：
- 从代码调研结果中主动提取："我发现 XX 有 N 处调用，如果改了接口，这些都要跟着改"
- 用 `AskUserQuestion` 对每个 breaking change 让用户选择处理策略
- 如果没有 breaking change，明确标注"无"并跳过

### 第 6 轮：验收标准

目标：定义怎么算"做完了"。验收标准必须覆盖 UX、DX、Breaking Changes 三个维度。

操作：
- **UX 验收**：用户按什么路径操作，应看到什么结果？
- **DX 验收**：开发者用新接口/API，行为符合预期？
- **兼容验收**：如有 breaking change，迁移后旧功能正常？
- 用 Given-When-Then 格式，每条可演示

## 执行规则

1. **善用 `AskUserQuestion` 给选项**：追问时优先提供 2-4 个选项点选，减少打字负担。结合代码调研构造有意义的选项
2. **渐进式追问**：每轮 2-3 个问题，不轰炸
3. **先复述后追问**：追问前先确认理解正确
4. **跳过不相关轮次**：纯后端改动跳过 UX 轮，纯 UI 调整跳过 DX 轮，无破坏性变更跳过 Breaking Changes 轮
5. **适时调研代码**：需要了解现有实现时，随时用 `Task`（Explore）或 `Grep`/`Read`
6. **收敛而非发散**：追问的目的是收窄范围，不是扩大
7. **尊重用户判断**：用户说"不需要考虑"就不追问

## 输出：生成 req.sh

澄清完成后生成 `req.sh` 启动脚本。

### prompt 格式

```markdown
# {一句话标题}

## 实现目标
{一句话描述做完后应该达到的状态——从用户/开发者视角}

## 背景
{为什么要做、解决什么问题}

## UX 变更
### 现状
{当前的用户体验/操作路径}
### 目标
{期望的用户体验/操作路径}

## DX 变更
### 现状
{当前的接口/API/调用方式}
### 目标
{期望的接口/API/调用方式}

## Breaking Changes
{列出每项不兼容变更、影响范围、处理策略。无则写"无"}

## 验收标准
- Given {前置条件}, When {操作}, Then {预期结果}
- ...

## 参考
- {相关规范文档路径、可复用模块——从代码调研中提取}

## 不做（Out of Scope）
- {明确排除的内容}
```

### prompt 生成原则

- **写目标，不写实现**：描述期望达到的状态（UX/DX 的 before→after），不写代码方案
- **变更要具体**：UX/DX 变更的现状和目标都要具体描述，不能笼统
- **Breaking Changes 要穷举**：每一项都列出，包含影响范围和处理策略
- **验收标准覆盖三维度**：UX、DX、兼容性都要有对应验收条件
- **参考可以具体**：列出规范文档路径、可复用模块，帮助执行 Agent 快速定位
- **无关章节可省略**：如果纯 UI 改动无 DX 变更，DX 章节写"无变更"；无 breaking change 则写"无"
- **信任执行 Agent**：它有完整的代码访问权限和 CLAUDE.md 上下文，能自行调研和规划

### 流程

1. 展示生成的 prompt 内容，用 `AskUserQuestion` 让用户确认或修改
2. 确认后在当前目录创建 `req.sh`（`<<'PROMPT'` 单引号定界符禁止 shell 展开）+ `chmod +x`
3. 提示用户：运行 `./req.sh` 启动自主执行

```bash
#!/usr/bin/env bash
# Auto-generated by clarify skill
claude --dangerously-skip-permissions "$(cat <<'PROMPT'
<prompt 内容>
PROMPT
)"
```

## 与其他技能的协作

- **典型流程**：`/create-wt` 创建工作区 → 进入工作区 → `/clarify-req` 澄清需求 → 生成 `req.sh` → 运行 `./req.sh` 自主实现
- **独立使用**：也可以单独调用来梳理任何需求

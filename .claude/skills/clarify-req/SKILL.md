通过结构化追问帮助用户将模糊想法转化为清晰、可执行的需求文档。

## 核心理念

用户说出来的往往是**解决方案**而非**问题本身**。需求澄清的目标是穿透表面诉求，找到背后的真实问题，然后从三个维度确定实现方向：

- **UX**：最终用户的体验如何变化？
- **DX**：开发者的使用方式如何变化？
- **Breaking Changes**：现有行为哪些会被打破，影响范围多大？

## 追问方法论

### 第 0 轮：整理用户输入

用户的输入往往杂乱无序。在做任何事之前，先整理成结构化理解。

操作：
- 通读完整输入，识别：1）用户想解决什么问题 2）设想的方案 3）具体细节和约束
- 输出"我理解你的意思是……"的复述
- 标记模糊部分，作为后续追问方向

**这一步只整理，不评判、不追问。**

### 第 1 轮：现状调研

**在追问之前，先主动调研代码现状。** 盲目追问只能得到通用答案，基于现状的追问才能挖出有价值的信息。

目标：理解项目现状——现有功能程度、数据模型、交互模式，以及**当前的 UX 和 DX 是什么样的**。

操作：
- 使用 `Task`（subagent_type=Explore）或 `Grep`/`Read` 调研相关功能区域
- 了解：现有数据模型、相似功能、当前交互模式、对外 API/接口
- 识别：可复用的模式、潜在冲突、**会受影响的现有行为和接口**

调研时特别关注：
- **UX 现状**：当前用户操作路径是什么？界面长什么样？
- **DX 现状**：有哪些对外接口、组件 API、配置项？其他模块怎么调用的？
- **Breaking 表面积**：如果改了这块，哪些地方会受影响？有多少调用方？

### 第 2 轮：动机与价值

目标：弄清**为什么做**——做了有什么好处，不做有什么坏处。

追问方向：
- **动机**：为什么要做？什么触发了这个需求？
- **目标状态**：做完后，用户/开发者应该能做到什么之前做不到的事？
- **做了的好处**：从用户/开发者/业务三个视角分别有什么价值？
- **不做的坏处**：维持现状会导致什么后果？是能忍受的不便还是持续恶化的问题？
- **范围**：这次做哪些？哪些明确不做？
- **优先级**：哪些是 P0（必须有），哪些是 P1（最好有）？

技巧：
- 结合代码调研给选项而非开放提问
- 用"如果不做 X，影响大吗？"帮用户想清楚价值和代价

### 第 3 轮：方案选择

目标：确定实现方案，说明**为什么选这个方案、考虑过哪些替代方案**。

追问方向：
- **候选方案**：基于代码调研提出 2-3 个可行方案，各有什么优劣？
- **选择理由**：为什么选定方案最优？核心优势是什么（简单/成本低/可扩展/与现有架构一致等）？
- **放弃原因**：每个放弃的方案为什么不选？是技术限制、过度设计、还是成本不划算？
- **风险**：选定方案有什么潜在风险或局限？

技巧：
- 基于调研主动提出候选方案，而非让用户从零思考
- 用 `AskUserQuestion` 对比方案让用户选择
- 如果方案显而易见（如只有一种合理做法），写"无明显备选"并说明原因

### 第 4 轮：预期变更

目标：明确 UX、DX、Breaking Changes 的**前后变化**。三者放在一起讨论因为它们互相影响。

追问方向：
- **UX**：用户操作路径怎么变？新增/移除/修改了哪些界面元素？状态与反馈如何处理？
- **DX**：API 参数、返回值、组件 props、配置项、schema 怎么变？调用方需要改什么？
- **Breaking Changes**：哪些现有行为会被打破？影响范围多大？兼容策略是什么？
- **边界情况**：极端输入、空数据、大量数据时如何表现？

技巧：
- 基于调研描述"现在用户/开发者是这样的：……"，让用户在此基础上说明期望变化
- 用 `AskUserQuestion` 的 `markdown` 预览展示 UI 布局选项（ASCII mockup）
- 无 UX 变化（纯后端）或无 DX 变化（纯 UI）时跳过对应子项
- Breaking Changes 从代码调研中主动提取："我发现 XX 有 N 处调用，如果改了接口都要跟着改"

### 第 5 轮：验收标准

目标：定义怎么算"做完了"。验收标准必须覆盖 UX、DX、Breaking Changes 三个维度。

操作：
- **UX 验收**：用户按什么路径操作，应看到什么结果？
- **DX 验收**：开发者用新接口/API，行为符合预期？
- **兼容验收**：如有 breaking change，迁移后旧功能正常？
- 用 Given-When-Then 格式，每条可演示

## 执行规则

1. **善用 `AskUserQuestion` 给选项**：追问时优先提供 2-4 个选项点选，减少打字负担。结合代码调研构造有意义的选项
2. **渐进式追问**：每轮 2-3 个问题，不轰炸
3. **先复述后追问**：追问前先确认理解正确
4. **跳过不相关子项**：预期变更中，纯后端改动跳过 UX 子项，纯 UI 调整跳过 DX 子项，无破坏性变更时 Breaking Changes 写"无"
5. **适时调研代码**：需要了解现有实现时，随时用 `Task`（Explore）或 `Grep`/`Read`
6. **收敛而非发散**：追问的目的是收窄范围，不是扩大
7. **尊重用户判断**：用户说"不需要考虑"就不追问

## 输出：生成 `.worktree/REQ.md`

澄清完成后生成需求文档，存放在 `.worktree/REQ.md`（已 gitignore）。

### 文档格式

```markdown
# {一句话标题}

## 实现目标
{一句话描述做完后应该达到的状态——从用户/开发者视角}

## 为什么做
### 动机
{什么触发了这个需求？当前痛点是什么？}
### 做了有什么好处
{解决什么问题、带来什么价值——从用户/开发者/业务三个视角}
### 不做有什么坏处
{维持现状会导致什么后果？是能忍受的不便还是持续恶化的问题？}

## 方案选择
### 选定方案
{一段话描述选定的方案}
### 为什么选这个
{选定方案的核心优势——简单/成本低/可扩展/与现有架构一致等}
### 考虑过但放弃的方案
- **{方案 B}**：{一句话描述}——放弃原因：{为什么不选}
- **{方案 C}**：{一句话描述}——放弃原因：{为什么不选}
{如果没有备选方案，写"无明显备选，此方案是自然选择"并说明原因}

## 预期变更

### UX
#### 现状
{当前的用户体验/操作路径}
#### 目标
{期望的用户体验/操作路径}

### DX
#### 现状
{当前的接口/API/调用方式}
#### 目标
{期望的接口/API/调用方式}

### Breaking Changes
{列出每项不兼容变更、影响范围、处理策略。无则写"无"}

## 验收标准
- Given {前置条件}, When {操作}, Then {预期结果}
- ...

## 参考
- {相关规范文档路径、可复用模块——从代码调研中提取}

## 不做（Out of Scope）
- {明确排除的内容}
```

### 写作原则

- **动机要讲清代价**："为什么做"必须包含做了的好处和不做的坏处，让 reviewer 理解紧迫性
- **方案选择要有对比**：至少说明考虑过什么替代方案、为什么放弃，没有备选时说明原因
- **写目标，不写实现**：描述期望达到的状态（UX/DX 的 before→after），不写代码方案
- **预期变更要具体**：UX/DX 变更的现状和目标都要具体描述，Breaking Changes 要穷举
- **验收标准覆盖三维度**：UX、DX、兼容性都要有对应验收条件
- **参考可以具体**：列出规范文档路径、可复用模块，帮助执行 Agent 快速定位
- **无关子项可省略**：预期变更中，纯 UI 改动无 DX 变更时该子项写"无变更"；无 breaking change 写"无"
- **信任执行 Agent**：它有完整的代码访问权限和 CLAUDE.md 上下文，能自行调研和规划

### 流程

1. 展示生成的文档内容，用 `AskUserQuestion` 让用户确认或修改
2. 确认后写入 `.worktree/REQ.md`
3. 提示用户：需求文档已保存，可直接开始实现；`/pr-wt` 生成报告时会自动关联需求

## 与其他技能的协作

- **典型流程**：`/create-wt` 创建工作区 → 进入工作区 → `/clarify-req` 澄清需求 → 输出 `.worktree/REQ.md` → 实现 → `/pr-wt` 生成报告（自动关联需求文档）
- **PR 报告集成**：`/pr-wt` 生成报告时，如果 `.worktree/REQ.md` 存在：
  - 并行创建至少 2 个独立 subagent 作为验收评估者，各自给出整体评价（亮点/不足）+ 二元判定（✅ 满足 / ❌ 不满足）
  - Verdict（合并判定）综合评估者共识 + 质量检查给出 ✅/⚠️/❌ 判定
  - Acceptance Reviews section 展示每个评估者的独立回复（整体评价 → 亮点 → 不足 → 判定）
  - Changes 每个变更项说明它满足了哪个需求点
- **serve-report 页面**：报告查看器将 REQ.md（原始需求）与 Acceptance Reviews（评估者回复）左右并排展示，reviewer 可直接对比
- **独立使用**：也可以单独调用来梳理任何需求

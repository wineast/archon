# /reflect — 元认知经验提取

**一句话**：从工作过程中提取可复用经验，转化为项目知识库的增量补丁。

## 核心理念

### 定位

其他技能修复系统，/reflect 修复认知。

```
缺陷链路：  /diagnose → /fix → /verify → /test-guard   （修复代码）
需求链路：  /requirement → /implement → /accept → /cap-guard （构建功能）
元认知层：  /reflect                                      （修复认知）
```

/reflect 不产生代码变更，它的产出是**知识补丁提案**——对 CLAUDE.md、各 SKILL.md、guide/ 文档的修改建议。

### 认识论基础

经验有三层输入，可信度递增：

| 层 | 来源 | 说明 |
|----|------|------|
| L1 | 过程备注 | 各技能报告末尾的「过程备注」节，执行过程中的偏差记录 |
| L2 | JOURNAL.md | 手动维护的工作日志，跨会话的观察积累 |
| L3 | 会话上下文 | 当前对话中的重试、方向修正、用户反馈 |

### 五元素

经验提取的结构化格式，与缺陷报告四元素类比：

| 缺陷四元素 | 经验五元素 | 类比关系 |
|-----------|-----------|---------|
| Delta（偏差） | Scene（场景） | 什么情况下发生 |
| Path（路径） | Pitfall（陷阱） | 具体踩了什么坑 |
| Location（定位） | Reality（现实） | 实际情况是什么 |
| Impact（影响） | Rule（规则） | 应该怎么做 |
| — | Mechanism（机理） | 为什么这个规则有效 |

## Phase 0: 扫描——识别学习信号

### 输入源

按优先级扫描三层输入：

1. **过程备注**（L1）：`Glob(".worktree/*.md")` → 读取所有报告的「过程备注」节
2. **JOURNAL.md**（L2）：`Read(".worktree/JOURNAL.md")`，如果存在
3. **会话上下文**（L3）：回顾当前对话中的偏差事件

### 信号类型

识别 5 种学习信号：

| 信号 | 含义 | 示例 |
|------|------|------|
| `[重试]` | 做了但失败，换了方式才成功 | 用 `.fill()` 对 Monaco 无效，改用 `evaluate()` |
| `[惊讶]` | 结果与预期不符 | 以为 ScrollArea 会自动限制宽度，实际会无限撑开 |
| `[绕路]` | 走了弯路后找到正确路径 | 先手动拼 URL 导航，后来发现应该走 UI 路径 |
| `[确认]` | 验证了一个有用的模式 | 证实了 `useWatch` 局部订阅确实避免了全量重渲染 |
| `[环境]` | 环境/工具链相关的发现 | dev 模式 CSS chunk 分裂导致响应式变体失效 |

### 输出

生成信号清单，每条包含：信号类型 + 简述 + 来源层级

## Phase 1: 结构化——五元素格式

将每个信号转化为五元素结构：

### 元素定义

- **Scene**（场景）：在什么条件下会遇到这个问题。具体到技术栈、操作步骤、前置条件
- **Pitfall**（陷阱）：容易犯的错误或直觉偏差。如果信号是 `[确认]` 类型，可能没有 Pitfall
- **Reality**（现实）：实际的行为/机制是什么。用事实陈述，不带评判
- **Rule**（规则）：基于现实推导出的操作指南。必须是可执行的、具体的
- **Mechanism**（机理）：为什么 Rule 有效。解释底层原因，让读者能举一反三

### 质量检查

每条经验必须通过：

- [ ] Scene 足够具体，读者能判断自己是否在同一场景？
- [ ] Pitfall 描述了真实的认知偏差，而非"不知道X"这种空洞陈述？
- [ ] Reality 可验证，不是猜测？
- [ ] Rule 可执行，不是"注意X"这种模糊建议？
- [ ] Mechanism 解释了因果关系，不是循环论证？

## Phase 2: 路由——分配目标文件

### 路由规则

根据 Scene 的领域，将经验分配到对应的目标文件：

| Scene 领域 | 目标文件 | 说明 |
|-----------|---------|------|
| 通用开发约定 | `.claude/CLAUDE.md` | 跨技能的约束和模式 |
| 特定技能执行 | `.claude/skills/{skill}/SKILL.md` | 该技能的执行规则 |
| UI/组件模式 | `web/guide/*.md` | 对应的使用指南 |
| 数据库/Schema | `web/guide/production-database.md` 等 | 数据库相关指南 |
| 测试约定 | `.claude/CLAUDE.md`（E2E 测试节） | 测试相关约束 |
| 模板引擎 | `web/guide/template-engine.md` | LiquidJS 相关 |

### 确认路由

用 `AskUserQuestion` 向用户展示路由方案，确认每条经验的目标文件是否正确。

## Phase 3: 转译——生成补丁提案

### 转译规则

**有 Pitfall 的经验**（来自 `[重试]`/`[惊讶]`/`[绕路]`）：

```
### {Scene 关键词}
- {Pitfall 描述}——{Reality 描述}
- **修复方式**：{Rule}
```

**无 Pitfall 的经验**（来自 `[确认]`/`[环境]`）：

```
### {Scene 关键词}
- {Reality 描述}
- {Rule}
```

### 去重流程

对每条经验的目标文件：

1. `Read` 目标文件
2. `Grep` 搜索 Rule 中的关键词
3. 判断：
   - **已存在且一致** → 跳过，标记 `[skip]`
   - **已存在但不完整** → 增强，标记 `[enhance]`，生成增量 diff
   - **不存在** → 新增，标记 `[new]`，生成插入位置 + 内容

### 输出

生成 `REFLECT_PATCHES.md`，包含所有补丁提案。

## 自检清单

生成报告前，逐项检查：

- [ ] **信号完整**：三层输入都扫描了吗？没有遗漏的偏差事件？
- [ ] **五元素完整**：每张经验卡片的五个元素都填了吗？
- [ ] **Scene 具体**：读者能判断自己是否在同一场景？
- [ ] **Rule 可执行**：不是"注意X"式的模糊建议？
- [ ] **去重完成**：每条补丁都检查了目标文件现有内容？
- [ ] **路由合理**：每条经验都分配到了最合适的文件？
- [ ] **用户确认**：路由方案经过用户确认？

## 执行规则

1. **只输出提案，不修改现有文件**：/reflect 的产出是 REFLECT.md 和 REFLECT_PATCHES.md，补丁由用户决定是否应用
2. **三层扫描不跳过**：过程备注、JOURNAL.md、会话上下文都要检查，即使某层为空也要显式声明
3. **信号必须有证据**：每条信号必须能追溯到具体的重试记录、错误日志或对话片段
4. **五元素不可省**：每张经验卡片的五个元素都要填写，Pitfall 为空时写"无"
5. **Rule 必须可执行**：模糊建议（如"注意XX"）不合格，必须转化为具体操作指令
6. **Mechanism 必须解释因果**：不能只说"因为文档这么写"，要解释底层为什么
7. **去重必须读文件**：不能凭记忆判断目标文件是否已有类似内容，必须 Read 后 Grep 确认
8. **路由必须确认**：用 AskUserQuestion 展示路由方案，用户确认后再生成补丁
9. **补丁粒度适中**：一个补丁对应一条经验，不要把多条经验合并成一个大补丁

## JOURNAL.md 约定

用户可以在 `.worktree/JOURNAL.md` 中手动记录跨会话的观察。格式约定：

```markdown
# 工作日志

## {YYYY-MM-DD}

- [重试] {简述}
- [惊讶] {简述}
- [绕路] {简述}
- [确认] {简述}
- [环境] {简述}
```

/reflect 会读取此文件作为 L2 输入。如果不存在，跳过此层。

## 与其他技能的协作

- **输入来源**：所有技能的报告「过程备注」节 → /reflect 的 L1 输入
- **输出去向**：REFLECT_PATCHES.md 的补丁 → 用户手动应用到 CLAUDE.md / SKILL.md / guide/
- **触发时机**：建议在一个完整链路（缺陷链或需求链）结束后调用
- **与 CLAUDE.md 的关系**：/reflect 是 CLAUDE.md 的增量更新通道——不直接写入，而是生成可审阅的补丁提案

## 资源管理

所有产物放在 `.worktree/` 下：
```
.worktree/
├── REFLECT.md              # 经验报告
├── REFLECT_PATCHES.md      # 补丁提案
├── JOURNAL.md              # 工作日志（用户手动维护，可选）
└── {其他技能报告}.md        # 过程备注的来源
```

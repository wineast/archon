从版本归档目录提取变更 → 生成三种发布内容 → 写入版本目录。

## 输入

读取 `releases/vN/` 目录下的：
- `RELEASE_REPORT.md` — Release Notes 部分（新功能、缺陷修复、其他）
- `INTEGRATE.md` — Scope + Additions（变更详情）
- `todo/*.md` — 需求任务文件（Context 和 Intent 提供用户视角描述）
- `issues/*.md` — 缺陷任务文件（Symptom 提供用户视角描述）

如果用户未指定版本号，自动取 `releases/` 下最大的 `vN`。

## 输出

在 `releases/vN/` 下生成三个文件：

### 1. `SOCIAL.md` — 社交媒体文案

适用于微信公众号、小红书、Twitter/X 等平台。

```markdown
# vN 发布文案

## 短文案（朋友圈/Twitter）
{1-2 句话，抓眼球，突出最大亮点}

## 长文案（公众号/小红书）
{3-5 段，叙事结构：痛点 → 解决 → 效果}

## 标签
{3-5 个 hashtag}
```

**写作原则**：
- 用户视角，不说技术术语（不说"schema"、"migration"、"API endpoint"）
- 聚焦"能做什么了"而非"改了什么代码"
- 有具体场景：不说"优化了性能"，说"打开页面从 3 秒降到 1 秒"
- 缺陷修复只提用户感知到的问题，不提内部重构

### 2. `SLIDES.md` — PPT 大纲

```markdown
# vN 发布 PPT 大纲

## 封面
- 标题：{产品名} vN 更新
- 副标题：{一句话主题}

## 本次更新概览
- {3-5 个要点，每个一句话}

## {功能 1 标题}
- 痛点：{用户之前遇到什么问题}
- 方案：{现在怎么解决的}
- 效果：{截图/演示建议}
- 演示路径：{从哪个页面开始操作}

## {功能 2 标题}
...

## {修复项}（如果用户感知明显）
- {修复了什么问题}

## 下一步
- {roadmap 预告，从 todo/ 中未归档的高优先级任务提取}

## 结尾
- {CTA：试用链接/联系方式}
```

**设计原则**：
- 每页一个核心信息
- 多用截图占位提示（标注"此处演示 XX 功能"）
- 演示路径具体到操作步骤，方便录屏时参考

### 3. `SCRIPT.md` — 视频口播稿

```markdown
# vN 发布视频脚本

## 基本信息
- 时长：{预估 N 分钟}
- 风格：{产品更新/功能演示}

## 开场（~15s）
[画面：产品 logo / 首页]
口播：{开场白，点明这次更新的主题}

## 功能 1：{标题}（~30-60s）
[画面：从 {页面} 开始操作]
口播：{解说词——痛点 → 演示 → 效果}
操作步骤：
1. {具体操作}
2. {具体操作}

## 功能 2：{标题}（~30-60s）
[画面：...]
口播：{...}
操作步骤：
1. {具体操作}
2. {具体操作}

## 修复项速览（~15s）
[画面：文字列表]
口播：{快速过一遍修复项}

## 结尾（~15s）
[画面：产品首页 / 二维码]
口播：{CTA + 预告下一版}
```

**脚本原则**：
- 口播稿写口语，不写书面语（"我们加了个功能"而非"本次新增了功能"）
- 每个功能配具体操作步骤，录屏时照着做
- 时间预估要保守（实际录制会更长）
- 画面提示标注从哪个页面开始，方便剪辑对位

## 执行流程

1. 确定版本号（用户指定或自动取最新）
2. 读取 `releases/vN/` 下的报告和任务文件
3. 提取变更要点，按用户影响程度排序
4. 生成三个文件，展示给用户
5. 用 `AskUserQuestion` 确认内容是否需要调整
6. 确认后写入 `releases/vN/`

## 关键约束

- **用户视角**：所有内容面向最终用户/客户，不面向开发者
- **版本自包含**：输出文件放在对应版本目录内
- **不虚构**：所有内容必须基于实际变更，不编造功能或效果
- **可操作**：PPT 大纲和视频脚本必须具体到操作步骤，拿来就能用

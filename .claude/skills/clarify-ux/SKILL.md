通过结构化追问帮助用户将模糊的交互描述转化为精确的、可实现的 UX 行为规格。

## 核心理念

交互设计的模糊地带不在"做什么功能"，而在**状态之间的转换**——用户点了之后发生什么？加载中显示什么？失败了怎么回退？空数据看到什么？这些"缝隙"才是 bug 和体验问题的温床。

> 需求澄清回答"做什么"，交互澄清回答"怎么表现"。

## 适用场景

- 新增 UI 功能，交互行为不明确
- 现有功能改版，需要重新定义交互细节
- Review 设计时发现状态/边界没覆盖到
- 用户描述了一个操作流程但缺少异常路径

## 追问方法论

### 第 0 轮：识别交互对象（Identify Target）

先搞清楚在讨论哪个交互组件/流程，以及当前实现是什么样子。

操作：
- 从用户描述中提取**交互对象**（按钮、表单、列表、弹窗、面板……）和**核心动作**（点击、拖拽、输入、切换……）
- 用 `Task`（Explore）或 `Grep`/`Read` 快速查看当前实现：组件结构、已有状态管理、现有交互模式
- 复述："你想讨论的是 XX 组件的 YY 交互行为，对吗？"

### 第 1 轮：状态枚举（States）

**任何交互元素都是一个状态机。** 先把所有可能的状态列出来，再逐个确认表现。

追问方向：
- **初始态**：用户首次看到时是什么样子？有数据和无数据分别什么样？
- **交互态**：hover、focus、active、selected、disabled 分别什么表现？
- **加载态**：操作触发后、结果返回前显示什么？（spinner？skeleton？禁用按钮？）
- **成功态**：操作完成后界面怎么变化？有动画/过渡吗？
- **失败态**：出错时显示什么？用户怎么恢复？（toast？inline error？重试按钮？）
- **空态**：没有数据时显示什么？（空状态插图？引导文案？创建入口？）

技巧：
- 结合代码调研，列出已实现的状态和缺失的状态，让用户补充
- 用 `AskUserQuestion` 给选项："加载态你倾向于 A）按钮内 Spinner B）全局 Loading C）Skeleton 占位"
- 对每个状态确认：是否需要过渡动画

### 第 2 轮：触发与流转（Triggers & Transitions）

**用户的每个操作都会触发状态转换。** 确认每条转换路径。

追问方向：
- **触发方式**：用什么手势/操作触发？（click、double-click、long-press、drag、keyboard shortcut）
- **即时反馈**：触发后立刻发生什么？（按钮变灰？出现进度条？乐观更新？）
- **确认机制**：需要二次确认吗？（确认弹窗？撤销 toast？inline 确认？）
- **可取消性**：操作进行中能取消吗？取消后回到什么状态？
- **连续操作**：快速重复点击怎么处理？（debounce？禁用？队列？）

技巧：
- 画出简单的状态流转："idle → loading → success/error"，让用户确认
- 区分"乐观更新"（先改 UI 再等 API）和"悲观更新"（等 API 再改 UI）
- 关注破坏性操作的确认机制

### 第 3 轮：布局与响应（Layout & Responsiveness）

**交互元素在不同容器尺寸下的表现。**

追问方向：
- **位置**：交互元素放在哪？（页面内、弹窗、抽屉、浮层、固定栏）
- **容器行为**：弹窗/Sheet 关闭后回到哪？侧栏折叠/展开怎么影响？
- **溢出处理**：内容超长怎么办？（truncate？scroll？tooltip 完整文本？）
- **多选/批量**：有批量操作模式吗？批量选中状态怎么表现？

技巧：
- 结合项目已有的布局模式（Sheet、Dialog、侧栏详情页）给建议
- 参考 CLAUDE.md 中的 UI 约定（ScrollArea、底部操作栏等）

### 第 4 轮：边界与异常（Edge Cases）

**正常路径之外的情况。**

追问方向：
- **权限**：无权限时显示什么？（隐藏？禁用+tooltip？提示升级？）
- **并发**：多人同时操作同一资源怎么办？（乐观锁？最后写入胜出？提示冲突？）
- **网络**：离线/弱网时怎么处理？（缓存？重试？降级？）
- **数据极端值**：0 条、1 条、100 条、10000 条数据分别什么表现？
- **中断恢复**：操作到一半刷新页面/关闭浏览器，回来后什么状态？

技巧：
- 不需要每个边界都追问——根据功能重要性判断哪些需要覆盖
- 用"如果……会怎样？"的句式探索
- 对 P0 功能要求覆盖全部边界，P1 功能只覆盖核心路径

### 第 5 轮：一致性检查（Consistency Check）

**确认与项目已有模式的一致性。**

操作：
- 对照 CLAUDE.md 的 UI 约定检查：
  - Loading → `<Spinner />`？
  - 错误提示 → `toast.error()`？
  - 底部操作栏 → Save/Reset/Delete 标准样式？
  - 弹窗按钮 → 只有 Cancel + Primary？
  - 开关 → 启用型 vs 激活型？
- 对照项目中类似功能的交互模式，确认一致或有意偏离
- 如有偏离，向用户确认是否有意为之

## 执行规则

1. **善用 `AskUserQuestion` 给选项**：交互选择天然适合选项式追问（"A 方案还是 B 方案？"），尽量提供可视化的选项描述
2. **每轮 2-3 个问题**：不要一次倒出所有状态让用户崩溃
3. **跳过已明确的**：用户已经描述清楚的状态直接确认跳过
4. **结合现有代码**：调研已有实现后再追问，避免问已经有答案的问题
5. **收敛到可实现**：UX 澄清的目标是产出开发可直接实现的规格，不是做完美设计
6. **尊重项目约定**：CLAUDE.md 中已有的 UI 规范直接沿用，不需要重新讨论

## 输出格式

当交互行为足够清晰后，输出 UX 行为规格：

```markdown
## 交互规格：{组件/功能名}

### 交互对象
{描述交互的目标组件和核心动作}

### 状态定义
| 状态 | 视觉表现 | 进入条件 | 退出条件 |
|------|---------|---------|---------|
| 初始态 | ... | ... | ... |
| 加载态 | ... | ... | ... |
| 成功态 | ... | ... | ... |
| 失败态 | ... | ... | ... |
| 空态 | ... | ... | ... |

### 状态流转
{用文字或简图描述状态转换路径}
- 用户点击 → idle → loading → success/error
- ...

### 交互细节
- **触发方式**：{click/drag/keyboard...}
- **即时反馈**：{按钮 Spinner/禁用/乐观更新...}
- **确认机制**：{无/确认弹窗/撤销 toast...}
- **连续操作**：{debounce/禁用/队列...}

### 边界处理
- **空数据**：{空状态表现}
- **超长内容**：{truncate/scroll/tooltip}
- **错误恢复**：{toast + 重试/inline error}

### 遵循的项目约定
- {列出本次交互涉及的 CLAUDE.md UI 约定}
```

## 与其他技能的协作

- **clarify 调用后衔接**：需求澄清（clarify）确定"做什么"后，可调用本技能进一步明确"怎么表现"
- **独立使用**：已知功能需求、只需确认交互细节时直接调用
- **worktree 中使用**：工作区开发过程中遇到交互不确定时调用

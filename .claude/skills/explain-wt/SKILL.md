解释工作区实现——同步上游、收集变更，然后用**反向采访**帮用户理解工作区做了什么。

## 前置条件

必须在 worktree 内执行（`.worktree/meta.json` 存在）。

## 流程

### 1. 同步上游

调用 `/sync-upstream` 技能，确保变更基于最新上游。

### 2. 收集变更

读取 `.worktree/meta.json` 获取 `baseBranch`，收集全部变更：

```bash
# 未暂存 + 已暂存
git diff
git diff --cached

# 相对于 baseBranch 的提交
git log <baseBranch>..HEAD --oneline
git diff <baseBranch>..HEAD --stat
git diff <baseBranch>..HEAD
```

三类变更都为空则告知用户"无变更"并结束。

如果 diff 过大（超过 3000 行），用 `Task`（subagent_type=Explore）分文件阅读，避免遗漏。

### 3. 提取需求（可选）

如果工作区根目录有 `req.sh`，从中提取 prompt 作为需求基线，便于讲解时对照需求。

### 4. 反向采访

#### 第 1 轮：全局概览

基于收集到的变更，给用户一个极简概览：

```
## {工作区名} 实现概览

{3-5 句话概述：做了什么、为什么这么做、核心架构决策}

涉及文件：
- {文件1} — {一句话说明}
- {文件2} — {一句话说明}
```

然后用 `AskUserQuestion` 提供深入方向供用户选择。

#### 第 2-N 轮：用户选题，AI 深入讲解

每轮：
1. **AI 回答**上一轮用户选择的问题，讲解对应的实现细节
2. **AI 提出**下一批问题选项，基于当前讲到的内容自然延伸

讲解原则：
- **先讲 Why，再讲 What，最后讲 How**
- **用代码佐证**——引用具体文件和行号（`file.ts:42`）
- **对比替代方案**——简要说明为什么选了当前方案
- **标注取舍**——每个设计决策的 trade-off

### 问题生成策略

每轮生成 2-4 个问题选项，覆盖不同维度：

- **架构**："整体数据流是怎样的？"、"为什么选择 X 而不是 Y？"
- **数据**："schema 怎么设计的？"、"新旧数据怎么兼容？"
- **执行**："并发/异步怎么处理？"、"错误处理机制？"
- **UI**："交互流程是什么？"、"状态变化怎么驱动 UI？"
- **边界**："边界情况怎么处理？"、"性能瓶颈在哪？"
- **测试**："怎么验证正确性？"、"测试覆盖了什么？"

技巧：
- 问题要**具体到本次变更**，不泛泛
- 基于上一轮内容**自然延伸**
- 始终保留"我想了解其他方面"的开放选项
- 核心维度覆盖后提供"总结"选项

### 结束条件

当以下任一满足时，主动提供"总结回顾"选项：
- 核心维度都已覆盖
- 用户选择了"总结"
- 已进行 5+ 轮问答

## 总结格式

```markdown
## {工作区名} 实现方案摘要

### 一句话概述
{做了什么}

### 架构决策
- {决策1}：{原因}

### 数据模型
- {表/类型变更概要}

### 核心流程
1. {步骤1}
2. {步骤2}

### 关键 Trade-off
- {取舍}：选了 A 而非 B，因为 {原因}

### 涉及文件
| 文件 | 类型 | 说明 |
|------|------|------|
| {file} | 新增/修改 | {一句话} |

### 需求覆盖度（如有 req.sh）
- ✅ / ⚠️ / ❌ 逐条
```

## 执行规则

1. **每轮必须用 `AskUserQuestion`**：提供问题选项让用户点选
2. **回答要有层次**：用标题/列表结构化
3. **引用代码要精确**：文件路径 + 行号
4. **主动读代码验证**：回答前用 `Read` 确认，不凭记忆
5. **控制篇幅**：每个回答 200-400 字
6. **尊重用户节奏**：用户选什么就讲什么

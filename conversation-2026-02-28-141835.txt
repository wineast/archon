❯ 我问你一个 缺陷报告有哪些基本核心 要素 用第一性原理和柏拉图式提问帮我分析 

⏺ 缺陷报告的第一性原理分析

  起点：缺陷报告的本质是什么？

  用柏拉图式追问层层剥离——

  Q: 缺陷报告为什么存在？
  A: 因为"现实"偏离了"应然"，且发现者和修复者不是同一个人。

  Q: 那它的本质功能是什么？
  A: 跨越认知鸿沟的信息载体——将发现者脑中的"偏差事实"完整传递给修复者，使其能理
  解、定位、复现、修复。

  Q: 如果信息传递完美（零损耗），最少需要传递什么？
  这就是第一性原理的核心问题。

  ---
  四个不可约元素

  从修复者的认知需求反推，任何一个缺少都无法完成修复：

  1. Delta（偏差）—— "错在哪"
  - 期望行为（should be）
  - 实际行为（is）
  - 二者之间的差

  Q: 为什么必须同时有期望和实际？
  A: 只有实际没有期望，修复者不知道什么是"对的"；只有期望没有实际，修复者不知道
  什么"坏了"。偏差是二者的关系，不是某一方的属性。

  2. Reproduction Path（复现路径）—— "怎么触发"
  - 环境/上下文（哪个系统、版本、配置）
  - 操作步骤（按什么顺序做什么）
  - 输入数据（用什么数据触发）

  Q: 为什么不能只描述结果，不给路径？
  A: 缺陷可能是状态依赖的。同一段代码在不同路径下表现不同。没有路径，修复者观察
  不到偏差，等于偏差"不存在"。不可复现的缺陷在认识论上等价于不存在。

  3. Location（定位）—— "在哪里"
  - 哪个模块/功能/页面
  - 哪个版本/分支

  Q: 复现路径不已经隐含了位置吗？
  A: 不完全。路径是用户视角的操作序列，位置是系统视角的代码空间坐标。一条路径可
  能穿过十个模块，修复者需要知道缺陷最终暴露在哪个节点。

  4. Impact（影响）—— "多严重"
  - 严重度（功能不可用 vs 体验瑕疵）
  - 影响范围（所有用户 vs 特定条件下的少数人）

  Q: 影响不是管理层关心的事吗？修复者需要吗？
  A: 修复者需要。影响决定修复策略——阻断级缺陷需要 
  hotfix，低影响缺陷可以等排期。没有影响信息，修复者无法做正确的工程决策。

  ---
  图示：四元素的逻辑关系

             缺陷报告
                │
      ┌─────────┼─────────┐
      │         │         │
    Delta    Path     Location
    (what)   (how)    (where)
      │         │         │
      └─────────┼─────────┘
                │
             Impact
             (so what)

  - Delta 回答"是什么"
  - Path 回答"怎么触发"
  - Location 回答"在哪里"
  - Impact 回答"为什么要修"

  四者构成完备闭环。缺任何一个，修复行为都会退化为猜测。

  ---
  反向验证：传统模板中的其他字段呢？

  ┌─────────────┬────────────────────────────┬────────────┐
  │  常见字段   │          本质归属          │ 独立存在？ │
  ├─────────────┼────────────────────────────┼────────────┤
  │ 标题        │ Delta 的摘要               │ 派生       │
  ├─────────────┼────────────────────────────┼────────────┤
  │ 截图/录屏   │ Delta + Path 的证据        │ 派生       │
  ├─────────────┼────────────────────────────┼────────────┤
  │ 日志        │ Path + Location 的机器视角 │ 派生       │
  ├─────────────┼────────────────────────────┼────────────┤
  │ 优先级      │ Impact 的管理映射          │ 派生       │
  ├─────────────┼────────────────────────────┼────────────┤
  │ 指派人      │ Location 的组织映射        │ 派生       │
  ├─────────────┼────────────────────────────┼────────────┤
  │ 报告人/日期 │ 行政元数据                 │ 与修复无关 │
  └─────────────┴────────────────────────────┴────────────┘

  没有任何传统字段超出四元素的覆盖范围。 这验证了四元素的完备性。

  ---
  一句话总结

  缺陷报告的柏拉图"理型"：用最小信息量回答——什么东西在哪里因为什么操作产生了多严
  重的偏差。

❯ 优化呢 刚才说了缺陷，我接下来会问你需求和优化，先是优化 

⏺ 优化报告的第一性原理分析

  起点：优化与缺陷的本质区别是什么？

  Q: 缺陷是"现实偏离了应然"，那优化是什么？
  A: 优化是"应然本身可以更好"。系统没有错，但存在一个更优的可能态。

  Q: 这意味着什么？
  A: 缺陷有明确的"对/错"判据（规格说明）。优化没有——它要回答的不是"对不对"，而是
  "好不好"和"能不能更好"。

  Q: "更好"是一个主观判断吗？
  A: 不完全。"更好"需要一个度量标准。没有度量标准的优化提案只是一个观点，不是工
  程命题。

  这就是优化与缺陷最根本的分歧：缺陷的锚点是规格，优化的锚点是度量。

  ---
  柏拉图式追问：最少需要什么？

  Q: 假设我是修复者，你告诉我"这里可以优化"，我第一个问题是什么？
  A: "优化什么？"——你需要告诉我度量维度。

  Q: 知道了维度，我第二个问题是什么？
  A: "现在多少？"——我需要基线值。

  Q: 然后呢？
  A: "要到多少？"——我需要目标值。

  Q: 知道了目标，我还缺什么？
  A: "为什么值得做？"——优化有成本，我需要知道收益是否值得投入。

  Q: 还有呢？
  A: "改哪里？"——我需要知道瓶颈在哪，否则我可能优化了错误的地方。

  到这里追问就闭合了——再问下去都是这五个的派生。

  ---
  五个不可约元素

             优化报告
                │
       ┌────────┼────────┐
       │        │        │
    Metric   Baseline   Target
    (量什么)  (现在多少)  (要到多少)
       │        │        │
       └────────┼────────┘
                │
        ┌───────┴───────┐
        │               │
    Bottleneck       Tradeoff
    (卡在哪)         (值不值)

  1. Metric（度量维度）—— "优化什么"

  性能？体验？成本？可维护性？

  Q: 为什么不能说"优化这个页面"？
  A: "页面"不是度量维度。加载速度是维度，渲染帧率是维度，跳出率是维度。同一个对
  象在不同维度上可能互相矛盾——压缩图片提升加载速度，但降低视觉质量。不指定维度，
  优化方向是不确定的。

  2. Baseline（基线值）—— "现在多少"

  当前状态的量化值。

  Q: 为什么需要量化？"感觉慢"不够吗？
  A: "感觉慢"是症状描述，不是工程输入。P50 响应 3.2s 
  是基线。没有基线，你无法判断优化后是否真的"更好了"——人的感知有锚定偏差，会被期
  望污染。没有基线的优化无法验证。

  3. Target（目标值）—— "要到多少"

  期望达到的值或范围。

  Q: "越快越好"不是一个合理目标吗？
  A: 不是。优化存在边际递减。从 3s 到 1s 可能只需要加个缓存，从 1s 到 200ms 
  可能需要重写架构。没有目标值，修复者不知道在哪里停下来，要么过度工程，要么不够
  到位。目标值定义了"完成"的含义。

  4. Bottleneck（瓶颈）—— "卡在哪"

  系统中限制度量值提升的具体环节。

  Q: 能不能让修复者自己找瓶颈？
  A: 可以，但这就等于把一半的工作量转嫁了。更重要的是——报告者和修复者看到的系统
  面不同。报告者可能从监控/用户反馈/生产数据中观察到了瓶颈分布，这些信息修复者不
  一定有。Bottleneck 是连接"度量"与"实现"的桥梁。

  Q: 缺陷报告里没有 Bottleneck，为什么优化需要？
  A: 缺陷的复现路径本身就指向了问题位置。优化不同——系统"正常运行"，所有路径都"没
  问题"，你需要额外信息来缩小调查范围。缺陷是局部故障，优化是全局调优。

  5. Tradeoff（权衡）—— "值不值"

  优化的代价是什么，收益与代价的比值。

  Q: 缺陷报告有 Impact，优化的 Tradeoff 与之对应吗？
  A: 不完全。Impact 
  是单向的——缺陷只有代价没有收益（修复只是恢复应然）。优化是双向的——有收益（度量
  改善）也有代价（开发成本、复杂度增加、其他维度退化）。Tradeoff 
  回答的不是"有多重要"，而是"划不划算"。

  Q: 具体包含什么？
  A: 三层：
  - 开发成本：改动规模、技术风险
  - 副作用：是否损害其他维度（如性能优化导致可读性下降）
  - 不做的后果：如果不优化，会恶化吗？还是维持现状可接受？

  ---
  与缺陷报告的结构对比

  ┌──────────┬──────────────────┬──────────────────────┐
  │          │     缺陷报告     │       优化报告       │
  ├──────────┼──────────────────┼──────────────────────┤
  │ 核心锚点 │ 规格（spec）     │ 度量（metric）       │
  ├──────────┼──────────────────┼──────────────────────┤
  │ 驱动力   │ "错了" → 必须修  │ "不够好" → 可以不做  │
  ├──────────┼──────────────────┼──────────────────────┤
  │ 判断标准 │ 二元（对/错）    │ 连续（好/更好/最好） │
  ├──────────┼──────────────────┼──────────────────────┤
  │ 验证方式 │ 复现 → 不再复现  │ 基线 → 达到目标      │
  ├──────────┼──────────────────┼──────────────────────┤
  │ 决策维度 │ 严重度（Impact） │ 性价比（Tradeoff）   │
  ├──────────┼──────────────────┼──────────────────────┤
  │ 结束条件 │ 偏差消除         │ 目标达成             │
  └──────────┴──────────────────┴──────────────────────┘

  ---
  一句话总结

  优化报告的柏拉图"理型"：用什么度量衡量，从什么基线提升到什么目标，瓶颈在哪，以
  及这件事值不值得做。

❯ 继续处理 需求 

⏺ 需求文档的第一性原理分析

  起点：需求的本质是什么？

  先把三者放在一起看——

  Q: 缺陷是"现实偏离应然"，优化是"应然可以更好"，那需求是什么？
  A: 需求是**"应然尚不存在"**。系统中没有这个能力，需要从无到有创造。

  Q: 更精确地说？
  A: 缺陷修复的是偏差，优化移动的是刻度，需求创造的是新维度。

  Q: 那需求文档的本质功能是什么？
  A: 将一个尚不存在的事物描述得足够清晰，使得实现者能够把它造出来，且造出来的东
  西与描述者脑中的一致。

  这比缺陷和优化都难——因为参照物不存在。缺陷有"正确行为"做锚，优化有"当前值"做锚
  ，需求的锚只存在于提出者的头脑中。

  ---
  柏拉图式追问：最少需要传递什么？

  Q: 假设我是实现者，你说"我要一个新功能"，我的第一个问题？
  A: "谁要用？"——我需要知道主体。

  Q: 知道了谁，第二个问题？
  A: "他现在遇到什么问题？"——我需要知道动机。

  Q: 知道了动机，然后？
  A: "他要能做什么？"——我需要知道能力。

  Q: 知道了要做什么，够了吗？
  A: 不够。"做到什么程度算成？"——我需要验收标准。

  Q: 还有呢？
  A: "有什么不能碰的？"——我需要知道约束。

  Q: 再追问一层呢？
  A: 闭合了。再问都是这五个的展开。

  ---
  五个不可约元素

                需求文档
                   │
           ┌───────┼───────┐
           │       │       │
         Who    Why     What
        (谁)   (为何)   (做什么)
           │       │       │
           └───────┼───────┘
                   │
           ┌───────┴───────┐
           │               │
      Acceptance       Constraint
      (怎么算成)       (什么不行)

  1. Who（主体）—— "谁在用"

  使用者是谁，什么角色，什么场景。

  Q: 为什么不能直接说"做什么"，非要先说"谁"？
  A: 因为同一个功能对不同主体的正确实现完全不同。"导出数据"——给运营导 Excel 
  就行，给财务要符合审计格式，给开发者要 API + JSON。主体决定了实现的形态。跳过 
  Who 直接写 What，实现者只能猜，猜错的概率极高。

  Q: Who 和"用户画像"是一回事吗？
  A: 用户画像是 Who 
  的一种展开形式，但核心只需要回答：谁，在什么场景下，以什么角色。三个定语足矣。

  2. Why（动机）—— "为什么需要"

  驱动这个需求的根本原因。

  Q: 这不是产品经理的事吗？实现者需要知道 Why？
  A: 必须。 Why 是需求文档中最重要的元素，没有之一。原因有二：
  - 实现者需要做设计决策。需求不可能覆盖所有边界情况，遇到文档没写的 case 
  时，实现者用 Why 来推导正确行为。没有 Why，每个边界 case 都要回去问。
  - Why 是唯一能区分"需要"和"想要"的工具。用户说"我要一匹更快的马"（What），Why 
  是"我要更快到达目的地"——这可能指向一辆车。没有 Why 
  的需求文档会忠实地交付一匹快马。

  Q: 这就是福特的经典例子？
  A: 正是。它揭示了一个结构性问题：What 是 Why 的一个解，但不是唯一解。只传递 
  What 等于把解空间压缩成一个点，剥夺了实现者发现更优解的可能性。

  3. What（能力）—— "要能做什么"

  系统获得的新能力边界。

  Q: What 是"功能描述"吗？
  A: 不完全。"功能描述"暗示了实现方式，What 
  应该是能力声明——描述用户获得了什么新的可能性，而不是系统怎么实现。

  Q: 区别在哪？
  A: 
  - 功能描述："在侧栏添加一个筛选下拉框，选项包含 A/B/C"
  - 能力声明："用户能够按类型筛选列表内容"

  前者锁死了 UI 方案。后者给实现者空间——也许搜索框 + 标签比下拉框更好。What 
  定义"能做什么"，不定义"怎么做"。

  4. Acceptance（验收标准）—— "怎么算完成"

  可验证的、具体的完成条件。

  Q: 不是有了 What 就知道做完没做完吗？
  A: What 是模糊的。"用户能够按类型筛选"——空列表要不要显示提示？筛选后要不要保持
  排序？URL 要不要同步状态？这些 What 
  都没说。验收标准把自然语言的模糊性压缩为可判定的命题。

  Q: 验收标准和测试用例是一回事吗？
  A: 不是。验收标准是契约（什么条件下宣告完成），测试用例是验证手段（用什么方法
  检查契约是否满足）。一个验收标准可能对应多个测试用例。验收标准属于需求域，测试
  用例属于实现域。

  Q: 缺陷和优化有没有类似的元素？
  A: 
  缺陷的验收是"偏差消除"（隐式的，不用写），优化的验收是"达到目标值"（已包含在 
  Target 中）。只有需求必须显式声明——因为它从无到有，没有任何隐式锚点可以借用。

  5. Constraint（约束）—— "什么不能做"

  实现过程中不可违反的边界。

  Q: 约束不是应该写在技术方案里吗？
  A: 有两类约束，来源不同：
  - 业务约束：来自需求提出者。"不能改变现有用户的操作习惯"、"必须兼容旧数据"、"
  不能依赖第三方服务"
  - 技术约束：来自系统现状。"必须在现有架构内实现"、"不能增加超过 50ms 延迟"

  前者必须在需求文档中，因为实现者无法自行推导。后者可以后补，但如果已知应该提前
  说明。

  Q: What 定义了"解空间"，Constraint 的角色是什么？
  A: Constraint 裁剪解空间。 What 说"能做什么"，Constraint 
  说"不能怎么做"。两者共同围出一个区域——实现者在这个区域内选择最优解。没有 
  Constraint，解空间太大，实现者可能选到一个技术上可行但业务上不可接受的解。

❯ 假如我已经有了这个缺陷报告，现在需要一个修复报告 他的核心要素是什么 

⏺ 修复报告的第一性原理分析

  起点：修复报告与缺陷报告的关系是什么？

  Q: 缺陷报告从发现者传向修复者，修复报告传向谁？
  A: 至少三个受众：
  - 验证者：要确认缺陷确实被消除了
  - 未来维护者：要理解这段代码为什么长这样
  - 报告者：要得到闭环

  Q: 那本质功能是什么？
  A: 缺陷报告传递的是观察（我看到了什么），修复报告传递的是决策（我做了什么以及
  为什么）。

  Q: 为什么强调"决策"而不是"改动"？
  A: 因为改动本身 diff 就能看到。修复报告存在的意义在于——diff 
  不会告诉你为什么这样改，也不会告诉你考虑过但没采用的方案。

  缺陷报告是问句（发生了什么？），修复报告是答句（因为什么，所以怎么做）。

  ---
  柏拉图式追问

  Q: 我是验证者，你说"修好了"。我第一个问题？
  A: "到底是什么原因？"——我需要 Root Cause。

  Q: 知道了原因，第二个问题？
  A: "你改了哪里？"——我需要 Change。

  Q: 看了 diff，第三个问题？
  A: "为什么这样改而不是那样改？"——我需要 Rationale。

  Q: 理解了决策，第四个问题？
  A: "这个改动会不会弄坏别的东西？"——我需要 Blast Radius。

  Q: 最后？
  A: "怎么证明确实修好了？"——我需要 Verification。

  闭合。

  ---
  五个不可约元素

                修复报告
                   │
          ┌────────┼────────┐
          │        │        │
     Root Cause  Change  Rationale
     (为什么坏)  (改了啥) (为什么这样改)
          │        │        │
          └────────┼────────┘
                   │
          ┌────────┴────────┐
          │                 │
     Blast Radius      Verification
     (还动了什么)      (怎么证明好了)

  1. Root Cause（根因）—— "为什么坏了"

  缺陷的真正成因，不是症状。

  Q: 缺陷报告里的 Delta 不就说了"哪里错"吗？
  A: Delta 说的是现象（期望 A 得到 B），Root Cause 回答的是机理（为什么会得到 
  B）。一个 Delta 背后可能有完全不同的 Root Cause：
  - 同样是"保存后数据丢失"，可能是竞态条件，可能是类型转换截断，可能是缓存未失效
  - Delta 是果，Root Cause 是因。 缺陷报告只传递果，修复报告必须回答因

  Q: Root Cause 找错了会怎样？
  A: 你会修复一个症状而非疾病。表面上缺陷消失了，过一阵以另一种症状复发。Root 
  Cause 的质量决定修复的持久性。

  2. Change（变更）—— "具体改了什么"

  修改了系统的哪些部分，做了什么改动。

  Q: 看 diff 不就行了？为什么要写出来？
  A: diff 是全量事实，Change 是结构化摘要。一个修复可能涉及 12 个文件 200 
  行改动，但逻辑上只做了三件事。Change 的价值是把散落的 diff 
  组织成可理解的叙事：
  - "在 X 模块增加了空值检查"
  - "修改了 Y 函数的调用顺序"
  - "移除了 Z 中的冗余缓存"

  Q: 这和 git commit message 不一样吗？
  A: commit message 是 Change 的最小化形式。当修复涉及多个 commit 
  或跨模块协调时，需要一个更高层次的叙事把它们串起来。

  3. Rationale（决策依据）—— "为什么这样改"

  选择此方案的理由，以及被排除的替代方案。

  Q: 缺陷报告、优化报告、需求文档里都没有这个元素，为什么修复报告独有？
  A: 因为前三者都是描述性文档（描述现实或期望），只有修复报告是决策性文档（记录
  做了一个选择）。有选择就有理由，有理由就有被排除的替代方案。

  Q: 具体需要回答什么？
  A: 三个子问题：
  - 为什么这个方案而不是另一个？ 
  "在调用层加空值检查，而非在数据源头修复，因为数据源是第三方 API 不可控"
  - 考虑过什么替代方案？ "也考虑过加全局拦截器，但影响范围太大"
  - 这个方案的已知局限？ "只处理了 null，undefined 的情况还需要后续跟进"

  Q: 不写 Rationale 会怎样？
  A: 六个月后另一个开发者看到这段"丑陋的空值检查"，觉得多余，重构掉了。缺陷复发
  。Rationale 是给未来维护者的护栏——告诉他们"这段代码长这样是有原因的，别动"。

  4. Blast Radius（影响范围）—— "还影响了什么"

  这个改动波及的其他行为、模块、用户场景。

  Q: 这和缺陷报告的 Impact 有什么区别？
  A: 方向相反。
  - Impact 是缺陷的扩散面——坏的东西影响了多少好的
  - Blast Radius 是修复的扩散面——修好一个东西可能弄坏多少别的

  Impact 回答"有多痛"，Blast Radius 回答"治疗有没有副作用"。

  Q: 为什么不能假设"只要测试通过就没有副作用"？
  A: 因为测试覆盖率不是 100%，且不可能是 100%。Blast Radius 
  的价值是告诉验证者该额外检查什么——那些测试可能没覆盖到的地方。

  Q: 具体包含什么？
  A:
  - 直接影响：修改的代码被哪些功能调用
  - 间接影响：行为变化是否可能引发上下游连锁反应
  - 不影响：明确声明不受影响的部分（减少验证者的焦虑）

  5. Verification（验证方式）—— "怎么证明修好了"

  如何确认缺陷已消除且没有引入新问题。

  Q: 这和缺陷报告里的 Path（复现路径）是什么关系？
  A: 镜像关系。Path 是"按这些步骤能看到缺陷"，Verification 
  是"按这些步骤不再看到缺陷"。但 Verification 比 Path 多一层——还要验证 Blast 
  Radius 中标记的影响区域没有回归。

  Q: 具体包含什么？
  A: 两部分：
  - 正向验证：原来的复现路径走一遍，缺陷不再出现
  - 回归验证：Blast Radius 标记的区域走一遍，行为正常

  ---
  与缺陷报告的镜像关系

  修复报告的每个元素都是缺陷报告对应元素的回应：

  缺陷报告                      修复报告
  ────────                      ────────
  Delta (现象)     ──回答──→    Root Cause (成因)
    "什么坏了"                    "为什么坏了"

  Location (位置)  ──回应──→    Change (变更)
    "在哪里"                      "改了哪里"

  Path (路径)      ──镜像──→    Verification (验证)
    "怎么触发"                    "怎么确认修好"

  Impact (影响)    ──反转──→    Blast Radius (波及)
    "坏了多少"                    "修复波及多少"

      ∅            ──新增──→    Rationale (决策)
                                  "为什么这样修"

  唯一新增的元素是
  Rationale——因为缺陷报告是观察，不做决策；修复报告是行动，必须解释决策。

✻ Cooked for 1m 23s

❯ 有了缺陷和修复，我还需要验证报告 帮我继续分析                             
  我基于这个报告就可以判断是否可以合并这个分支了                            

⏺ 验证报告的第一性原理分析

  起点：验证报告在链条中的位置

  缺陷报告          修复报告          验证报告
  发现者 → 修复者    修复者 → 验证者    验证者 → 决策者
   "这里坏了"        "我这样修的"       "可以/不可以合并"
    观察              决策               裁定

  Q: 三份报告传递的东西本质上有什么不同？
  A:
  - 缺陷报告传递事实（what is）
  - 修复报告传递行动（what was done）
  - 验证报告传递判决（should we ship）

  Q: 验证报告为什么不能被"测试通过"替代？
  A: 因为"测试通过"只是证据的一种。合并决策需要的是综合判断——测试可能没覆盖到关
  键路径，Root Cause
  可能被误诊，修复可能只是压制了症状。验证报告不是测试报告，它是审判书。

  Q: 那它的本质功能是什么？
  A: 将修复者声称的一切逐项质证，产出一个有证据支撑的二元判决：合并或驳回。

  ---
  柏拉图式追问

  Q: 我是决策者，你告诉我"验证通过了"。我第一个问题？
  A: "缺陷真的消失了吗？"——我需要 Reproduction Result。

  Q: 消失了。第二个问题？
  A: "修复者说的根因对吗？改法合理吗？"——我需要 Cause-Fix Coherence。

  Q: 为什么？缺陷消失了不就够了吗？
  A: 不够。感冒吃了止痛药，头不疼了，但感冒没好。症状消除 ≠ 病因消除。
  我必须确认修复者治的是病，不是止的痛。

  Q: 好，根因确认了。还需要什么？
  A: "换个姿势还成立吗？"——我需要 Boundary Validation。

  Q: 什么意思？
  A: 缺陷报告给了一条复现路径，但这条路径只是触发缺陷的一个实例。其他输入、并发
  场景、极端值呢？修复可能恰好堵住了那一个洞，旁边还有三个。

  Q: 边界也验过了。然后？
  A: "别的东西没坏吧？"——我需要 Regression Result。

  Q: 最后？
  A: "所以结论是什么？"——我需要一个
  Verdict。不是"大概可以"，是有条件的明确裁定。

  闭合。

  ---
  五个不可约元素

                 验证报告
                    │
         ┌──────────┼──────────┐
         │          │          │
    Reproduction  Coherence  Boundary
    (缺陷消了吗)  (因果对吗) (边界扛吗)
         │          │          │
         └──────────┼──────────┘
                    │
          ┌─────────┴─────────┐
          │                   │
      Regression           Verdict
      (别处坏了吗)          (合不合并)

  1. Reproduction Result（复现验证）—— "缺陷真的消失了吗"

  用缺陷报告的原始 Path 走一遍，Delta 不再出现。

  Q: 这不就是"跑一遍测试"吗？
  A: 不完全。测试验的是代码逻辑，复现验证验的是用户视角的完整路径。测试可能 mock
   了中间环节，复现验证必须端到端走完。测试说"函数返回值对了"，复现验证说"用户看
  到的结果对了"。

  Q: 通过了说明什么？没通过说明什么？
  A: 
  - 通过：修复至少在已知路径上消除了症状（必要条件，非充分条件）
  - 未通过：修复无效，直接驳回，后续步骤无需继续

  2. Cause-Fix Coherence（因果一致性）—— "根因分析对吗？改法合理吗"

  质证修复报告中声称的 Root Cause 和 Rationale 是否经得起推敲。

  Q: 缺陷消失了，为什么还要检验根因？
  A: 因为正确结果可以由错误推理产生。一个经典场景：
  - Root Cause 声称"竞态条件导致数据覆盖"
  - 实际改动是"加了 200ms 延迟"
  - 缺陷确实消失了——因为延迟恰好避开了竞态窗口
  - 但负载一高、机器一慢，窗口又会重叠，缺陷复发

  复现通过只证明"现在好了"，因果一致性证明"以后也会好"。

  Q: 验证者怎么判断因果是否一致？
  A: 三个检查：
  - Root Cause 可解释 Delta：声称的原因能否逻辑上导出观察到的现象？
  - Change 可消除 Root Cause：改动是否从机理上切断了因果链，而非绕过它？
  - Rationale 无漏洞：排除的替代方案理由是否成立？选择的方案有无逻辑盲区？

  Q: 如果因果不一致但复现通过了，结论是什么？
  A: 驳回或有条件通过。要求修复者重新分析根因。一个因果不一致的修复是定时炸弹。

  3. Boundary Validation（边界验证）—— "换个姿势还行吗"

  在原始复现路径的变体下验证修复是否依然有效。

  Q: 这和 Reproduction 有什么区别？
  A: Reproduction 走的是缺陷报告给出的原路径——是已知的、确定的。Boundary 
  验的是未知的、推导出的路径。
  - 原路径：输入 null 触发崩溃
  - 边界变体：undefined 呢？空字符串呢？超长字符串呢？并发提交呢？

  Reproduction 验证"这个洞堵上了"，Boundary 验证"旁边没有同类型的洞"。

  Q: 边界从哪来？怎么确定测什么？
  A: 三个来源：
  - Root Cause 推导：根因是空值未处理，那所有"类空值"输入都要验
  - Change 波及推导：改了这个函数，调用它的其他路径要验
  - 领域知识：这类缺陷的常见变体（如时区、编码、并发、权限）

  Q: Boundary 和 Regression 有什么区别？
  A: 方向不同。
  - Boundary 是纵深——同一个缺陷的不同触发方式
  - Regression 是横向——其他不相关的功能是否受损

  一个验"修得够不够彻底"，一个验"修的过程中有没有弄坏别的"。

  4. Regression Result（回归验证）—— "别的东西没坏吧"

  修复报告声明的 Blast Radius 区域 + 核心功能路径的完整性检查。

  Q: 跑 CI 全量测试不就行了？
  A: CI 是 Regression 的自动化部分，但不是全部。
  - CI 覆盖的是已有测试用例，已有测试可能没覆盖 Blast Radius 标记的区域
  - 修复报告说"可能影响 X 模块"，如果 X 模块测试覆盖率只有 30%，CI 通过不代表 X 
  没坏
  - Regression = CI 结果 + Blast Radius 区域的定向手动验证

  Q: 如果 Blast Radius 写了"不影响其他模块"，还需要验吗？
  A: 仍需抽检。修复者声称的 Blast Radius 是一个待验证的假设，不是事实。 
  修复者可能低估了耦合程度。

  5. Verdict（裁定）—— "合还是不合"

  基于以上四项证据，给出明确判决。

  Q: 为什么需要一个独立的 Verdict？前四项结果不就是结论了吗？
  A: 因为四项结果可能互相矛盾或需要权衡：
  - 复现通过 + 因果不一致 → 怎么判？
  - 复现通过 + 边界有一个 case 失败但极端罕见 → 怎么判？
  - 全部通过但 Blast Radius 的手动验证不完整 → 怎么判？

  Verdict 不是机械汇总，是综合判断。

  Q: Verdict 应该包含什么？
  A: 三部分：
  - 判决：合并 / 驳回 / 有条件合并
  - 证据摘要：四项验证的关键发现（一句话 each）
  - 残留风险（如有）：已知但可接受的风险、需后续跟进的事项

  Q: "有条件合并"是什么？
  A: 比如：
  - "合并，但需补充 X 场景的自动化测试"
  - "合并，但需在灰度环境观察 48 小时"
  - "合并，但标记 Y 问题为 follow-up issue"

  不是所有事情都必须在当前修复中解决。Verdict 
  要区分"阻塞合并的问题"和"合并后跟进的问题"。

  ---
  与修复报告的镜像关系

  验证报告的每个元素都是修复报告对应元素的质证：

  修复报告                        验证报告
  ────────                        ────────
  Root Cause (根因)    ──质证──→   Coherence (因果一致性)
    "因为 X 所以坏了"               "X 真的能导致这个现象吗？"

  Change (变更)        ──质证──→   Coherence (因果一致性)
    "改了 Y"                       "Y 真的能消除 X 吗？"

  Rationale (决策)     ──质证──→   Coherence (因果一致性)
    "选 A 不选 B 因为..."          "这个理由成立吗？"

  Verification (验证)  ──执行──→   Reproduction (复现验证)
    "按这个步骤确认"               "执行了，结果是..."

  Blast Radius (波及)  ──执行──→   Regression (回归验证)
    "可能影响 Z 区域"              "Z 区域验过了，结果是..."

       ∅               ──新增──→   Boundary (边界验证)
                                    "还有这些变体也要验"

       ∅               ──新增──→   Verdict (裁定)
                                    "综上，合并/驳回"

  新增两个元素：Boundary（修复者不会主动挑战自己的修复）和
  Verdict（修复者不做合并决策）。

  ---
  完整链条：从发现到合并

   发现者          修复者           验证者          决策者
     │               │               │              │
     │  缺陷报告     │               │              │
     │──────────────→│               │              │
     │               │  修复报告     │              │
     │               │──────────────→│              │
     │               │               │  验证报告    │
     │               │               │─────────────→│
     │               │               │              │
     │               │               │           合并/驳回

  四份文档构成完整的证据链：

  ┌──────────┬────────┬──────────┬──────┐
  │   文档   │  性质  │ 核心问题 │ 产出 │
  ├──────────┼────────┼──────────┼──────┤
  │ 缺陷报告 │ 起诉书 │ 什么坏了 │ 事实 │
  ├──────────┼────────┼──────────┼──────┤
  │ 修复报告 │ 辩护词 │ 怎么修的 │ 决策 │
  ├──────────┼────────┼──────────┼──────┤
  │ 验证报告 │ 审判书 │ 能不能信 │ 判决 │
  └──────────┴────────┴──────────┴──────┘

  Q: 为什么用司法隐喻？
  A: 因为结构同构。起诉书陈述事实，辩护词解释行为，审判书质证双方并做裁定。验证
  者不是修复者的助手，是独立的第三方裁判。

  一句话总结

  验证报告的柏拉图"理型"：缺陷确实消失了吗，根因和改法因果一致吗，边界变体扛住了
  吗，其他功能没坏吧——综上，合还是不合。

❯ 然后我们走需求的那个链路 你先帮我分析 需求报告的 

⏺ 需求报告的第一性原理分析（链路视角）

  先建立平行结构

  前面我们走完了缺陷链路：

  缺陷报告 ──→ 修复报告 ──→ 验证报告
   起诉书       辩护词       审判书
   事实         决策         判决

  现在要走需求链路。先追问：这条链路的结构是什么？

  Q: 缺陷链路是"偏差出现 → 偏差消除 → 确认消除"。需求链路呢？
  A: "能力缺失 → 能力创造 → 确认创造"。

  需求报告 ──→ 实现报告 ──→ 验收报告
    ？          ？           ？

  Q: 那需求报告在链路中扮演什么角色？
  A: 缺陷报告是起诉书——指着一个坏掉的东西说"这里有问题"。需求报告是委托书——指着
  一片空白说"这里要造一个东西"。

  Q: 哪个更难？
  A: 需求报告更难。根本性地更难。

  Q: 为什么？
  A: 缺陷报告描述已经存在的现象——你看到了，拍下来，写下来就行。需求报告描述尚不
  存在的事物——你要用语言在两个人脑中构建出同一个幻象。

  缺陷报告的失败模式是"描述不清"，需求报告的失败模式是"理解不一致"。
  前者是精度问题，后者是认知对齐问题——量级完全不同。

  ---
  柏拉图式追问：从链路倒推

  这次不从"实现者需要什么"正向推，而是从链路终点倒推——

  Q: 链路的终点是什么？
  A: 验收报告的 Verdict：这个东西造出来了，合并。

  Q: 验收报告需要验什么？
  A: 造出来的东西与需求一致。

  Q: "一致"用什么衡量？
  A: 需求报告中定义的验收标准。

  Q: 那验收标准从哪来？
  A: 从对"要造什么"的精确定义——What。

  Q: What 从哪来？
  A: 从"为什么要造"——Why。Why 决定了 What 的形态。

  Q: Why 从哪来？
  A: 从"谁遇到了什么困境"——Who + Context。

  Q: 还缺什么？
  A: 有了"造什么"和"怎么算成"，还缺"什么不能碰"——Constraint。没有它，实现者可能
  交付一个功能正确但违反业务规则的解。

  Q: 再追问？
  A: 闭合。

  关键洞察：从链路终点倒推和之前从实现者需求正向推，收敛到同样五个元素——这交叉验
  证了完备性。

  ---
  五个不可约元素（链路版）

  之前独立分析过这五个元素，现在用链路视角重新审视——每个元素在链路中承担什么角色
  。

                需求报告
                   │
           ┌───────┼───────┐
           │       │       │
         Who     Why     What
        (谁)    (为何)   (做什么)
           │       │       │
           └───────┼───────┘
                   │
           ┌───────┴───────┐
           │               │
      Acceptance       Constraint
      (怎么算成)       (什么不行)

  1. Who（主体 + 场景）—— "谁在什么处境下"

  Q: 缺陷报告没有 Who，为什么需求报告需要？
  A: 因为缺陷是系统出了问题，跟谁在用无关——任何人走同一条路径都会触发。需求是人
  有了需要，不同的人同一句话含义完全不同。

  "我要导出数据"：
  - 运营说这句话 → Excel，带筛选条件，日常使用
  - 审计说这句话 → 固定格式 PDF，带数字签名，年度一次
  - 开发者说这句话 → API + JSON，批量拉取，自动化脚本

  不确定 Who，What 是不确定的。

  链路中的角色：Who
  传递给实现报告后，实现者据此设计用户流程；传递给验收报告后，验收者用 Who
  的视角走验收路径。

  2. Why（动机）—— "为什么需要这个能力"

  Q: 缺陷报告有 Delta（什么坏了），这里的 Why 对应什么？
  A: Delta 是"可观察的偏差"，Why 是"可理解的痛点"。Delta 
  可以机械复制（截图、日志），Why 必须被理解——这是需求链路比缺陷链路更难的根源。

  Q: 为什么 Why 是五个元素中最重要的？
  A: 因为 Why 是链路中唯一不可从其他元素推导的信息。
  - What 可以从 Why 推导（知道为什么，能推出做什么）
  - Acceptance 可以从 What 推导（知道做什么，能推出怎么验）
  - Constraint 可以从 Who + Context 推导（知道谁在什么环境下，能推出什么限制）
  - 但 Why 不能从任何其他元素反推。 它是根节点。

  丢失 What，实现者可以从 Why 重新推导出一个 What。
  丢失 Why，实现者只能照着 What 机械执行——遇到 What 没覆盖的边界 case 就瞎了。

  链路中的角色：Why 是整条链路的北极星。实现报告中的 Design Decision 要锚定
  Why，验收报告中的 Verdict 最终也要回答"这个 Why 被满足了吗"。

  3. What（能力声明）—— "系统要获得什么新能力"

  Q: 缺陷报告的 Delta 和需求报告的 What 结构上有什么区别？
  A: 
  - Delta = 期望值 - 实际值（两端都已知）
  - What = 目标态 - 当前态（目标态不存在，需要构造）

  Delta 是做减法（找差距），What 是做创造（定义新事物）。

  Q: What 应该写到什么粒度？
  A: 这是需求报告中最微妙的平衡。用柏拉图的洞穴比喻：
  - 太抽象（只有影子）："用户能管理数据"——实现者看到的是模糊的轮廓
  - 太具体（锁死实现）："在页面右上角加一个 32px 
  蓝色按钮"——剥夺了实现者寻找更优解的空间
  - 恰好（能力边界）："用户能够批量删除已过期的记录，操作前需确认"——清晰的能力声
  明，不锁定 UI 方案

  链路中的角色：What 是需求报告与实现报告之间的契约接口。实现报告的 Change Set
  必须覆盖 What 声明的每一项能力。

  4. Acceptance（验收标准）—— "怎么判定做到了"

  Q: 缺陷链路中没有独立的 Acceptance 
  元素（验证是"偏差消除"就行），为什么需求链路需要？
  A: 因为缺陷有隐式锚点——修复前的正确行为就是验收标准，不用额外定义。需求没有锚
  点——你在创造新东西，"做到了"的定义必须显式声明，否则需求方和实现方脑中的"做到
  了"是两个不同的画面。

  Q: Acceptance 和 What 的区别是什么？
  A:
  - What：自然语言的能力声明（有解读空间）
  - Acceptance：可判定的命题集（只有 true/false）

  What："用户能按类型筛选列表"
  Acceptance：
  - 选择类型 A 后，列表只显示类型 A 的条目 ✓/✗
  - 选择"全部"后，列表恢复完整 ✓/✗
  - 筛选状态在刷新后保持 ✓/✗
  - 无匹配时显示空状态提示 ✓/✗

  What 是散文，Acceptance 是清单。

  链路中的角色：Acceptance 是整条链路的终止条件。验收报告的核心工作就是逐项核对
  Acceptance 清单。没有 Acceptance，链路没有终点——永远可以说"还不够好"。

  5. Constraint（约束）—— "什么边界不可越过"

  Q: 缺陷链路的 Blast Radius 是"修复影响了什么"，Constraint 与之对应吗？
  A: 方向相反。
  - Blast Radius 是事后描述：改完了才知道波及了什么
  - Constraint 是事前声明：动手前就划定不可触碰的红线

  Blast Radius 是修复者写给验证者的，Constraint 是需求方写给实现者的。

  Q: 为什么不能让实现者自己判断约束？
  A: 因为约束有两个来源，实现者只能看到一个：
  - 技术约束：实现者能自行判断（架构限制、性能预算）
  - 业务约束：实现者无法推导（"不能改变老用户习惯"、"必须兼容旧系统"、"法规要求
  留审计日志"）

  业务约束必须由需求方显式声明，否则实现者交付的解可能技术完美但业务不可接受。

  链路中的角色：Constraint 传递给实现报告后，实现者需在 Design Decision
  中说明如何满足每条约束；传递给验收报告后，验收者需逐项确认约束未被违反。

  最根本的区别：缺陷链路的每个环节都有客观判据（能复现 / 
  不能复现），需求链路的判据是主观构建的（Acceptance 是人为定义的合格线）。这就
  是为什么需求链路更容易出现扯皮——不是实现不好，是验收标准没事先对齐。

❯ 下一步 是 实现报告的 设计帮我分析 

⏺ 实现报告的第一性原理分析

  起点：实现报告与修复报告的本质区别

  缺陷链路：缺陷报告 ──→ 修复报告 ──→ 验证报告
  需求链路：需求报告 ──→ 实现报告 ──→ 验收报告

  Q: 修复报告和实现报告都是"做完了一件事"的汇报，区别在哪？
  A: 修复是复原——把偏离的轨道拉回来。实现是创造——在空地上盖一栋楼。

  Q: 这个区别导致什么结构性差异？
  A: 三个层面：

  ┌────────────┬─────────────────────────┬──────────────────────────────────┐
  │            │        修复报告         │             实现报告             │
  ├────────────┼─────────────────────────┼──────────────────────────────────┤
  │ 解空间     │ 窄（消除已知根因，方案  │ 宽（满足同一需求可以有截然不同的 │
  │            │ 有限）                  │ 架构）                           │
  ├────────────┼─────────────────────────┼──────────────────────────────────┤
  │ 核心智力活 │ 诊断（找到根因）        │ 设计（选择方案）                 │
  │ 动         │                         │                                  │
  ├────────────┼─────────────────────────┼──────────────────────────────────┤
  │ 不完美的形 │ 副作用（改坏别的）      │ 缺口（没做完/没做好）            │
  │ 态         │                         │                                  │
  └────────────┴─────────────────────────┴──────────────────────────────────┘

  修复报告的灵魂是 Root Cause（为什么坏了），实现报告的灵魂是 Solution 
  Design（怎么造的）。
  一个是回溯性的（向后看），一个是构建性的（向前看）。

  ---
  柏拉图式追问

  Q: 我是验收者，你说"功能做好了"。第一个问题？
  A: "给我看看怎么用。"——我需要 Solution Design。

  Q: 看了方案，第二个问题？
  A: "为什么这样设计？"——我需要 Design Rationale。

  Q: 理解了思路，第三个问题？
  A: "具体改了哪些代码？"——我需要 Change Set。

  Q: 看了代码，第四个问题？
  A: "需求里的每一条都覆盖了吗？"——我需要 Traceability。

  Q: 都覆盖了？或者没覆盖？最后一个问题？
  A: "有什么已知的不完美？"——我需要 Known Gaps。

  闭合。

  五个不可约元素

                 实现报告
                    │
          ┌─────────┼─────────┐
          │         │         │
     Solution    Design    Change
      Design    Rationale    Set
     (怎么造的) (为什么这样造) (改了什么)
          │         │         │
          └─────────┼─────────┘
                    │
          ┌─────────┴─────────┐
          │                   │
     Traceability        Known Gaps
     (需求覆盖了吗)      (什么没做到)

  1. Solution Design（方案设计）—— "造了个什么东西"

  用户视角的完整方案：架构、流程、交互方式。

  Q: 修复报告没有这个元素，为什么实现报告需要？
  A: 
  因为修复的"方案"就是"消除根因"，几乎不需要解释长什么样——把错的改对就行。实现不
  同——你在创造一个之前不存在的东西，验收者脑中没有画面，你必须先让他看到实物。

  修复报告可以从 Root Cause 直接推出 Change（因为 X 坏了所以改了 Y）。
  实现报告不行——从 Why（"用户要能筛选数据"）推不出唯一的方案，可能是下拉框、标签
  、搜索、侧栏面板……Solution Design 是从无限解空间中选择的那个具体解。

  Q: Solution Design 应该包含什么？
  A: 三层：
  - 用户怎么用：操作流程、交互方式（从 Who 的视角描述）
  - 系统怎么工作：架构、数据流、模块关系
  - 关键界面/接口：UI 草图、API 契约、数据结构

  Q: 和需求报告的 What 有什么区别？
  A: What 是能力声明（"用户能批量删除过期记录"），Solution Design 
  是具体实现（"列表页顶部增加多选 + 批量操作栏，选中后弹确认弹窗，调用 DELETE 
  /api/records 批量接口"）。What 是合同条款，Solution Design 是施工图纸。

  2. Design Rationale（设计决策）—— "为什么这样造"

  选择此方案的理由，以及被排除的替代方案。

  Q: 修复报告也有 Rationale，实现报告的有什么不同？
  A: 体量和复杂度完全不同。
  - 修复的 Rationale：解空间小，通常是"方案 A 能根治，方案 B 
  只是止痛"——决策相对简单
  - 实现的 Design Rationale：解空间巨大，涉及架构选型、技术栈、性能 vs 
  复杂度、短期 vs 长期——每个决策都是一棵分叉树

  Q: 具体要回答什么？
  A: 对每个关键设计决策：
  - 选了什么：最终方案
  - 还考虑过什么：至少一个被排除的替代方案
  - 为什么选这个：选择依据（性能？可维护性？与现有架构一致性？工期约束？）
  - 已知妥协：这个方案不完美在哪里

  Q: 不写 Design Rationale 的代价？
  A: 两种后果：
  - 近期：验收者无法判断方案是否合理，只能看到"做了"，不知道"为什么这样做"——审查
  形同虚设
  - 远期：后来的维护者不理解设计意图，按自己的理解"优化"，破坏了设计中精心维护的
  某个不变量——没有 Rationale 的代码是等待退化的代码

  3. Change Set（变更集）—— "在代码层面改了什么"

  系统中新增和修改的具体内容。

  Q: 和修复报告的 Change 有什么结构性区别？
  A: 规模和性质不同。
  - 修复的 Change：通常是局部手术——改几个文件，逻辑集中
  - 实现的 Change 
  Set：通常是系统性工程——新文件、新模块、新接口、现有模块的扩展，散布在多个层次

  修复报告的 Change 可以用一两句话概括。实现报告的 Change Set 
  需要结构化组织——按模块、按层次、按功能分组，否则验收者淹没在 diff 中。

  Q: 应该包含什么？
  A: 
  - 新增了什么：新文件、新模块、新 API
  - 修改了什么：现有代码的变更及原因
  - 删除了什么：移除的代码及原因（如替换旧实现）
  - 配置变更：数据库 schema、环境变量、依赖更新

  4. Traceability（需求追溯）—— "每条需求都有着落吗"

  需求报告中的每个元素与实现的对应关系。

  Q: 修复报告没有这个元素，为什么实现报告需要？
  A: 修复报告的追溯是隐式的 1:1 映射——一个 Delta，一个 Root Cause，一个 
  Change，关系显然。

  实现报告面对的是多对多映射：
  - 一条 What 可能需要多处代码变更来实现
  - 一处变更可能同时服务于多条 What
  - 一条 Acceptance 标准可能依赖多个模块协作
  - 一条 Constraint 可能需要在多个地方分别满足

  没有显式追溯，验收者不知道从哪里验起。

  Q: Traceability 长什么样？
  A: 一张映射表：

  | 需求项           | 类型       | 实现位置              | 验证方式 |
  |------------------|------------|-----------------------|----------|
  | 批量删除过期记录 | What       | RecordList + BatchAPI | 功能测试 |
  | 删前确认弹窗     | What       | ConfirmDialog         | UI 测试  |
  | 操作留审计日志   | Constraint | AuditMiddleware       | 日志检查 |
  | 删除后列表刷新   | Acceptance | RecordList.onDelete   | E2E      |
  | 不影响未过期记录 | Acceptance | BatchAPI.filter       | 单元测试 |


  Q: 如果某条需求没有对应的实现呢？
  A: 那就是 Known Gap，必须显式声明。Traceability 
  的价值不仅是展示"做了什么"，更是暴露"没做什么"。

  5. Known Gaps（已知缺口）—— "什么没做到"

  已知的不完美：未实现的需求项、技术妥协、遗留问题。

  Q: 修复报告有 Blast Radius（波及范围），Known Gaps 与之对应吗？
  A: 视角不同。
  - Blast Radius 是无意的副作用——"修 A 可能不小心弄坏了 B"
  - Known Gaps 是有意的取舍——"知道 C 没做完，但决定先交付"

  Blast Radius 源于恐惧（怕弄坏），Known Gaps 源于诚实（承认不完美）。

  Q: 为什么需要显式声明？不声明会怎样？
  A: 不声明 Known Gaps 的后果：
  - 
  验收扯皮：验收者发现某个需求项没实现，不知道是"忘了"还是"故意的"——沟通成本暴增
  - 虚假通过：验收者没注意到缺口，放行了一个不完整的实现
  - 信任损耗：后来发现缺口时，"你为什么不早说"——本可避免的信任危机

  Known Gaps 是实现者的主动诚实声明。 缺口本身不可怕，隐瞒缺口才可怕。

  Q: 具体包含什么？
  A: 三类：
  - 未实现项：需求报告中明确提到但未实现的 
  What/Acceptance，以及原因（工期不够、技术阻塞、需进一步澄清）
  - 已知限制：实现了但有质量/性能/兼容性方面的已知不足
  - 技术债务：为了赶工期做的妥协，后续需要重构的部分

  ---
  修复报告 vs 实现报告：结构对比

  修复报告                         实现报告
  ────────                         ────────
  Root Cause (根因)      ←→       Solution Design (方案)
    回溯性："为什么坏了"             构建性："造了什么"

  Rationale (决策)       ←→       Design Rationale (设计决策)
    窄："为什么这样修"               宽："为什么这样设计"

  Change (变更)          ←→       Change Set (变更集)
    局部手术                        系统工程

  Blast Radius (波及)    ←→       Known Gaps (已知缺口)
    无意的副作用                     有意的取舍

  Verification (验证)    ←→       Traceability (需求追溯)
    1:1 映射                        多对多映射

  核心差异的根源：修复是在已知空间中操作（系统已存在，缺陷已定位），实现是在创造
  空间中操作（方案要设计，权衡要做出）。这让实现报告的每个元素都比修复报告的对应
  元素更开放、更复杂、更需要解释。

  ---
  链路中的位置：承上启下

  需求报告                 实现报告                  验收报告
  ────────                 ────────                  ────────
  Who (主体)      ──→    Solution Design 中的      ──→  场景走查
                          用户流程

  Why (动机)      ──→    Design Rationale 的       ──→  动机满足度
                          决策锚点

  What (能力)     ──→    Traceability 中的         ──→  能力逐项核对
                          需求覆盖映射

  Acceptance      ──→    Traceability 中的         ──→  验收清单 ✓/✗
                          验证方式

  Constraint      ──→    Traceability 中的         ──→  约束逐项确认
                          约束合规列

  实现报告是需求报告和验收报告之间的翻译层——把需求方的"我要什么"翻译成验收方可检
  验的"这里有什么"。

  ---
  一句话总结

  实现报告的柏拉图"理型"：造了个什么方案，为什么这样设计，代码层面改了什么，需求
  每条都有着落吗，以及什么没做到要坦白。

❯ 下一步 是 验收报告的 设计帮我分析  

⏺ 验收报告的第一性原理分析

  起点：验收报告与验证报告的本质区别

  缺陷链路：缺陷报告 ──→ 修复报告 ──→ 验证报告
  需求链路：需求报告 ──→ 实现报告 ──→ 验收报告

  Q: 两条链路的终点文档——验证报告和验收报告——看上去都是"审判书"，区别在哪？

  A: 审判的对象不同。

  ┌──────────┬─────────────────────────┬────────────────────────────────┐
  │          │        验证报告         │            验收报告            │
  ├──────────┼─────────────────────────┼────────────────────────────────┤
  │ 审判对象 │ 一个修复行为            │ 一个创造物                     │
  ├──────────┼─────────────────────────┼────────────────────────────────┤
  │ 核心问题 │ "缺陷消除了吗？"        │ "需求满足了吗？"               │
  ├──────────┼─────────────────────────┼────────────────────────────────┤
  │ 判据来源 │ 缺陷报告（已知的偏差）  │ 需求报告（主观构建的标准）     │
  ├──────────┼─────────────────────────┼────────────────────────────────┤
  │ 判据性质 │ 客观（偏差存在/不存在） │ 半主观（标准本身是人为定义的） │
  └──────────┴─────────────────────────┴────────────────────────────────┘

  Q: "半主观"是什么意思？
  A: 验证报告的判据是物理性的——缺陷要么复现要么不复现，没有商量余地。验收报告的
  判据——Acceptance 标准——是人写的契约，而契约有解读空间。

  "筛选后列表只显示匹配项" ← 这条标准看起来清晰，但：空列表算"匹配项"吗？异步加
  载中的瞬间闪烁算不算？模糊匹配还是精确匹配？

  验证报告裁定的是事实问题（缺陷在不在），验收报告裁定的是契约问题（实现符不符合
  约定）。 后者天然更容易产生分歧。

  Q: 这意味着验收报告需要额外解决什么问题？
  A: 验证报告只需要回答"是/否"。验收报告还需要处理灰色地带——标准写了但实现理解不
  同、标准没写但验收时觉得应该有、标准写了但实现发现不合理而调整了。

  验证报告是二元裁定（通过/不通过），验收报告是三方对账（需求方的意图 vs 
  实现方的交付 vs 验收方的判断）。

  ---
  柏拉图式追问

  Q: 我是决策者，你说"验收完了"。第一个问题？
  A: "需求里每条验收标准都过了吗？"——我需要 Criteria Verdict。

  Q: 标准都过了。第二个问题？
  A: "做出来的东西，用户真能用吗？"——我需要 Experience Validation。

  Q: 为什么？标准不是已经过了吗？
  A: 因为标准是离散的检查点，用户体验是连续的旅程。每个检查点都过了，但连起来走
  一遍可能不通顺。

  类比：考试每道题都对了（标准通过），但整篇论文读起来前后矛盾、逻辑跳跃（体验不
  通）。

  Q: 体验也验了。第三个问题？
  A: "实现方说的那些没做到的地方，影响大吗？"——我需要 Gap Assessment。

  Q: 评估了缺口。第四个问题？
  A: "对现有系统有没有副作用？"——我需要 Regression Result。

  Q: 最后？
  A: "综上，能不能合并？"——我需要 Verdict。

  闭合。

  五个不可约元素

                  验收报告
                     │
          ┌──────────┼──────────┐
          │          │          │
     Criteria    Experience    Gap
     Verdict    Validation   Assessment
    (标准过了吗) (用得顺吗)  (缺口要紧吗)
          │          │          │
          └──────────┼──────────┘
                     │
           ┌─────────┴─────────┐
           │                   │
       Regression           Verdict
       (旧的没坏吧)         (合不合并)

  1. Criteria Verdict（标准裁定）—— "验收标准逐项过了吗"

  逐条核对需求报告中的 Acceptance 标准。

  Q: 这和验证报告的 Reproduction Result 是什么关系？
  A: 结构同源，但复杂度不同。
  - Reproduction Result：一条路径，走一遍，过/不过。1:1
  - Criteria Verdict：N 条标准，每条独立判定。1:N

  验证报告验的是"一个缺陷消没消"，验收报告验的是"一组契约逐项满没满足"。

  Q: 逐条核对就够了吗？
  A: 对每条标准需要记录三项：
  - 结论：通过 / 不通过 / 部分通过
  - 证据：怎么验的，看到了什么（截图、日志、测试结果）
  - 偏差说明（如有）：不通过或部分通过时，实际行为与标准的具体差异

  Q: "部分通过"是什么？验证报告里没有这个概念。
  A: 这正是验收报告特有的灰色地带。例如：
  - 标准："筛选后列表刷新，状态保持"
  - 实际：筛选后列表刷新了（通过），但页码重置到第一页（不通过）
  - 这算通过还是不通过？部分通过——核心能力有了，边界行为缺失

  验证报告不需要这个概念，因为缺陷要么在要么不在。验收报告需要，因为需求的满足是
  一个光谱，不是一个开关。

  2. Experience Validation（体验验证）—— "连起来用得顺吗"

  以 Who（用户角色）的视角走完整个使用旅程。

  Q: 验证报告没有这个元素，为什么验收报告需要？
  A: 
  验证报告验的是点（一个缺陷点消失了），验收报告验的是面（一个完整功能可用了）。

  标准是离散的：✓ 能筛选、✓ 能排序、✓ 能导出。
  但用户不会按清单使用产品——他会筛选完排序，排序完导出，导出完再筛选。标准之间的
  衔接、流转、整体流畅度，不在任何一条标准里，但决定了功能是否真正可用。

  Q: 这不就是"用户测试"吗？
  A: 不完全。用户测试是方法，Experience Validation 是维度。具体包含：
  - Happy Path：标准场景完整走通
  - 流程衔接：步骤之间的过渡是否自然
  - 认知负荷：用户能不能不看说明就会用
  - 异常恢复：操作出错时能不能回到正轨

  Q: 如果 Criteria Verdict 全部通过但 Experience Validation 不通过，说明什么？
  A: 说明需求报告的 Acceptance 标准写漏了——覆盖了功能点但没覆盖体验连贯性。这是
  一个重要的反馈信号，应记录在验收报告中。

  Q: 验证报告里的 Boundary Validation（边界验证）和这里的 Experience Validation 
  是什么关系？
  A: 
  - Boundary 是纵深——同一个缺陷的不同触发变体（技术视角）
  - Experience 是广度——整个功能的端到端连贯性（用户视角）

  一个在找"漏洞"，一个在找"不顺"。

  3. Gap Assessment（缺口评估）—— "没做到的地方要紧吗"

  对实现报告中声明的 Known Gaps 进行影响评估。

  Q: 验证报告里没有这个元素，为什么验收报告需要？
  A: 因为修复报告追求完全消除缺陷——要么修好了，要么没修好，没有"部分修好可以接受
  "的概念。

  实现报告不同——几乎没有需求是 100% 完美交付的，总有 Known 
  Gaps。验收报告不是判断"有没有缺口"（肯定有），而是判断"缺口是否可接受"。

  Q: 怎么判断缺口可不可接受？
  A: 对每个 Known Gap 评估：
  - 影响面：影响多少用户、多少场景
  - 严重度：功能不可用 vs 体验瑕疵 vs 仅影响极端情况
  - 紧迫度：必须在合并前修复 / 可合并后跟进 / 可无限期搁置
  - 判定：阻塞合并 / 不阻塞（记为 follow-up）

  Q: 如果实现报告没声明 Known Gaps，但验收时发现了缺口呢？
  A: 这是两种不同性质的缺口：
  - 声明的缺口：实现者知道并主动告知——评估影响即可
  - 发现的缺口：实现者没意识到——这更像缺陷，需要回溯：是需求理解偏差？还是实现遗
  漏？

  声明的缺口走 Gap Assessment，未声明的缺口走回缺陷链路。

  4. Regression Result（回归验证）—— "现有功能没坏吧"

  新功能对既有系统的影响检查。

  Q: 这和验证报告的 Regression Result 一模一样？
  A: 几乎一样，但关注点略有差异：
  - 验证报告的回归：修了一个 bug，怕改坏附近的东西——范围由 Blast Radius 界定
  - 验收报告的回归：加了一个功能，怕影响全局的东西——范围更大

  新功能通常涉及更多模块、更多数据流，回归风险面更广。

  Q: 具体验什么？
  A: 三层：
  - 实现报告声明的影响区域：Change Set 触及的现有模块
  - 核心路径冒烟测试：系统最关键的 Happy Path
  - CI 自动化结果：全量测试套件

  5. Verdict（裁定）—— "合还是不合"

  基于以上四项证据的综合判决。

  Q: 和验证报告的 Verdict 有什么区别？
  A: 验证报告的 Verdict 
  相对简单——四项检查的逻辑与：全过则合，有一项不过则驳回，偶尔有条件通过。

  验收报告的 Verdict 更复杂，因为有灰色地带需要权衡：
  - 15 条标准过了 13 条，2 条部分通过——合不合？
  - 体验验证发现两处不顺畅但不影响核心功能——合不合？
  - 3 个 Known Gaps，1 个轻微 2 个中等——合不合？

  验证报告的 Verdict 是逻辑判断，验收报告的 Verdict 是综合判断。

  Q: Verdict 应该包含什么？
  A: 四部分：
  - 判决：合并 / 驳回 / 有条件合并
  - 证据摘要：四项验证的关键发现
  - 阻塞项（如有）：必须修复后才能合并的问题
  - Follow-up 清单：合并后需跟进的事项（可接受的 Gap、体验优化建议等）

  ---
  验证报告 vs 验收报告：结构对比

  验证报告                          验收报告
  ────────                          ────────
  Reproduction (复现验证)   ←→     Criteria Verdict (标准裁定)
    一条路径：过/不过                N 条标准：逐项判定
    二元结果                         光谱结果（通过/部分/不通过）

  Coherence (因果一致性)    ←→     Experience Validation (体验验证)
    根因-修复逻辑链成立吗             标准之间的体验连贯吗
    技术视角的深度检验                用户视角的广度检验

  Boundary (边界验证)       ←→     Gap Assessment (缺口评估)
    缺陷的变体还在吗                  已知缺口可接受吗
    找"漏洞"                         评"妥协"

  Regression (回归验证)     ←→     Regression (回归验证)
    修复波及范围                      新功能波及范围
    结构相同，范围不同

  Verdict (裁定)            ←→     Verdict (裁定)
    逻辑判断（全过则合）              综合判断（权衡灰色地带）

  ---
  与实现报告的镜像关系

  实现报告                           验收报告
  ────────                           ────────
  Solution Design (方案)    ──验──→  Experience Validation
    "怎么造的"                        "用起来顺吗"

  Design Rationale (决策)   ──验──→  Experience Validation
    "为什么这样造"                    "这个决策带来了好体验还是差体验"

  Change Set (变更集)       ──验──→  Regression
    "改了什么代码"                    "改的代码弄坏别的了吗"

  Traceability (需求追溯)   ──验──→  Criteria Verdict
    "每条需求映射到哪"                "每条需求真的满足了吗"

  Known Gaps (已知缺口)     ──验──→  Gap Assessment
    "什么没做到"                      "没做到的可接受吗"

  实现报告的每个声明，都在验收报告中被逐一质证。

⏺ Todo 记录的第一性原理分析

  起点：先看全景——记录层在哪里

  记录层（种子）          报告层（正式文档）              裁定层（终结文档）
  ─────────              ────────────                    ─────────
    todo   ──成长──→     需求报告 ──→ 实现报告 ──→ 验收报告
    issue  ──成长──→     缺陷报告 ──→ 修复报告 ──→ 验证报告
                         优化报告 ──→ ...

  Q: 记录层为什么存在？不能直接写报告吗？
  A: 因为想法和观察的保质期极短。你在代码审查中注意到"这个模块以后需要重构"，如
  果当场要写一份完整需求报告，摩擦太大，你会选择不记——然后永远忘记。

  记录层的存在理由：降低捕获摩擦，防止信息在"想到"和"处理"之间丢失。

  Q: 那 todo 和 issue 的区别是什么？
  A:

  ┌────────────┬────────────────────────────────┬──────────────────────────┐
  │            │              todo              │          issue           │
  ├────────────┼────────────────────────────────┼──────────────────────────┤
  │ 本质       │ 意图备忘                       │ 问题档案                 │
  ├────────────┼────────────────────────────────┼──────────────────────────┤
  │ 触发       │ "以后要做这个"                 │ "这里有个问题"           │
  ├────────────┼────────────────────────────────┼──────────────────────────┤
  │ 包含分析？ │ 否                             │ 是（涉及文件、修复方向） │
  ├────────────┼────────────────────────────────┼──────────────────────────┤
  │ 情绪       │ 主动（我决定要做）             │ 被动（我发现了问题）     │
  ├────────────┼────────────────────────────────┼──────────────────────────┤
  │ 演化方向   │ 需求报告 / 优化报告 / 直接完成 │ 缺陷报告                 │
  └────────────┴────────────────────────────────┴──────────────────────────┘

  Q: 用一句话区分？
  A: Todo 记录决定，Issue 记录发现。

  ---
  Todo 的本质是什么？

  Q: 一个 todo 最根本的功能？
  A: 把一个转瞬即逝的意图从大脑转移到持久存储，使得未来的自己（或他人）能还原当
  时的想法并行动。

  Q: 那本质上 todo 是什么？
  A: 一封写给未来的信。收信人是一周后的你，他已经忘了你现在在想什么。

  Q: 这封信要达成什么效果？
  A: 收信人读完后能够：
  1. 知道要做什么
  2. 知道为什么要做
  3. 知道从哪里开始

  做不到这三点中的任何一个，todo
  就会沦为——你的列表里那些写了半年再也看不懂的条目。

  ---
  柏拉图式追问：todo 的失败模式反推

  正向推导已经做了很多次，这次从失败模式反推——一个 todo 怎么会变成废纸？

  失败模式 1："Refactor auth"
  一周后打开：重构什么？auth 的哪个部分？当时为什么觉得要重构？
  → 缺少 Context（触发上下文）

  失败模式 2："处理一下上次讨论的那个问题"
  一周后打开：哪次讨论？什么问题？
  → 缺少 Intent（清晰的意图）

  失败模式 3："优化 UserService.getAll() 的 N+1 查询，当前用了 forEach 逐条查 
  relation，应该改用 JOIN，影响 Dashboard 和 Report 两个页面，预计需要同时改 
  schema..."
  这不是 todo——这是一份优化报告。写到这个程度的摩擦太大了，下次你不会记了。
  → 违反了轻量原则

  失败模式 4：一个完美的 todo，但两个月后拿起来，找不到代码在哪里
  → 缺少 Anchor（锚点）

  三种失败模式指向三个缺失。零冗余，零遗漏。

  ---
  三个不可约元素

            todo
             │
       ┌─────┼─────┐
       │     │     │
    Intent Context Anchor
    (做什么) (为什么) (从哪开始)

  为什么是三个而不是五个？因为 todo 是种子，不是树。种子只需要携带足够发芽的信息
  ——其余的在发芽时（升级为正式报告）再展开。

  1. Intent（意图）—— "做什么"

  用祈使句描述要完成的事情。

  Q: Intent 和需求报告的 What 有什么区别？
  A: 精度完全不同。
  - What（需求报告）："用户能够按类型筛选列表内容，支持多选，筛选状态持久化到 
  URL"
  - Intent（todo）："给列表加筛选功能"

  What 是经过分析的精确能力声明。Intent 是未经分析的原始意图——够你想起来就行。

  Q: Intent 要写多详细？
  A: 一个测试标准：一周后的你读到这句话，能否在 5 秒内知道要做什么。
  - "优化性能" ← 太模糊，5 秒后还是懵
  - "优化 Dashboard 页面首屏加载速度" ← 5 秒内清楚
  - "Dashboard 页面首屏加载需从 3.2s 降到 1s，主要瓶颈在 getAll 的 N+1 查询..." 
  ← 过度展开，这是优化报告

  2. Context（触发上下文）—— "为什么记这个"

  是什么促使你现在写下这个 todo。

  Q: 为什么 Intent 不够，还需要 Context？
  A: 因为 Intent 只说"做什么"，不说"为什么值得做"。一周后你看着"给列表加筛选功能
  "会想——为什么？现在不是能用的吗？是谁要的？是必须做的还是锦上添花？

  没有 Context 的 todo 会在优先级排序时变成黑箱——你无法判断它相对于其他 todo 
  有多重要，因为你忘了当初为什么觉得它重要。

  Q: Context 应该包含什么？
  A: 回答一个问题："此刻是什么让我觉得这件事需要做？"
  - "客户反馈列表数据太多找不到目标"
  - "代码审查时发现这个模块耦合度太高"
  - "和产品开会时提到的"
  - "部署后发现日志刷得太快"

  一句话，不超过两句。够还原触发场景即可。

  Q: Context 在 todo 升级为正式报告时起什么作用？
  A: Context 是 Why 的种子。 
  - todo 升级为需求报告 → Context 展开为 Why
  - todo 升级为优化报告 → Context 展开为 Metric + Baseline
  - todo 直接完成 → Context 在 commit message 中交代背景

  没有 Context 的 todo 
  升级时，你得重新调研"当初为什么要做这个"——信息已经丢失了。

  3. Anchor（锚点）—— "从哪里开始"

  足够让未来的自己找到切入点的线索。

  Q: 这在正式报告中对应什么？
  A: 
  - 缺陷报告的 Location + Path（在哪、怎么触发）
  - 需求报告的 Who（谁在什么场景下）

  Anchor 是这些元素的压缩版——不需要完整描述，只需要一个能让你快速定位到相关代码/
  页面/人的指针。

  Q: Anchor 长什么样？
  A: 形式不限，一两个关键指针即可：
  - 文件路径：src/services/UserService.ts
  - 页面路径：/dashboard
  - 关联人：产品经理 Lisa 的需求
  - 关联讨论：#channel-product 2月25日讨论
  - 关联 PR：PR #142 的 review 评论

  Anchor 不是文档，是地址。 告诉未来的你去哪里找更多信息。

  Q: 没有 Anchor 会怎样？
  A: Intent 和 Context 都有了，但你坐到电脑前不知道从哪下手。
  - "给列表加筛选功能"（Intent）
  - "客户反馈数据太多"（Context）
  - 然后呢？哪个列表？哪个文件？谁说的？去问谁？

  你开始在代码里搜索，在聊天记录里翻……Anchor 的缺失把一个 30 
  秒能启动的任务变成了 30 分钟的考古。

  ---
  为什么只有三个？不需要优先级/截止日期/标签吗？

  Q: 传统 todo 应用都有优先级、截止日期、标签，为什么这里没有？
  A: 因为那些是管理属性，不是本质要素。

  区分两件事：
  - 捕获：把想法从大脑转移到存储（Intent + Context + Anchor）
  - 管理：对已捕获的 todo 进行排序、筛选、调度（优先级、截止日期、标签）

  捕获是创造行为，管理是组织行为。 一个 todo 没有优先级仍然是一个有效的
  todo（以后排序就行），但没有 Intent 就不是一个 todo。

  本质要素只回答"这个 todo 是否可被理解和执行"，不回答"这个 todo 
  什么时候做、排第几"。

  ---
  Todo 的生命周期：从种子到归宿

                          ┌──→ 需求报告 ──→ 需求链路
                          │
    todo (种子) ──评估──→ ├──→ 优化报告 ──→ 优化链路
                          │
                          ├──→ 直接完成 ──→ commit
                          │
                          └──→ 废弃 ──→ 关闭

  Q: todo 怎么知道该走哪条路？
  A: 靠 Context 判断。 
  - Context 是"客户要一个新功能" → 需求报告
  - Context 是"这个查询太慢了" → 优化报告
  - Context 是"改个文案" → 直接完成
  - Context 是"当时想多了" → 废弃

  这就是为什么 Context 不可省略——它是 todo 的分拣依据。

⏺ Issue 记录的第一性原理分析

  起点：Issue 和 Todo 的根本分野

  Q: 都是记录层，都是种子，为什么需要两种？
  A: 因为人脑产生两种根本不同的信号：

  ┌──────────┬────────────────┬─────────────────┐
  │          │      Todo      │      Issue      │
  ├──────────┼────────────────┼─────────────────┤
  │ 信号类型 │ "我决定要做 X" │ "我发现 X 坏了" │
  ├──────────┼────────────────┼─────────────────┤
  │ 认知起源 │ 意志（主动）   │ 观察（被动）    │
  ├──────────┼────────────────┼─────────────────┤
  │ 指向     │ 未来的行动     │ 已存在的问题    │
  ├──────────┼────────────────┼─────────────────┤
  │ 包含判断 │ 否（纯意图）   │ 是（初步诊断）  │
  └──────────┴────────────────┴─────────────────┘

  Q: 为什么观察比意图需要更多信息？
  A: 因为意图是自洽的——"我想做 X"不需要证据。观察是可证伪的——"X
  坏了"需要证据支撑，否则可能是你搞错了。

  Todo 是主观宣言，不需要论证。Issue 是客观陈述，需要初步举证。

  Q: 那 Issue 和缺陷报告的区别呢？
  A: 精度和深度。

  issue（便签）           缺陷报告（正式文档）
  ──────────             ──────────────
  "我看到了什么"           期望值 vs 实际值（精确 Delta）
  "当时在做什么"           完整复现步骤（精确 Path）
  "大概在哪个模块"         具体到文件/函数（精确 Location）
  "我猜是因为..."         影响面评估（Impact）
  5 分钟写完               可能需要 1 小时

  Issue 是现场速写——趁观察还新鲜，用最小摩擦把关键信息固定下来。
  缺陷报告是精密检查报告——经过系统调研后的完整文档。

  ---
  核心问题：Issue 要防止什么信息丢失？

  Q: 发现一个 bug 的瞬间，你的大脑里有什么独特信息？
  A: 四样东西，且它们的保质期各不相同：

  1. 症状——"我看到了什么不对的"（保质期：数小时，记忆快速模糊化）
  2. 触发条件——"我当时在做什么操作"（保质期：极短，操作上下文转瞬即逝）
  3. 位置直觉——"大概跟哪个模块有关"（保质期：中等，但会被后续工作覆盖）
  4. 因果直觉——"我猜是因为..."（保质期：最短，这是最珍贵也最易消散的信息）

  Q: 为什么因果直觉最珍贵？
  A: 因为发现 bug 的瞬间，你的脑中同时持有用户操作上下文 + 系统行为上下文 + 代码
  结构记忆三层信息。这三层的交集产生了一个直觉性的判断："大概是这里出了问题"。

  五分钟后你去接杯水，回来这三层的交集就散了。一周后让另一个人来查，他需要从零重
  建这三层——Issue 的因果直觉字段可能为他节省数小时的调查时间。

  ---
  柏拉图式追问：从失败模式反推

  和 Todo 一样，从 Issue 的死亡方式反推它的必要器官——

  失败模式 1："登录有 bug"
  一周后：什么 bug？怎么触发的？什么浏览器？什么账号？
  → 缺少 Trigger（触发条件），无法复现

  失败模式 2："点击保存按钮后页面白屏，控制台报 TypeError: Cannot read property 
  'id' of null"
  信息足够吗？可以复现。但修复者打开代码，保存按钮背后有 6 个 API 调用、4
  层组件嵌套——从哪开始查？
  → 缺少 Locale（涉及范围），复现了但定位不了

  失败模式 3：完整的症状 + 触发条件 + 位置，但没有任何判断
  修复者能复现、能定位，但他面对的是一个黑箱——为什么会出这个错？发现者当时有没有
  什么线索？
  → 缺少 Hypothesis（初步判断），丢失了发现者的第一手直觉

  失败模式 4：有触发条件、有位置、有假设，但症状描述模糊——"表现不正常"
  修复者照着步骤操作了一遍，看到了一些输出——但不确定哪个是"不正常"。
  → 缺少清晰的 Symptom（症状），不知道该关注什么

  四种失败模式，四个缺失，零冗余。

  ---
  四个不可约元素

              issue
                │
         ┌──────┼──────┐
         │      │      │
     Symptom  Trigger  Locale
     (看到什么) (怎么触发) (在哪一带)
         │      │      │
         └──────┼──────┘
                │
            Hypothesis
            (猜是什么原因)

  为什么是四个而不是三个？因为 Issue 比 Todo 多了一层——初步分析。Todo
  是纯捕获（三元素），Issue 是捕获 + 分析（三元素 + 一元素）。

  1. Symptom（症状）—— "看到了什么不对"

  观察到的异常现象。

  Q: Symptom 和缺陷报告的 Delta 有什么区别？
  A: 精度层级不同。
  - Symptom（Issue）："保存后数据丢了"
  - Delta（缺陷报告）："点击保存按钮，期望表单数据持久化到数据库，实际刷新后 
  name 字段恢复为空字符串，其他字段正常"

  Symptom 是印象，Delta 是精确测量。Issue 只需要印象——够识别问题就行。

  Q: Symptom 应该写多详细？
  A: 测试标准：另一个开发者读完后，能区分这个问题和其他问题。
  - "有 bug" ← 无法区分任何问题
  - "保存后数据丢了" ← 能区分，但如果有多个保存相关 bug 会混淆
  - "Agent 配置页保存后 name 字段被清空" ← 能精确区分

  2. Trigger（触发条件）—— "当时在做什么"

  触发症状的操作和环境。

  Q: Trigger 和缺陷报告的 Path 有什么区别？
  A: Path 是可复现的精确步骤序列。Trigger 是粗略的操作描述。
  - Trigger（Issue）："编辑 Agent 名称，切到另一个 tab 再切回来，然后保存"
  - Path（缺陷报告）："1. 打开 /agents/xxx/build 2. 修改 name 字段为 'Test' 3. 
  点击 Skills tab 4. 点击 General tab 5. 点击 Save 按钮 6. 刷新页面 7. 观察 name
   字段为空"

  Trigger 是故事（"我当时大概在做什么"），Path 
  是剧本（"按这个步骤一定能复现"）。

  Q: Trigger 不精确，复现不了怎么办？
  A: 这是正常的。Issue 的 Trigger 可能不足以 100% 复现——这恰好是 Issue 
  升级为缺陷报告时需要补充的部分。Issue 的 Trigger 
  只需要提供足够的线索让调查者知道大致方向。

  Q: 环境信息（浏览器、操作系统、账号状态）算 Trigger 的一部分吗？
  A: 是。Trigger 
  回答的是广义的"在什么条件下发生"——操作是条件，环境也是条件。但在 Issue 
  层级，只记录你认为相关的环境信息，不需要穷举。

  3. Locale（涉及范围）—— "大概在哪一带"

  问题可能涉及的代码区域。

  Q: Locale 和缺陷报告的 Location 有什么区别？
  A: 精度和确定性。
  - Locale（Issue）："大概在表单提交或状态管理那块"——猜测，可能指向多个模块
  - Location（缺陷报告）："src/components/AgentForm.tsx:142 的 onSubmit 
  handler"——定位，精确到行

  Locale 是搜索范围，Location 是精确坐标。

  Q: 如果完全不知道代码在哪呢？
  A: 那就写功能区域：
  - "Agent 配置页面"（页面级）
  - "表单保存流程"（功能级）
  - "数据持久化"（系统级）

  任何粒度的定位都比没有好。Locale 的下限是功能描述，上限是文件路径。

  Q: Locale 和 Todo 的 Anchor 有什么区别？
  A: 指向不同。
  - Anchor（Todo）："从哪里开始做"——指向行动的起点
  - Locale（Issue）："问题可能在哪"——指向调查的范围

  Anchor 是路标（往这走），Locale 是搜索区（在这找）。

  4. Hypothesis（初步判断）—— "猜是什么原因"

  发现者基于当时上下文的因果推测。

  Q: 这个元素在缺陷报告里没有，在修复报告里才有（Root Cause）。为什么 Issue 
  要提前记？
  A: 因为时效性。

  修复报告的 Root Cause 是经过系统调查后确认的——修复者可以花几个小时深入研究。
  Issue 的 Hypothesis 是发现者在发现瞬间的直觉判断——这个直觉的保质期极短。

  发现者当时可能刚好在看相关代码、刚好理解数据流、刚好注意到一个可疑的 race 
  condition——五分钟后这个认知状态就散了。Hypothesis 
  是对这个转瞬即逝的认知状态的快照。

  Q: Hypothesis 可以是错的吗？
  A: 当然可以，而且经常是错的。 这没关系。Hypothesis 
  的价值不在于正确性，在于方向性。
  - 正确的 Hypothesis → 修复者直接沿着方向走，节省大量时间
  - 错误的 Hypothesis → 修复者排除一个方向，也有价值（知道这条路不通）
  - 没有 Hypothesis → 修复者面对一个完全的黑箱，从零开始

  一个错误的假设比没有假设强十倍。

  Q: Hypothesis 和缺陷报告的 Impact 为什么不能并存？
  A: 不是不能，是时机不同。
  - 发现 bug 的瞬间：你有因果直觉（Hypothesis），但没做过影响面调查（Impact）
  - 正式写缺陷报告时：你经过调查，确认了影响面（Impact），因果直觉已经被系统分析
  取代

  Issue 用 Hypothesis 替代 Impact，因为在记录时刻，你有前者但没有后者。 Impact 
  是缺陷报告阶段才有条件产出的信息。

  Q: Hypothesis 应该写什么？
  A: 三个可选维度，有什么写什么：
  - 猜原因："可能是表单 reset 时序问题，切 tab 触发了意外 reset"
  - 猜位置："怀疑在 useFormContext 的 cleanup 逻辑里"
  - 猜修复方向："可能需要在 tab 切换时保存草稿状态"

  ---
  Todo 与 Issue 的结构对比

  Todo (三元素)                 Issue (四元素)
  ────────────                 ─────────────
  Intent   (做什么)      ←→    Symptom    (看到什么)
    主观意图                     客观观察

  Context  (为什么记)    ←→    Trigger    (怎么触发)
    触发场景                     触发条件

  Anchor   (从哪开始)    ←→    Locale     (在哪一带)
    行动起点                     搜索范围

      ∅                  ←→    Hypothesis (猜什么原因)
    不需要分析                    需要初步分析

  Issue = Todo 的三层骨架 + 一层分析。 三层骨架回答同样的基本问题（什么事、什么
  触发、哪里相关），但从"意图视角"转为"观察视角"。第四层 Hypothesis 是 Issue 
  独有的——因为问题需要解释，意图不需要。

  ---
  Issue 的生命周期：从种子到归宿

                       ┌──→ 缺陷报告 ──→ 缺陷链路（大多数情况）
                       │
  issue (种子) ──评估──→├──→ 优化报告 ──→ 优化链路（不是 bug 而是性能/体验问题）
                       │
                       ├──→ todo ──→ 降级为待办（不是 bug，是 feature request）
                       │
                       └──→ 关闭 ──→ 无法复现 / 不是 bug / 已被其他修复覆盖

  Q: Issue 怎么知道该走哪条路？
  A: 靠 Symptom + Hypothesis 共同判断：
  - Symptom 是功能错误 + Hypothesis 指向代码缺陷 → 缺陷报告
  - Symptom 是"太慢" + Hypothesis 指向性能瓶颈 → 优化报告
  - Symptom 是"不好用"但不是错 + Hypothesis 指向功能缺失 → 降级为 todo
  - Symptom 无法复现 + Hypothesis 站不住 → 关闭

  ---
  记录层全景：Todo + Issue 完整对照

  ┌──────────────┬──────────────┬──────────────────────┐
  │     维度     │     Todo     │        Issue         │
  ├──────────────┼──────────────┼──────────────────────┤
  │ 本质         │ 意图备忘     │ 问题档案             │
  ├──────────────┼──────────────┼──────────────────────┤
  │ 信号         │ "我决定要做" │ "我发现坏了"         │
  ├──────────────┼──────────────┼──────────────────────┤
  │ 元素数       │ 3            │ 4                    │
  ├──────────────┼──────────────┼──────────────────────┤
  │ 多出的元素   │ —            │ Hypothesis（分析层） │
  ├──────────────┼──────────────┼──────────────────────┤
  │ 摩擦度       │ ~30 秒       │ ~5 分钟              │
  ├──────────────┼──────────────┼──────────────────────┤
  │ 主要演化方向 │ 需求报告     │ 缺陷报告             │
  ├──────────────┼──────────────┼──────────────────────┤
  │ 类比         │ 便签纸       │ 急诊初诊单           │
  ├──────────────┼──────────────┼──────────────────────┤
  │ 写给谁       │ 未来的自己   │ 未来的调查者         │
  └──────────────┴──────────────┴──────────────────────┘

  Todo 是写给执行者的（"去做这件事"），Issue 
  是写给调查者的（"去查这个问题"）。受众不同，所需信息结构不同。

  ---
  从记录层到报告层的信息膨胀

  记录层              报告层                信息膨胀
  ──────              ──────                ────────
  Symptom  ──展开──→  Delta              印象 → 精确测量
  Trigger  ──展开──→  Path               故事 → 精确剧本
  Locale   ──展开──→  Location           搜索范围 → 精确坐标
  Hypothesis ──迁移──→ (修复报告 Root Cause)  直觉 → 确认的因果
      ∅     ──新增──→  Impact             记录时没有 → 调查后补充

  Issue 到缺陷报告的升级，本质是把四个"大概"变成四个"精确"，再补上一个"影响面"。
   Hypothesis 不会留在缺陷报告中——它要么被确认为 Root Cause 
  写入修复报告，要么被推翻。

  ---
  一句话总结

  Issue 的柏拉图"理型"：趁记忆还热，记下看到了什么、怎么触发的、大概在哪、以及猜
  是为什么——一张急诊初诊单，给未来的调查者一个起跑点而非一个黑箱。

⏺ 经验报告的第一性原理分析

  起点：经验报告在系统中的位置

  先看它和所有其他报告的根本区别——

  Q: 
  之前所有报告都在链路中：缺陷→修复→验证，需求→实现→验收。经验报告在哪条链路里？
  A: 哪条都不在。 它不是链路的一环，它是链路的副产品。

  缺陷链路:  缺陷 → 修复 → 验证 ──┐
                                   ├──→ 经验报告 ──→ 项目指令
  需求链路:  需求 → 实现 → 验收 ──┘         ↑
                                       会话记录

  Q: 其他报告描述的是什么？
  A: 描述的是任务对象——系统的缺陷、系统的需求、系统的实现。

  Q: 经验报告描述的是什么？
  A: 描述的是操作者的认知修正——"我以为是这样，结果是那样"。

  所有其他报告：系统出了问题 → 修复系统。
  经验报告：心智模型出了问题 → 修复认知。

  Q: 那经验报告的本质是什么？
  A: 一份心智模型的缺陷报告。 系统没有 bug，是操作者对系统的理解有 bug。

  ---
  关键洞察：经验报告 = 心智模型的缺陷报告

  把这个类比展开：

  ┌──────────┬─────────────────┬─────────────────────────┐
  │          │    缺陷报告     │        经验报告         │
  ├──────────┼─────────────────┼─────────────────────────┤
  │ 什么坏了 │ 系统行为        │ 操作者的心智模型        │
  ├──────────┼─────────────────┼─────────────────────────┤
  │ 偏差     │ 系统行为 ≠ 规格 │ 心智模型 ≠ 系统实际     │
  ├──────────┼─────────────────┼─────────────────────────┤
  │ 修复对象 │ 代码            │ 项目指令 / CLAUDE.md    │
  ├──────────┼─────────────────┼─────────────────────────┤
  │ 修复方式 │ 改代码          │ 写规则                  │
  ├──────────┼─────────────────┼─────────────────────────┤
  │ 受益者   │ 用户            │ 未来的 Claude Code 会话 │
  └──────────┴─────────────────┴─────────────────────────┘

  你的例子完美印证了这个结构：
  - 心智模型："点击 Agent 卡片 → 进入配置页"
  - 系统实际："点击 Agent 卡片 → 进入聊天页"
  - 系统没有 bug。是心智模型需要修正。
  - 修复：在项目指令中写入"导航到配置页需用三点菜单→构建，或直接 URL"

  ---
  经验报告的独特挑战

  Q: 为什么不能直接在每次会话后手动更新 CLAUDE.md？
  A: 三个问题：

  1. 分散性：经验散落在整个会话的不同位置——第 3 轮对话踩了一个坑，第 15
  轮又踩了一个，第 28 轮发现了一个好用的技巧。不提取就丢失。
  2. 隐蔽性：很多经验不是显式的"我犯了错"，而是隐式的"我多试了三次才找到正确方法
  "——操作者自己可能没意识到这是一条值得记录的经验。
  3. 格式差异：会话记录是叙事体（"我试了 A，不行，然后试了
  B，还不行，最后发现要用 C"），项目指令需要的是规则体（"做 X 时用 C，不要用 A
  或 B"）。

  经验报告的核心功能：从叙事体的会话记录中提取规则体的可复用知识。

  ---
  柏拉图式追问：什么构成一条完整的经验？

  用你的例子走一遍——

  Q: 假设未来的 Claude Code 会话要做 Playwright 自动化，它需要什么？
  A: 首先它得知道什么时候这条经验适用。

  Q: 什么时候？
  A: "当你需要在 Playwright 中导航到 Agent 配置页面时"——Scene（场景）。

  Q: 知道了场景，然后呢？
  A: 它得知道不要做什么——因为它的第一反应一定是那个"自然但错误"的做法。

  Q: 为什么一定是错的？
  A: 因为 AI 和人一样有默认假设。看到卡片列表，默认假设"点击卡片 =
  进入详情"——这是交互设计的普遍模式，99%
  的应用都是这样。陷阱之所以是陷阱，正因为它符合直觉。 ——这就是
  Pitfall（陷阱）。

  Q: 知道了不要做什么，还需要什么？
  A: 需要知道实际发生了什么——"点击卡片实际上进入聊天页面"——Reality（实际行为）。

  Q: 知道了陷阱和现实，够了吗？
  A: 不够。还需要应该怎么做——"用三点菜单→构建，或 URL
  /agents/xxx/build"——Rule（规则）。

  Q: 有了 Rule 就够了？直接背规则不行吗？
  A: 不行。规则没有解释就是魔法数字——未来的 AI
  不知道这条规则的适用边界。加了一个新的导航入口怎么办？UI
  改版了怎么办？需要为什么——"因为应用是 chat-first
  设计，卡片的主要动作是开始对话"——Mechanism（机理）。

  Q: 再追问？
  A: 闭合。

  ---
  五个不可约元素（每条经验的单元结构）

             经验条目
                │
         ┌──────┼──────┐
         │      │      │
      Scene  Pitfall  Reality
     (什么时候) (直觉做法) (实际情况)
         │      │      │
         └──────┼──────┘
                │
          ┌─────┴─────┐
          │           │
        Rule      Mechanism
       (正确做法)   (为什么)

  1. Scene（场景）—— "什么情况下会遇到"

  触发这条经验的操作场景。

  Q: 为什么需要 Scene？直接写 Rule 不行吗？
  A: 因为 Rule 无条件适用就变成了全局规则。"导航用 URL 
  而不是点击"——什么时候？所有页面都这样？还是只有 Agent 配置页？

  Scene 是 Rule 的作用域。 没有 Scene 的 Rule 
  要么过度泛化（到处适用→到处限制），要么无法匹配（未来的 AI 
  不知道什么时候该调用这条规则）。

  Q: Scene 怎么写？
  A: 写触发条件，不写过程叙事：
  - "在 Playwright E2E 测试中导航到 Agent 配置（Build）页面时"
  - "在 Monaco 编辑器中填写代码内容时"
  - "等待 Eval Run 完成并验证结果时"

  2. Pitfall（陷阱）—— "自然但错误的做法"

  未经训练的 AI 会本能尝试的方法。

  Q: 为什么要记录错误做法？只记正确做法不行吗？
  A: 因为 AI 的"默认行为"是可预测的。看到卡片列表就会点卡片，看到输入框就会用 
  .fill()，看到按钮文本就会 getByRole('button', { name })。

  Pitfall 是未来 AI 的"第一反应"。 如果你不提前警告它这个第一反应是错的，它会先
  浪费一轮尝试、失败、再寻找替代——或者更糟，它以为成功了但实际到了错误的页面。

  Q: Pitfall 和缺陷报告的 Delta 有什么结构性区别？
  A: 
  - Delta："系统做了 B，但应该做 A"——系统的问题
  - Pitfall："我以为应该做 X，但 X 会导致错误结果"——认知的问题

  Delta 指控系统，Pitfall 修正自己。

  3. Reality（实际行为）—— "系统到底怎么工作的"

  系统的真实行为，与 Pitfall 中的预期形成对比。

  Q: 这不就是 Pitfall 的反面吗？能合并吗？
  A: 不能。它们回答不同的问题：
  - Pitfall："我以为点击卡片去配置页"——描述的是错误的心智模型
  - Reality："点击卡片实际去聊天页"——描述的是系统的真实行为

  合并成"点击卡片不是去配置页而是去聊天页"——可以，但丢失了一层信息：为什么有人会
  搞错（Pitfall 解释了错误的合理性）。保留 Pitfall 有助于未来的 AI 
  理解"这个错误我也会犯"→ 提高警惕。

  Q: Reality 需要多详细？
  A: 描述可观察的行为，一句话：
  - "点击 Agent 卡片进入的是 /agents/xxx/chat 聊天页面"
  - ".fill() 对 Monaco 编辑器无效，内容不会被写入 model"
  - "getByRole('button', { name: 'Import' }) 会匹配到 sidebar 中同名按钮"

  4. Rule（规则）—— "正确的做法是什么"

  可直接写入项目指令的操作规则。

  Q: Rule 和 Reality 的区别是什么？Reality 不就暗示了该怎么做吗？
  A: Reality 说的是"世界是怎样的"，Rule 说的是"你该怎么做"。
  - Reality："Monaco 不响应标准 DOM 输入事件"
  - Rule："用 page.evaluate(() => monaco.editor.getModels()[i].setValue(code)) 
  写入内容"

  Reality 是描述性的（is），Rule 是规定性的（ought）。AI 
  需要的不是理解世界（它可以推导），而是直接可执行的指令。

  Q: Rule 的格式有什么要求？
  A: 必须满足一个标准：可以直接复制粘贴到 CLAUDE.md 中作为项目规则。
  - 祈使句
  - 具体到操作级别
  - 包含代码片段（如适用）
  - 不含叙事（"当时我试了..."）

  Q: Rule 可以有多条吗？
  A: 可以。一个 Scene 可能有一条主 Rule + 一条备选 Rule：
  - 主 Rule："点击三点菜单 → 构建，通过 data-testid 定位菜单项"
  - 备选 Rule："或直接导航到 /agents/${id}/build"

  5. Mechanism（机理）—— "为什么是这样"

  系统行为背后的设计原因。

  Q: 有了 Rule 为什么还要 Mechanism？AI 照做不就行了？
  A: 三个原因：

  a) 泛化能力：Rule 是具体的，Mechanism 是原理性的。
  - Rule："Agent 卡片点击进聊天，用菜单进配置"
  - Mechanism："应用是 chat-first 设计，所有资源的主动作都是开始对话"
  - 未来遇到 Dataset 卡片、Wiki 卡片时，AI 可以从 Mechanism 
  推导出同样的规则，而不需要每种资源单独记一条

  b) 失效判断：Mechanism 让 AI 能判断规则是否过时。
  - 如果代码重构后卡片改为直接进配置页，Mechanism 提供的 "chat-first" 
  理由不再成立，AI 可以质疑规则的有效性
  - 没有 Mechanism，AI 只能盲目遵循可能已过时的规则

  c) 冲突解决：当两条 Rule 冲突时，Mechanism 提供仲裁依据。

  ---
  经验报告 vs 缺陷报告：结构对照

  缺陷报告（系统的缺陷）           经验报告（心智模型的缺陷）
  ──────────────────              ──────────────────────
  Delta     (期望 vs 实际)   ←→   Pitfall + Reality (以为 vs 实际)
  Path      (怎么触发)       ←→   Scene (什么场景下)
  Location  (在哪)           ←→   Rule 中隐含 (操作哪个元素)
  Impact    (多严重)         ←→   Mechanism (为什么会这样)

  修复方式:  改代码              修复方式:  改项目指令
  验证方式:  缺陷不再复现         验证方式:  未来会话不再踩坑

  报告层级结构

  单条经验是条目，经验报告是条目的结构化集合：

  经验报告
  ├── Source（溯源）
  │   ├── 工作区 / 任务名
  │   ├── 会话时间范围
  │   └── 关联报告（缺陷报告 / 实现报告 / ...）
  │
  ├── 经验条目 1
  │   ├── Scene: "Playwright 中导航到 Agent 配置页"
  │   ├── Pitfall: "点击 Agent 卡片"
  │   ├── Reality: "卡片进入聊天页 /chat"
  │   ├── Rule: "用三点菜单→构建，或直接 URL /build"
  │   └── Mechanism: "chat-first 设计，卡片主动作是对话"
  │
  ├── 经验条目 2
  │   ├── Scene: "E2E 中填写 Monaco 编辑器内容"
  │   ├── Pitfall: "用 .fill() 或 .type()"
  │   ├── Reality: "Monaco 不响应标准 DOM 事件"
  │   ├── Rule: "用 page.evaluate + monaco.editor.getModels().setValue()"
  │   └── Mechanism: "Monaco 自有输入系统，绕过 DOM 事件"
  │
  ├── 经验条目 N
  │   └── ...
  │
  └── Instruction Patch（指令补丁）
      └── 可直接合入 CLAUDE.md 的规则集

  Q: 为什么要有 Instruction Patch？
  A: 因为经验报告的终极目的不是被阅读，而是被执行——转化为项目指令。Instruction 
  Patch 是从所有条目的 Rule 中提炼的、可直接写入 CLAUDE.md 
  的格式化规则集。报告是过程文档，Patch 是交付物。

  ---
  第一性追问：消费管道长什么样？

  Q: 经验报告生成了，然后呢？
  A: 不能直接用。里面是原始经验条目——混杂着导航经验、诊断经验、修复经验。需要先
  分拣。

  Q: 分拣后呢？
  A:
  分拣后需要转译——经验条目的五元素格式是给人理解的，技能提示词需要的是可执行的 
  SOP 规则。

  Q: 转译后呢？
  A: 转译后需要合并——目标文件已有内容，新规则不能覆盖旧规则，要插入到正确的位置
  ，且不产生冲突或重复。

  所以消费管道是：

  提取 → 路由 → 转译 → 合并

  四步。逐步分析——

  1. 提取（从会话记录中识别经验）

  Q: 会话记录里什么信号代表一条经验？
  A: 五种模式：

  模式 1 - 重试模式（最常见）
  做 A → 失败 → 做 B → 失败 → 做 C → 成功
  经验：Scene 下别做 A/B，直接做 C

  模式 2 - 惊讶模式
  预期 X → 实际 Y → "原来是这样"
  经验：X 是陷阱，实际是 Y

  模式 3 - 绕路模式
  标准做法行不通 → 找到非显然的解法
  经验：这个场景需要特殊处理

  模式 4 - 确认模式
  假设 → 验证成功
  经验：这个方法确实有效（正面经验）

  模式 5 - 环境模式
  配置/环境问题 → 解决
  经验：环境搭建注意事项

  2. 路由（决定每条经验去哪个文件）

  Q: 怎么判断一条经验属于哪个技能？
  A: 看 Scene 的领域：

  ┌─────────────────────────────┬────────────────────────┐
  │         Scene 领域          │        目标文件        │
  ├─────────────────────────────┼────────────────────────┤
  │ 项目导航、UI 结构、页面路由 │ CLAUDE.md              │
  ├─────────────────────────────┼────────────────────────┤
  │ Bug 定位、日志分析、复现    │ diagnose 技能提示词    │
  ├─────────────────────────────┼────────────────────────┤
  │ 代码修改、修复策略          │ fix 技能提示词         │
  ├─────────────────────────────┼────────────────────────┤
  │ 验证方法、测试执行          │ verify 技能提示词      │
  ├─────────────────────────────┼────────────────────────┤
  │ Playwright/E2E 操作         │ CLAUDE.md E2E 测试章节 │
  ├─────────────────────────────┼────────────────────────┤
  │ 需求理解、澄清技巧          │ clarify-req 技能提示词 │
  ├─────────────────────────────┼────────────────────────┤
  │ 跨领域/通用                 │ CLAUDE.md              │
  └─────────────────────────────┴────────────────────────┘

  3. 转译（从五元素 → SOP 规则）

  Q: 经验条目和 SOP 规则有什么格式差异？

  【经验条目格式——给人理解的】
  Scene: 在 Playwright 中导航到 Agent 配置页
  Pitfall: 点击 Agent 卡片
  Reality: 卡片进入聊天页 /chat
  Rule: 用三点菜单→构建，或直接 URL /build
  Mechanism: chat-first 设计

  【SOP 规则格式——给 AI 执行的】
  - **导航到 Agent 配置页**：不要点击 Agent 卡片（进入的是聊天页），
    应通过三点菜单 →「构建」进入，或直接导航到 `/agents/${id}/build`

  转译的本质：从叙事结构（五个字段）压缩为规则结构（条件→行动，一两句话）。

  4. 合并（插入到目标文件的正确位置）

  Q: 新规则插入到文件的哪里？
  A: 看目标文件的现有结构：
  - CLAUDE.md 有章节（### E2E 测试、### UI 等）→ 按章节匹配
  - 技能提示词有步骤/阶段 → 按阶段匹配
  - 找不到匹配位置 → 新增章节

  ---
  技能设计：经验提取技能的提示词结构

  这个技能和其他技能有一个根本区别——

  Q: diagnose 读缺陷报告，fix 读缺陷报告执行修复，verify 
  读修复报告执行验证。experience 读什么？
  A: 读会话记录本身——它是唯一一个以对话过程而非任务文档作为输入的技能。

  Q: 这带来什么特殊挑战？
  A: 会话记录是噪声极高的信号源。一段 50 轮的会话里，可能只有 3-5
  个值得提取的经验，其余都是常规操作。技能的核心能力是从噪声中识别信号。

  提示词骨架

  # 经验提取（experience）

  ## 你是什么
  你是一个元认知提取器。你的工作不是完成任务，而是审视
  任务完成的过程，从中提取可复用的操作经验。

  ## 输入
  1. 当前工作区的会话记录（{conversation_path}）
  2. 当前工作区的报告文件（缺陷/修复/验证/实现/验收）
  3. 现有项目指令（CLAUDE.md）
  4. 现有技能提示词（{skills_dir}/*.md）

  ## 提取：识别学习时刻

  逐轮扫描会话记录，识别以下五种信号：

  ### 信号 1：重试模式
  特征：同一目标连续尝试多种方法
  标志词/模式：工具调用失败 → 换方法 → 成功
  提取：失败的方法 = Pitfall，成功的方法 = Rule

  ### 信号 2：惊讶模式
  特征：预期行为与实际行为不符
  标志词/模式："原来"、"实际上"、"不是...而是"、
             预期 A 但工具返回 B
  提取：预期 = Pitfall，实际 = Reality

  ### 信号 3：绕路模式
  特征：标准方法无效，使用非显然方案
  标志词/模式：常规 API 不可用、需要 workaround、
             "只能通过...来实现"
  提取：标准方法 = Pitfall，绕路方案 = Rule

  ### 信号 4：确认模式
  特征：假设被验证有效
  标志词/模式：明确的方法论发现，可能被其他会话复用
  提取：方法 = Rule（正面经验，无 Pitfall）

  ### 信号 5：环境模式
  特征：配置/环境/工具链的非显然行为
  标志词/模式：环境报错 → 调整配置 → 解决
  提取：默认配置 = Pitfall，正确配置 = Rule

  ## 结构化：五元素格式

  每条提取的经验按以下结构输出：

  ```yaml
  - scene: "在什么场景下"     # 触发条件，用"当...时"句式
    pitfall: "直觉做法"       # 自然但错误/低效的方法，可空（确认模式）
    reality: "实际行为"       # 系统真实表现
    rule: "正确做法"          # 祈使句，可执行的指令
    mechanism: "底层原因"     # 为什么，一句话
    target: "目标文件"        # 路由到哪个文件

  路由：确定目标文件

  根据 scene 的领域决定 target：

  ┌──────────────────────────────────┬───────────────────────┐
  │            scene 涉及            │        target         │
  ├──────────────────────────────────┼───────────────────────┤
  │ 项目结构/导航/UI 行为            │ CLAUDE.md             │
  ├──────────────────────────────────┼───────────────────────┤
  │ 缺陷诊断/复现/日志分析           │ skills/diagnose.md    │
  ├──────────────────────────────────┼───────────────────────┤
  │ 代码修复/修改策略                │ skills/fix.md         │
  ├──────────────────────────────────┼───────────────────────┤
  │ 验证/测试/回归                   │ skills/verify.md      │
  ├──────────────────────────────────┼───────────────────────┤
  │ E2E/Playwright 操作              │ CLAUDE.md → E2E 章节  │
  ├──────────────────────────────────┼───────────────────────┤
  │ 需求理解/澄清                    │ skills/clarify-req.md │
  ├──────────────────────────────────┼───────────────────────┤
  │ 实现/架构决策                    │ skills/implement.md   │
  ├──────────────────────────────────┼───────────────────────┤
  │ 特定技术栈（Monaco/Drizzle/...） │ CLAUDE.md → 对应章节  │
  └──────────────────────────────────┴───────────────────────┘

  转译：生成规则文本

  将五元素条目转译为 SOP 规则格式：

  有 Pitfall 时：
    "- {scene 关键词}：不要{pitfall}（{reality}），
     应{rule}"

  无 Pitfall 时（确认模式）：
    "- {scene 关键词}：{rule}（{mechanism}）"

  去重：对比现有规则

  读取每个 target 文件，检查是否已存在语义相同的规则：
  - 已存在且一致 → 跳过
  - 已存在但不完整 → 输出更新补丁
  - 不存在 → 输出新增补丁

  输出

  1. 经验报告（experience-report.md）

  完整的五元素条目列表，按 target 分组

  2. 指令补丁（分文件输出）

  每个受影响的 target 文件生成一个补丁块：

  === CLAUDE.md ===
  位置：### E2E 测试（Playwright）章节末尾
  新增：
  - **导航到 Agent 配置页**：不要点击 Agent 卡片
    （进入的是聊天页），应通过三点菜单→构建进入，
    或直接导航到 /agents/${id}/build

  === skills/diagnose.md ===
  位置：## 复现步骤 章节末尾
  新增：
  - **日志定位**：服务端错误优先查看 .logs/dev.log，
    不要只看浏览器控制台

  ### 提示词设计的三个关键决策

  **决策 1：谁触发这个技能？**

  > Q: 在什么时机执行经验提取？
  > A: 两个自然时机：
  > - **链路终结时**：验证/验收报告输出后，顺带提取
  > - **显式调用**：用户说"提取经验"、"总结一下这次学到了什么"

  **决策 2：自动写入还是人工审批？**

  > Q: 补丁直接写入 CLAUDE.md 和技能提示词吗？
  > A: **不能直接写入。** 原因：
  > - 经验可能是误判（某次失败可能是临时环境问题，不是通用规律）
  > - 规则措辞可能不准确
  > - 插入位置可能不对
  >
  > 正确流程：输出补丁 → 人工审阅 → 确认后写入。
  > 技能只产出**提案**，不执行**写入**。

  **决策 3：单条经验的置信度？**

  > Q: 一次踩坑就该写规则吗？还是需要多次确认？
  > A: 区分两类：
  > - **确定性经验**：系统行为明确（点击卡片去聊天页——这是确定的事实）→ 一次即可
  > - **策略性经验**：某种方法效果更好（用 URL 导航比 UI
  点击更稳定——这是概率性的）→ 标注置信度，让审阅者决定

⏺ 测试规约的第一性原理分析

  起点：为什么验证/验收之后还需要测试？

  Q: 验证报告说"缺陷已消除"，验收报告说"功能已达标"——不是已经结束了吗？
  A: 只证明了此刻是好的。明天有人改了相关代码呢？

  验证/验收是一次性人工判定，测试是永久性自动守卫。

  Q: 所以测试的本质功能是什么？
  A: 把一次性的人工判定固化为可重复执行的自动断言，使得"此刻证明过的事实"在未来
  的每次构建中被持续验证。

  Q: 用一句话说？
  A: 验证/验收证明"现在好了"，测试保证"以后也好"。

  ---
  核心问题：缺陷和需求的测试一样吗？

  Q: 缺陷验证后的测试和需求验收后的测试，结构一样吗？

  先看它们保护的东西——

  ┌──────────┬──────────────────────────────┬──────────────────────────────┐
  │          │         缺陷链路测试         │         需求链路测试         │
  ├──────────┼──────────────────────────────┼──────────────────────────────┤
  │ 保护什么 │ 一个特定的 bug 不复发        │ 一组能力不退化               │
  ├──────────┼──────────────────────────────┼──────────────────────────────┤
  │ 来源     │ 一条复现路径 + 变体          │ N 条验收标准 + 用户流程      │
  ├──────────┼──────────────────────────────┼──────────────────────────────┤
  │ 范围     │ 窄而深（一个点的周围）       │ 宽而系统（一个面的覆盖）     │
  ├──────────┼──────────────────────────────┼──────────────────────────────┤
  │ 性质     │ 回归防护（regression guard） │ 能力防护（capability guard） │
  └──────────┴──────────────────────────────┴──────────────────────────────┘

  Q: 那测试用例的单元结构一样吗？
  A: 一样。 不论来源，每个测试用例最终都是：

  Given（前置状态）→ When（操作）→ Then（断言）

  差异不在测试用例的结构，在于"从什么推导出测试用例"的过程。

  ---
  柏拉图式追问：一条测试规约需要什么？

  Q: 我要写一个自动化测试。最少需要知道什么？

  第一： "这个测试保护什么？"——Guard
  第二： "具体怎么测？"——Scenario
  第三： "还有哪些变体要覆盖？"——Variants
  第四： "放在测试金字塔的哪一层？"——Level
  第五： "这个测试为什么存在？"——Traceability

  闭合。

  ---
  五个不可约元素（每条测试规约的单元结构）

              测试规约
                 │
          ┌──────┼──────┐
          │      │      │
       Guard  Scenario  Variants
      (守什么) (怎么测)  (还测什么)
          │      │      │
          └──────┼──────┘
                 │
           ┌─────┴─────┐
           │           │
         Level    Traceability
        (哪层测)   (为什么测)

  1. Guard（守护目标）—— "这个测试保护什么不变量"

  一句话的断言：什么事实必须永远为真。

  Q: 为什么不直接写测试代码，要先声明 Guard？
  A: 因为没有 Guard 的测试是孤儿测试——半年后它失败了，没人知道它在保护什么，不知
  道该修测试还是修代码。

  Guard 是测试的存在理由。删除一个测试前，你看 Guard 
  就知道"删了它就没人防守这个不变量了"。

  Q: 缺陷和需求的 Guard 有什么不同？

  缺陷 Guard（具体的、防御性的）：
    "Agent 配置页编辑 name 后切 tab 再切回保存，name 不被清空"
    → 防止特定 bug 复发

  需求 Guard（通用的、确认性的）：
    "用户能按类型筛选列表，筛选后只显示匹配项"
    → 确保能力持续存在

  缺陷 Guard 像疫苗——针对已知的病原体。
  需求 Guard 像体检——确认机能正常。

  2. Scenario（测试场景）—— "具体怎么测"

  Given → When → Then 的完整描述。

  Q: Scenario 从哪来？

  缺陷链路：
    Given ← 缺陷报告的 Path 前置条件
    When  ← 缺陷报告的 Path 操作步骤
    Then  ← 缺陷报告的 Delta 取反（"期望行为"必须成立）

  需求链路：
    Given ← 需求报告的 Who（用户角色 + 场景状态）
    When  ← 验收标准中的操作
    Then  ← 验收标准中的预期结果

  缺陷的 Scenario 是复现路径的自动化版本——手动走过的路，让机器永远走。
  需求的 Scenario 是验收标准的可执行版本——人工判断过的清单，让机器永远检查。

  3. Variants（变体）—— "边界情况也要测"

  核心场景之外需要覆盖的变体。

  Q: Variants 从哪来？

  缺陷链路：
    → 验证报告的 Boundary Validation 中测过的变体
    → 修复报告的 Root Cause 推导出的同类输入
    "空值触发了 bug → undefined、空字符串、超长字符串也要测"

  需求链路：
    → 验收报告的 Experience Validation 中发现的边界行为
    → 需求报告的 Constraint 推导出的边界条件
    "筛选功能 → 空结果、单条结果、大量结果、特殊字符、并发筛选"

  Q: 缺陷和需求的 Variants 生成逻辑有什么区别？
  A: 
  - 缺陷 Variants 是纵深式：从一个已知故障点向外扩散——同一类输入的不同变体
  - 需求 Variants 是网格式：从多条验收标准的交叉组合生成——多个维度的排列

  4. Level（测试层级）—— "放在金字塔的哪一层"

  单元测试、集成测试、还是 E2E 测试。

  Q: 这个决策依据是什么？

  判断规则：
    Guard 涉及纯逻辑（计算、转换、校验）→ 单元测试
    Guard 涉及模块间交互（API调用、数据流）→ 集成测试
    Guard 涉及用户可见行为（页面、流程）  → E2E 测试

  Q: 缺陷和需求的 Level 分布有什么不同？
  A: 
  - 缺陷测试：通常集中在一个层级——bug 在哪层暴露就在哪层测。一个 API 层的 race 
  condition 写集成测试，一个 UI 层的状态丢失写 E2E
  - 需求测试：通常跨多个层级——一个需求可能需要单元测试验逻辑 + 集成测试验 API + 
  E2E 验完整流程

  缺陷测试分布        需求测试分布

      △                  △
     /E\                /E\    ← 用户流程
    /   \              /   \
   / I   \            / I   \  ← API 集成
  /       \          /       \
  / U       \        / U       \ ← 业务逻辑
  ───────────        ───────────
   ↑ 集中一层         ↑ 分布多层

  5. Traceability（追溯）—— "这个测试因何而生"

  链接回原始报告的引用。

  Q: 为什么需要 Traceability？测试本身不够吗？
  A: 三个场景需要它：

  a) 测试失败时：这个测试是为了防止什么？是 #127 的 bug 回归还是需求 R-05 
  的验收项？知道来源才能判断严重度。

  b) 需求变更时：需求 R-05 
  被修改了，哪些测试需要相应更新？没有追溯就得全局搜索。

  c) 测试清理时：这个测试还有存在价值吗？追溯到原始报告，如果那个功能已经下线，
  测试可以安全删除。

  Q: Traceability 长什么样？

  缺陷链路追溯：
    origin: "defect-report#127"
    fixed_by: "fix-report#127"
    verified_by: "verification-report#127"

  需求链路追溯：
    origin: "requirement#R-05"
    criterion: "Acceptance#3: 筛选后列表刷新"
    accepted_by: "acceptance-report#R-05"

  ---
  缺陷 vs 需求：同结构、异推导

                 测试规约结构（统一）
                       │
                ┌──────┼──────┐
                │      │      │
             Guard  Scenario  Variants
                │      │      │
                └──────┼──────┘
                       │
                 ┌─────┴─────┐
                 │           │
               Level    Traceability

  推导过程（不同）：

  缺陷链路推导                     需求链路推导
  ─────────────                    ─────────────

  缺陷报告.Delta ──→ Guard         需求报告.Acceptance ──→ Guard
    "什么不能再错"                    "什么必须保持"

  缺陷报告.Path ──→ Scenario       验收报告.Criteria ──→ Scenario
    "复现步骤自动化"                   "验收标准可执行化"

  验证报告.Boundary ──→ Variants   验收报告.Experience ──→ Variants
    "已验边界纳入测试"                  "已验边界纳入测试"

  修复报告.Root Cause ──→ Level    需求报告.What ──→ Level
    "根因在哪层就测哪层"                "能力跨几层就测几层"

  缺陷报告 ID ──→ Traceability     需求报告 ID ──→ Traceability

  结论：测试用例是同一种"砖"，但缺陷链路和需求链路是两套不同的"图纸"。

  覆盖矩阵：怎么确认测够了

  单独的测试规约不够——你需要知道整体覆盖情况。

  缺陷链路覆盖矩阵：

  | 验证报告检查项 | 测试用例 | 层级 | 状态 |
  |---------------|---------|------|-----|
  | 复现验证 | test_name_not_cleared | E2E | ✓ |
  | 边界：undefined | test_name_undefined | Unit | ✓ |
  | 边界：空字符串 | test_name_empty | Unit | ✓ |
  | 回归：其他字段 | test_other_fields | Integration | ✓ |

  需求链路覆盖矩阵：

  | 验收标准 | 测试用例 | 层级 | 状态 |
  |---------|---------|------|-----|
  | AC1: 按类型筛选 | test_filter_by_type | E2E | ✓ |
  | AC2: 多选筛选 | test_multi_filter | E2E | ✓ |
  | AC3: 筛选持久化 | test_filter_url_sync | Integration | ✓ |
  | AC4: 空结果提示 | test_empty_state | Unit | ✓ |
  | 约束: 不影响排序 | test_sort_with_filter | Integration | ✓ |
  | 体验: 筛选→排序→导出 | test_full_flow | E2E | ✓ |

⏺ 缺陷守护规约的第一性原理分析

  起点：缺陷守护的特殊性

  Q: 缺陷守护和普通测试有什么根本区别？
  A: 普通测试可能是先验的（"我觉得该测这个"）。缺陷守护是后验的——它来自一次真实
  的事故。

  Q: 这导致什么结构性差异？
  A: 缺陷守护拥有普通测试没有的东西——完整的事故档案。它知道：
  - 什么坏了（缺陷报告）
  - 为什么坏了（修复报告）
  - 怎么确认修好了（验证报告）

  普通测试只有"我认为应该测什么"。缺陷守护有"我知道什么曾经出过事"。

  普通测试是猜测性防御，缺陷守护是针对性免疫。

  ---
  关键洞察：双层防护

  Q: 缺陷守护应该测"症状"还是测"根因"？

  用你的例子——

  ┌────────┬────────────────┬────────────────────────────────────────────────┐
  │  层级  │     测什么     │                      例子                      │
  ├────────┼────────────────┼────────────────────────────────────────────────┤
  │ 症状层 │ 用户可见的行为 │ "编辑 name → 切 tab → 切回 → 保存，name        │
  │        │                │ 不丢失"                                        │
  ├────────┼────────────────┼────────────────────────────────────────────────┤
  │ 根因层 │ 底层的故障机制 │ "tab 切换时 form reset handler 不应被触发"     │
  └────────┴────────────────┴────────────────────────────────────────────────┘

  Q: 只测症状行不行？
  A: 不行。假设未来有人重构了 tab 组件，引入了一个新的 reset 触发路径。原来的
  E2E 测试路径恰好没走到这条新路径——症状测试通过了，但同类 bug 已经埋下。

  Q: 只测根因行不行？
  A: 也不行。假设根因被正确防护，但另一个地方（不在 reset handler 里）也能导致
  name 丢失。根因测试通过了，但用户又看到了同样的症状。

  症状层测的是"用户看到的结果对吗"，根因层测的是"底层机制健康吗"。缺陷守护必须双
  层覆盖——这是它区别于需求测试的根本特征。

  需求测试没有"根因"概念——它不知道什么曾经坏过，只知道什么应该是对的。缺陷守护知
  道具体的故障机制，必须在那个机制层面上钉一颗钉子。

  ---
  柏拉图式追问

  Q: 我要给一个已修复的缺陷写守护测试。最少需要什么？

  第一： "这个测试守护什么？"——我需要 Invariant。

  第二： "怎么触发原来的 bug？"——我需要 Trigger Scenario。

  Q: 有了触发场景不就够了？Given/When/Then 一写，自动化执行。
  A: 不够。你只防住了这条路径上的这个症状。根因不设防的话，同一个故障机制从另一
  条路径爆出来，你的测试不会响。

  第三： "在根因层面怎么守？"——我需要 Cause Anchor。

  第四： "原路径的变体呢？"——我需要 Boundary Set。

  第五： "修复本身没弄坏别的吧？"——我需要 Blast Shield。

  闭合。

  五个不可约元素

               缺陷守护规约
                    │
            ┌───────┼───────┐
            │       │       │
       Invariant  Trigger  Cause
        (守什么)  (怎么触发) Anchor
                           (根因钉)
            │       │       │
            └───────┼───────┘
                    │
            ┌───────┴───────┐
            │               │
       Boundary Set    Blast Shield
        (变体集)        (防爆盾)

  1. Invariant（不变量）—— "什么事实必须永远为真"

  一句断言，是 Delta 的反面。

  Q: Invariant 和 Guard 有什么区别？之前通用测试规约里用的是 Guard。
  A: Guard 是通用概念（"测试保护什么"）。Invariant 
  是缺陷守护的具体化——它来自一个已被证伪过的命题，现在要确保它永远为真。

  Q: 怎么从缺陷报告推导？
  A: Delta 取反：
  - Delta："期望 name 保存后持久化，实际刷新后 name 为空"
  - Invariant："编辑 name 并保存后，刷新页面 name 必须保留"

  Delta 说的是"什么坏了"，Invariant 说的是"什么不能再坏"。

  Q: Invariant 应该写多具体？
  A: 测试标准：读完后能直接写出 expect() 断言。
  - 太模糊："保存功能正常" ← 无法转为断言
  - 恰好："编辑 Agent name 为 'X' → 切 tab → 切回 → 保存 → 刷新，name 应等于 
  'X'" ← 可直接 expect(name).toBe('X')
  - 过度："内存中 formState.dirtyFields 应包含 name 键且值为 true..." ← 
  这是实现细节，不是不变量

  2. Trigger Scenario（触发场景）—— "怎么复现原来的 bug"

  将缺陷报告的 Path 转化为 Given/When/Then。

  Q: 直接照搬 Path 吗？
  A: 不完全。Path 是人工复现步骤（可能有冗余），Trigger Scenario 
  是最小必要步骤。

  Path（缺陷报告）：
  1. 打开 /agents 页面
  2. 找到 Agent "Test"
  3. 点击三点菜单
  4. 点击"构建"
  5. 修改 name 为 "New Name"
  6. 点击 Skills tab
  7. 等待 3 秒
  8. 点击 General tab
  9. 点击 Save
  10. 刷新页面

  Trigger Scenario（精简）：
  - Given：已打开 Agent 配置页，name = "Original"
  - When：修改 name 为 "New Name" → 切离当前 tab → 切回 → 保存
  - Then：刷新后 name === "New Name"

  Q: 为什么要精简？保留全部步骤不更安全吗？
  A: 冗余步骤会引入虚假依赖。如果第 7 步"等待 3 秒"其实和 bug 
  无关，但测试里保留了它，那未来有人优化了加载速度让 3 
  秒等待失效，测试就会假阴性（fail for wrong reason）。Trigger Scenario 只保留与
   bug 因果相关的步骤。

  Q: 怎么判断哪些步骤因果相关？
  A: 参考修复报告的 Root Cause。Root Cause 说"tab 切换触发了意外 reset"，那"切 
  tab"是因果相关的，"等待 3 秒"不是。

  3. Cause Anchor（根因锚点）—— "在故障机制层面钉一颗钉子"

  直接测试修复报告中 Root Cause 指向的代码逻辑。

  Q: 这是缺陷守护独有的元素？
  A: 是。 需求测试没有这个概念——它不知道什么曾经坏过。缺陷守护知道故障的精确机制
  ，所以可以（也必须）在那个机制层面设置哨兵。

  Q: Cause Anchor 和 Invariant 的区别？
  A: 不同抽象层级的断言：
  - Invariant（症状层）："保存后 name 不丢失"——用户视角
  - Cause Anchor（机制层）："tab 切换时 formState 不被 reset"——代码视角

  同一个 bug 的两道防线，一道在外（用户看到的），一道在内（代码里的）。

  Q: Cause Anchor 怎么从修复报告推导？
  A: 
  - Root Cause："tab 切换组件 unmount 时触发了 form reset cleanup"
  - Change："在 tab 切换逻辑中加了 shouldReset 条件判断"
  - Cause Anchor：test("tab switch should not reset form state", () => { 
  switchTab(); expect(form.isDirty).toBe(true); })

  Q: Cause Anchor 通常是什么层级的测试？
  A: 
  通常是单元测试或集成测试——因为它测的是代码内部机制，不需要完整的用户流程。这和
   Trigger Scenario（通常 E2E）形成互补：

            E2E层    ─── Invariant + Trigger Scenario
                         "用户视角：保存后 name 在"

       Integration  ─── Cause Anchor（可能在此层）

           Unit层   ─── Cause Anchor
                         "代码视角：tab 切换不 reset form"

  双层防护 = E2E 守症状 + Unit/Integration 守根因。

  4. Boundary Set（边界集）—— "同类变体也要防住"

  基于 Root Cause 推导的同类输入和路径变体。

  Q: Boundary Set 从哪来？
  A: 两个来源，逻辑不同：

  来源 1：验证报告的 Boundary Validation（已验证的变体）
    → 验证者已手动确认过的边界 case
    → 直接转为测试用例

  来源 2：Root Cause 推导（未验证但可推理的变体）
    → 根因是"组件 unmount 触发 reset"
    → 推导：还有哪些操作会触发 unmount？
      → 切到其他 tab ✓（已验）
      → 关闭侧面板再打开？（未验，但同一机制）
      → 路由跳转再返回？（未验，但同一机制）
    → 这些推导出的变体也应纳入测试

  Q: 来源 1 和来源 2 的区别？
  A: 
  - 来源 1 是经验变体——人已经验过，转为自动化
  - 来源 2 是推理变体——从根因推导出的同类触发条件，可能没人手动验过

  来源 2 是缺陷守护比手动验证更强的地方——它可以覆盖验证者没想到但逻辑上应该测的 
  case。

  Q: Boundary Set 应该有多大？
  A: 收敛原则：围绕 Root Cause 画圆，半径不超过一步推导。
  - 同一机制的不同触发路径 ← 要测
  - 同一函数的不同输入值 ← 要测
  - 不同机制但类似症状 ← 太远，不属于此 bug 的守护范围

  5. Blast Shield（防爆盾）—— "修复本身没制造新问题"

  确认修复的波及范围内功能仍正常。

  Q: 这不是验证报告已经做了的 Regression Result 吗？
  A: 验证报告做了一次性的人工回归检查。Blast Shield 把这个检查永久化。

  Q: Blast Shield 从哪来？
  A: 
  - 修复报告的 Blast Radius："改了 form reset 逻辑，可能影响 form 的 dirty 
  检测和 reset 按钮行为"
  - 验证报告的 Regression Result："手动验证了 reset 按钮仍正常、dirty 
  标记仍正确"
  - Blast Shield：把这些回归验证点转为自动化测试

  Q: Blast Shield 和 Boundary Set 的区别？
  A: 方向不同。
  - Boundary Set 是内向的——同一个 bug 的不同触发变体（围绕缺陷本身）
  - Blast Shield 是外向的——修复可能影响的其他功能（围绕修复的影响面）

  Boundary Set 问"bug 有没有兄弟"。Blast Shield 问"药有没有副作用"。

  Q: Blast Shield 需要多大范围？
  A: 只覆盖修复报告 Blast Radius 中明确标记的区域。不做全量回归——那是 CI 
  的事。Blast Shield 是定向回归：你改了什么区域，就守住那个区域。

  从缺陷链路三份报告到五个元素的推导路径

  缺陷报告                修复报告               验证报告
  ────────                ────────               ────────
  Delta ───────────────────────────────────────→ Invariant

  都能追溯到一次真实的事故。

⏺ 需求守护规约的第一性原理分析

  起点：需求守护与缺陷守护的根本分野

  Q: 缺陷守护知道"什么曾经坏过"，需求守护知道什么？
  A: 需求守护知道"什么应该是对的"——但从来没坏过，所以没有事故档案可依赖。

  Q: 这导致什么结构性差异？

  ┌──────────┬───────────────────────────┬───────────────────────────┐
  │          │         缺陷守护          │         需求守护          │
  ├──────────┼───────────────────────────┼───────────────────────────┤
  │ 知识来源 │ 一次真实事故              │ 一份契约（验收标准）      │
  ├──────────┼───────────────────────────┼───────────────────────────┤
  │ 保护目标 │ 一个点（特定 bug 不复发） │ 一个面（整体能力不退化）  │
  ├──────────┼───────────────────────────┼───────────────────────────┤
  │ 测试数量 │ 少而深（1 个触发 + 变体） │ 多而广（N 条标准 + 旅程） │
  ├──────────┼───────────────────────────┼───────────────────────────┤
  │ 独特优势 │ 有根因可以钉              │ 有用户旅程可以串          │
  └──────────┴───────────────────────────┴───────────────────────────┘

  Q: 缺陷守护的灵魂是"双层防护"（症状层 + 根因层）。需求守护的灵魂是什么？
  A: 也是双层——但两层的含义不同：

  缺陷守护的双层：           需求守护的双层：
    ┌─── 症状层（用户看到的）    ┌─── 标准层（每条标准独立验）
    └─── 根因层（代码机制的）    └─── 旅程层（标准串起来走通）

  缺陷守护垂直切：从表象钻到机制。需求守护水平扫：从单点扩到全程。

  ---
  关键洞察：标准全过 ≠ 功能可用

  Q: 把每条验收标准转成测试用例不就行了？
  A: 不行。验收报告已经揭示了这个问题——

  验收标准 ✓ 能筛选
  验收标准 ✓ 能排序
  验收标准 ✓ 能导出

  但是：筛选 → 排序 → 导出，这个连续流程中
  排序丢失了筛选状态 → 导出的是未筛选的全量数据

  每条标准独立测试都通过，串起来就崩了。

  标准是离散的检查点，用户体验是连续的旅程。需求守护必须同时覆盖两者——这是它的核
  心设计难题。

  柏拉图式追问

  Q: 我要给一个已验收的需求写守护测试。最少需要什么？

  第一： "这组测试保护什么能力？"——我需要 Capability。

  第二： "验收标准怎么转成测试？"——我需要 Criteria Matrix。

  Q: 每条标准一个 Given/When/Then 不就完了？
  A: 不够。标准之间的衔接没有被测到。用户不会一个个孤立地使用功能——他筛选完就排
  序，排序完就导出。

  第三： "完整的用户旅程通不通？"——我需要 Journey Test。

  Q: 功能通了就行了？
  A: 还差两样。需求报告有
  Constraint——业务规则不能被违反。功能做出来了，但可能悄悄越界。

  第四： "业务约束没被打破吧？"——我需要 Constraint Guard。

  Q: 最后呢？
  A: 实现报告声明了 Known
  Gaps——已知的不完美。这些不完美被接受了，但不能恶化。今天"只支持 CSV
  导出"是可接受的，明天 CSV 导出也坏了就不可接受了。

  第五： "已知的底线没被跌破吧？"——我需要 Degradation Fence。

       (守什么)    Matrix     Test

  1. Capability（能力宣言）—— "保护什么能力不退化"

  对整组测试要守护的能力的顶层声明。

  Q: 和缺陷守护的 Invariant 有什么区别？
  A: 粒度和性质不同。
  - Invariant："Agent name 编辑后保存不丢失"——一个点，来自一次事故
  - Capability："用户能按类型筛选、排序、导出列表数据"——一个面，来自一份需求

  Invariant 是否定式（这个不能再坏），Capability 是肯定式（这个必须保持能用）。

  Q: Capability 从哪来？
  A: 需求报告的 What（能力声明）+ Why（动机）：
  - What："用户能按类型筛选列表"
  - Why："因为数据太多找不到目标"
  - Capability："列表筛选能力：用户能通过类型筛选快速定位目标数据"

  Why 的价值：当未来有人质疑"这个测试还需要吗"时，Why 解释了能力的业务必要性。

  Q: 一个需求对应一个 Capability？
  A: 通常是。但大需求可能拆成多个 Capability：
  - 需求："列表管理功能"
  - Capability 1："筛选能力"
  - Capability 2："排序能力"
  - Capability 3："批量操作能力"

  每个 Capability 独立一份守护规约。

  2. Criteria Matrix（标准矩阵）—— "逐条验收标准转为测试"

  将需求报告的每条 Acceptance 标准转化为独立的 Given/When/Then。

  Q: 这是需求守护的主体部分？
  A: 是。缺陷守护的主体是一个 Trigger Scenario（单一路径），需求守护的主体是一个
   矩阵（多条标准 × 多种场景）。

  Q: 怎么从验收标准推导？
  A:
  验收标准 AC-1："选择类型 A 后，列表只显示类型 A 的条目"
    → Given: 列表中有类型 A/B/C 各若干条目
      When:  选择筛选类型 A
      Then:  列表只显示类型 A 的条目，B/C 不可见

  验收标准 AC-2："选择'全部'后，列表恢复完整"
    → Given: 当前已筛选类型 A
      When:  选择"全部"
      Then:  列表显示所有类型的条目

  验收标准 AC-3："筛选状态刷新后保持"
    → Given: 当前已筛选类型 A
      When:  刷新页面
      Then:  筛选仍为类型 A，列表仍只显示 A

  Q: 和缺陷守护的 Trigger Scenario 对比？
  A: 
  - Trigger Scenario：1 个场景，精确到步骤级别（最小必要路径）
  - Criteria Matrix：N 个场景，每条验收标准至少一个，覆盖面优先

  缺陷守护追求深度（一个点钻到底），需求守护追求广度（所有标准都覆盖到）。

  Q: 每条标准只需要一个测试吗？
  A: 核心路径一个。但如果标准本身有隐含的边界，可以展开：
  AC-1 核心: 筛选类型 A → 只显示 A
  AC-1 边界: 筛选后无匹配项 → 显示空状态提示
  AC-1 边界: 筛选后只有 1 条 → 正常显示（非空状态）

  3. Journey Test（旅程测试）—— "标准串起来走通吗"

  模拟用户的完整使用旅程，测试标准之间的衔接。

  Q: 这是需求守护的独有元素？
  A: 是。 就像 Cause Anchor 是缺陷守护的独有元素一样。
  - Cause Anchor 独有是因为只有缺陷才有"根因"可钉
  - Journey Test 独有是因为只有需求才有"用户旅程"可串

  缺陷没有"旅程"概念——它是一个点状事故。需求有——它是一个面状能力。

  Q: Journey Test 和 Criteria Matrix 的区别到底是什么？
  A: 用餐厅类比：
  - Criteria Matrix 测的是：每道菜单独好不好吃（前菜 ✓、主菜 ✓、甜点 ✓）
  - Journey Test 测的是：整顿饭的体验顺不顺（上菜顺序对吗？口味递进合理吗？前菜
  太咸导致主菜无味？）

  Criteria Matrix 测节点，Journey Test 测边（节点之间的连接）。

  Q: Journey Test 从哪来？
  A: 两个来源：
  来源 1：验收报告的 Experience Validation
    验收者走过的完整旅程，已确认顺畅的路径
    → 直接转为 E2E 测试

  来源 2：需求报告的 Who 场景推导
    用户角色的典型工作流
    → "运营人员每天的流程：打开列表 → 筛选类型 → 排序 → 查看详情 → 导出"
    → 这个完整流程作为一个 E2E Journey Test

  Q: Journey Test 应该有几个？
  A: 收敛原则：覆盖验收报告中 Experience Validation 走过的主要路径，通常 1-3 
  个。
  - Happy Path Journey（主流程）：必须有
  - Alternative Journey（备选流程）：如果用户有不同使用模式
  - Recovery Journey（异常恢复）：如果验收时发现过不顺畅的恢复路径

  Q: Journey Test 和 E2E 测试是一回事吗？
  A: Journey Test 一定是 E2E 层级的，但不是所有 E2E 都是 Journey Test。
  - Criteria Matrix 中的某些项也可能是 E2E（如"筛选后列表刷新"）
  - 但 Criteria Matrix 的 E2E 测的是单一标准
  - Journey Test 的 E2E 测的是标准的串联——一个测试里包含多个标准的连续操作

  4. Constraint Guard（约束守卫）—— "业务红线没被越过"

  确保需求报告中的 Constraint 在实现中持续被尊重。

  Q: 缺陷守护没有这个元素，为什么需求守护需要？
  A: 因为缺陷没有"约束"的概念——bug 
  就是错的，修好就行，没有"可以修但不能这样修"的限制。

  需求有约束——"做筛选功能，但不能改变现有排序逻辑"、"做批量删除，但必须留审计日
  志"。功能可能做对了，但约束可能悄悄被违反。

  Q: Constraint Guard 测什么？
  A: 测否定性断言——"什么不应该发生"：
  Criteria Matrix（肯定性）：
    When: 筛选类型 A
    Then: 只显示 A  ← "应该发生的事确实发生了"

  Constraint Guard（否定性）：
    When: 筛选类型 A
    Then: 排序顺序不变  ← "不应该发生的事确实没发生"

    When: 批量删除记录
    Then: audit_log 表有对应记录  ← "约束条件持续被满足"

  Q: Constraint 从哪来？
  A: 两个来源：
  - 需求报告的 Constraint（显式声明的约束）
  - 实现报告 Traceability 中的 约束合规列（实现如何满足约束）
  - 验收报告中对约束的 验证结果

  Q: Constraint Guard 和 Criteria Matrix 能合并吗？
  A: 技术上可以（都是 Given/When/Then），但语义上应分开：
  - Criteria Matrix 回答"功能做了什么"（正面验证）
  - Constraint Guard 回答"功能没做什么"（反面验证）

  分开的好处：未来约束变更时（如"审计日志不再需要"），可以精确定位到 Constraint 
  Guard 中的对应测试，而不用在整个测试套件里搜索。

  5. Degradation Fence（退化围栏）—— "已接受的底线不能再跌"

  防止 Known Gaps 中的已知局限进一步恶化。

  Q: 这是需求守护独有的？缺陷守护没有？
  A: 独有。 因为：
  - 缺陷修复追求完全消除——bug 要么修好要么没修好，没有"可接受的部分修好"
  - 需求实现常有部分交付——"导出只做了 CSV，Excel 以后补"。这个"以后补"的 CSV 
  如果也坏了，就是退化

  Q: Degradation Fence 测什么？
  A: 测 Known Gaps 的底线：
  Known Gap: "导出只支持 CSV，不支持 Excel"
    → 验收时接受了这个缺口
    → Degradation Fence: CSV 导出必须持续工作
    → 如果某天 CSV 导出也坏了，就是跌破底线

  Known Gap: "筛选不支持模糊匹配，只支持精确匹配"
    → 验收时接受了这个缺口
    → Degradation Fence: 精确匹配必须持续工作
    → 如果某天精确匹配也坏了，就是跌破底线

  Q: Degradation Fence 从哪来？
  A: 
  - 实现报告的 Known Gaps："什么没做到"
  - 验收报告的 Gap Assessment："哪些缺口被接受了"
  - 从"被接受的缺口"中提取已实现的部分作为底线

  Q: 和 Criteria Matrix 的区别？
  A: 
  - Criteria Matrix 守护的是达标的能力（验收通过的标准）
  - Degradation Fence 守护的是及格线以下的底线（验收时已知不完美但可接受的部分）

  Criteria Matrix 划的是"优秀线"，Degradation Fence 划的是"生死线"。

  需求报告              实现报告               验收报告
  ────────              ────────               ────────
  What + Why ──────────────────────────────→ Capability
    "要什么能力/为什么"                        "守护什么能力"

  Acceptance ─────────────────────────────→ Criteria Matrix
    "验收标准"                                "标准→测试场景"

  Who ──────────┐
                ├─── Experience ──────────→ Journey Test
                │    Validation              "完整旅程走通"
  (用户角色/场景)│

  Constraint ────── Traceability ─────────→ Constraint Guard
    "业务约束"       "约束如何满足"            "约束持续满足"

                Known Gaps ─┐
                            ├────────────→ Degradation Fence
                Gap ────────┘               "底线不跌破"

  ---
  缺陷守护 vs 需求守护：终极对照

  缺陷守护                          需求守护
  ──────                            ──────
  Invariant (不变量)        ←→     Capability (能力宣言)
    一个点的否定式守护                一个面的肯定式守护
    "这个不能再坏"                    "这个必须保持能用"

  Trigger Scenario (触发)   ←→     Criteria Matrix (标准矩阵)
    1 条路径                          N 条标准
    追求深度                          追求广度

  Cause Anchor (根因锚点)   ←→     Journey Test (旅程测试)
    【缺陷独有】                      【需求独有】
    垂直钻：从症状到机制               水平串：从单点到全程
    "在根因层面钉钉子"                 "标准串起来走通吗"

  Boundary Set (边界集)     ←→     Constraint Guard (约束守卫)
    同一 bug 的输入变体                业务红线的否定断言
    "bug 有没有兄弟"                   "规矩有没有被破"

  Blast Shield (防爆盾)     ←→     Degradation Fence (退化围栏)
    修复的副作用防护                   已知缺口的底线防护
    "药有没有副作用"                   "及格线有没有跌破"

  两者的双层防护方向正交：
  - 缺陷守护：垂直双层（E2E 守症状 ↕ Unit 守根因）
  - 需求守护：水平双层（Criteria 守单点 ↔ Journey 守全程）
